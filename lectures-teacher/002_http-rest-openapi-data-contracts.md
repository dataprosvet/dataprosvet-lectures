## Слайд 04. HTTP — Запрос: структура HTTP/1.1

Время: 09:03:15–09:04:08
Длительность: 53 с.

### На слайде

![Запрос: структура HTTP/1.1](../assets/lecture-002/http11-request.png)

- Headers: заголовков может быть много — каждый на отдельной строке

- Источник: RFC 9112 §2.1

### Пояснение преподавателя

HTTP (Hypertext Transfer Protocol) задаёт семантику запросов и ответов. Клиент инициирует запрос, сервер сообщает результат. Сначала рассмотрим общую запись HTTP/1.1; угловые скобки обозначают места для значений, а английские подписи на рисунке — объяснение, не часть сообщения.[^http]

```text
<method> <path?query> HTTP/1.1  ← request line
Host: <host[:port]>                     ← host
<header-name>: <value>                 ← headers
<empty line>                            ← header/body boundary
<optional content>           ← body (may be binary)

HTTP/1.1 <status-code> <reason-phrase>            ← status line
<header-name>: <value>                 ← response headers
<empty line>
<response content, when permitted>
```

В HTTP/1.1 строки разделены CRLF. Границу и длину содержимого определяют правила протокола; показанная схема не утверждает, что после любого запроса обязательно есть тело. `Content-Length`, когда используется, измеряет байты, а не символы.[^http11]

### Ход показа и границы

Сначала читать абстрактную схему. Указать метод, цель запроса, версию, имя/значение заголовка, пустую строку и тело; затем числовой статус ответа. Подписи справа не являются сетевыми байтами. Не обсуждать сейчас chunked, HPACK или парсинг протокола.

## Слайд 06. HTTP — Получение прогноза: заполненный запрос

Время: 09:05:00–09:06:30
Длительность: 90 с.

### На слайде

![Получение прогноза: заполненный запрос](../assets/lecture-002/http11-forecast-highlighted.png)

- Path и query

- 42 — офис / days=1 — горизонт

- Accept

- Желаемый формат / ответа сервера

### Пояснение преподавателя

Конкретный запрос к локальному Read API:

```http
GET /offices/42/forecast?days=1 HTTP/1.1
Host: 127.0.0.1:8000
Accept: application/json

```

`GET` выражает намерение получить представление. `/offices/42/forecast` адресует ресурс; `42` — значение параметра пути `office_id`. `days=1` — query-параметр, уточняющий горизонт. У GET в нашем контракте нет тела. Полный URL при этом — `http://127.0.0.1:8000/offices/42/forecast?days=1`: схема и authority не повторяются в показанной origin-form стартовой строке.

`Accept` задаёт предпочтения клиента для **ответа**. `Content-Type` описывает содержимое **того сообщения, в котором стоит**. Если клиент отправляет JSON и хочет получить CSV, он задаёт `Content-Type: application/json` и `Accept: text/csv`. Сервер должен поддерживать такой обмен по контракту; одни заголовки эту возможность не создают.

Второе обращение передаёт наблюдение. Здесь показан полный JSON без завершающего перевода строки; его длина — 30 байт:

```http
POST /observations HTTP/1.1
Host: 127.0.0.1:8001
Content-Type: application/json
Content-Length: 30

{"office_id":42,"visitors":45}
```

Ответ мока — `201 Created` с `Content-Type: application/json` и телом:

```json
{"id":"mock-observation","observation":{"office_id":42,"visitors":45}}
```

Это имитация: данные не сохраняются, идентификатор фиктивный, повтор снова вернёт 201. В реальном контракте успешное создание должно подтверждать обещанный эффект. Ответ GET значительно длиннее: он содержит 24 часовые точки для одного дня или 168 для недели, а также `office_id`, `days`, `interval_hours`, временные отметки и признаки учебного результата. Полные проверенные тела доступны в [сохранённых обменах](../attachments/seminar-002/lecture-02-reserve/exchanges.md).

### Ход показа и границы

Прочитать заполненный GET: method, path, query, version, headers, пустая строка; показать отсутствие тела. Затем перейти к POST. Accept описывает желаемый формат ответа.

## Слайд 08. HTTP — Версии: одна семантика, разная передача

Время: 09:08:00–09:09:00
Длительность: 60 с.

### На слайде

- HTTP/1.1 → TCP; текстовая стартовая строка и заголовки

- Тело может быть бинарным. Соединение переиспользуется.

- HTTP/2 → Кадры разных потоков в одном TCP-соединении

- HPACK; потеря TCP-данных задерживает доставку потокам.

- HTTP/3 → Потоки поверх QUIC/UDP

- QPACK; QUIC обеспечивает надёжность и интегрирует TLS 1.3.

### Пояснение преподавателя

Смысл методов, статусов и основных полей сохраняется между версиями; меняется организация передачи. Поэтому текстовая запись HTTP/1.1 удобна для первого чтения контракта, даже когда реальное соединение использует другую версию.[^http2][^http3]

| Версия | Передача | Практическое следствие |
|---|---|---|
| HTTP/1.1 | Текстовая стартовая строка и заголовки поверх TCP; тело может быть бинарным; соединение переиспользуется | Ответы при pipelining следуют порядку запросов; для независимого параллелизма часто используют несколько соединений |
| HTTP/2 | Бинарные кадры нескольких логических потоков в TCP-соединении; HPACK для заголовков | Два ответа можно передавать вперемежку; потеря TCP-данных всё ещё задерживает доставку потокам этого соединения |
| HTTP/3 | Потоки и кадры поверх QUIC/UDP; QPACK; TLS 1.3 интегрирован в QUIC | Надёжность обеспечивает QUIC. Потеря данных одного потока не создаёт TCP-блокировку других; общая перегрузка и иные зависимости остаются |

**Первые RFC версий:** январь 1997 — HTTP/1.1 (RFC 2068) → **18 лет 4 месяца** → май 2015 — HTTP/2 (RFC 7540) → **7 лет 1 месяц** → июнь 2022 — HTTP/3 (RFC 9114). Здесь «дата принятия» означает публикацию первого стандартизующего RFC, а не начало экспериментов или массового внедрения. RFC 9112 и RFC 9113, опубликованные в июне 2022 года, уточняют HTTP/1.1 и HTTP/2; они не означают, что обе версии появились в 2022 году.[^history]

В датированном снимке **Cloudflare Radar, Worldwide, All traffic, семь дней до 14.09.2026 14:30 UTC**: HTTP/2 — **52,5%**, HTTP/1.x — **27,6%**, HTTP/3 — **19,9%**. В этой выборке чаще HTTP/2. Это доли запросов, наблюдаемых Cloudflare, а не всех API или сайтов мира; 1.x объединяет версии семейства. Показатели меняются. На участках браузер → CDN и CDN → исходный сервер версии могут различаться.[^radar]

### Ход показа и границы

## Слайд 11. HTTP — HTTP/2: соединение, поток, сообщение, кадр

Время: 09:11:00–09:13:00
Длительность: 120 с.

### На слайде

![HTTP/2: соединение, поток, сообщение, кадр](../assets/lecture-002/http2-frame.png)

Источники схемы: [Cabulous — HTTP/2 and how it works](https://cabulous.medium.com/http-2-and-how-it-works-9f645458e4b2), [RFC 9113, §§4–5](https://www.rfc-editor.org/rfc/rfc9113.html).

- Carson: HTTP/2 and How it Works RFC 9113 §§4–5, 8

### Пояснение преподавателя

**Соединение → потоки → сообщения запроса/ответа → кадры.** Логический поток HTTP/2 — последовательность связанных кадров внутри соединения; это не поток операционной системы. HEADERS передаёт блок полей, сжатый HPACK, а DATA — содержимое сообщения. JSON-тело при переходе на HTTP/2 может остаться JSON.

```text
Заголовок кадра — 9 байт; числа в скобках обозначают биты
+-------------+----------+-----------+-------+----------------+
| Length (24) | Type (8) | Flags (8) | R (1) | Stream ID (31) |
+-------------+----------+-----------+-------+----------------+
| Payload: Length байт                                       |
+-----------------------------------------------------------+
```

Источник идеи подачи схемы — [Carson, HTTP/2 and How it Works](https://cabulous.medium.com/http-2-and-how-it-works-9f645458e4b2); технические правила — [RFC 9113 §4.1](https://www.rfc-editor.org/rfc/rfc9113.html#section-4.1). Схема составлена для этой лекции.

`Length` измеряет **байты payload**, без девяти байт заголовка. `Type` задаёт вид кадра; `Flags` уточняет его обработку. `R` — зарезервированный бит. `Stream ID` связывает кадр с потоком; нулевой ID используется для кадров уровня соединения. Поля порядкового номера кадра здесь нет.

Метод и адрес не исчезают. Например, **после HPACK-декодирования** поля запроса можно прочитать так:

```text
:method    = GET
:scheme    = https
:authority = api.example.edu
:path      = /offices/42/forecast?days=1
```

В ответе будет псевдозаголовок `:status = 200`. Это читаемое представление декодированных полей, не буквальные сетевые байты и не строка `GET … HTTP/2`.[^http2]

### Ход показа и границы

Обязательно показать готовый рисунок. Подробный побитовый разбор Length/Type/Flags/R/Stream ID, допустимых значений и примеров флагов — в методичке преподавателя; здесь достаточно связать заголовок с payload и потоком. Показать девять байт заголовка. Во врезке вывести декодированные :method/:scheme/:authority/:path из пояснения и :status ответа, обязательно подписав «после HPACK-декодирования». Не изображать строку GET … HTTP/2 как начало сетевого сообщения. На слайде числа размеров подписать битами, Length — байтами payload.

## Слайд 12. HTTP — HTTP/2: два потока в одном соединении

Время: 09:13:00–09:15:00
Длительность: 120 с.

### На слайде

![HTTP/2: два потока в одном соединении](../assets/lecture-002/http2-streams.png)

Источники схемы: [Cabulous — HTTP/2 and how it works](https://cabulous.medium.com/http-2-and-how-it-works-9f645458e4b2), [RFC 9113, §§4–5](https://www.rfc-editor.org/rfc/rfc9113.html).

- Carson: HTTP/2 and How it Works RFC 9113 §§4–5, 8

### Пояснение преподавателя

Рассмотрим отдельную иллюстрацию протокола: соединение уже установлено, начальные настройки опущены, сервер располагает прогнозами для обоих офисов. В реальном учебном HTTP/1.1-моке для офиса 43 ответ другой — 404; схема ниже не является записью его трафика.

```text
Клиент → сервер: HEADERS [1] END_HEADERS END_STREAM   GET /offices/42/forecast
Клиент → сервер: HEADERS [3] END_HEADERS END_STREAM   GET /offices/43/forecast

Сервер → клиент: HEADERS [1] END_HEADERS              :status = 200
Сервер → клиент: HEADERS [3] END_HEADERS              :status = 200
Сервер → клиент: DATA    [1]                         первая часть ответа 42
Сервер → клиент: DATA    [3] END_STREAM               весь ответ 43
Сервер → клиент: DATA    [1] END_STREAM               остаток ответа 42
```

Источник идеи разбора streams — [Carson](https://cabulous.medium.com/http-2-and-how-it-works-9f645458e4b2); правила последовательности — [RFC 9113 §§5, 8.1](https://www.rfc-editor.org/rfc/rfc9113.html#section-8.1). Авторская схема.

Клиент связывает ответы с запросами по Stream ID. Клиентские потоки здесь имеют нечётные ID 1 и 3. Короткий ответ завершается раньше длинного; порядок доставки внутри потока сохраняется. `END_HEADERS` означает окончание блока полей, `END_STREAM` — окончание отправки в данном направлении. Запрос без тела уже закончен, но сервер ещё может отправить ответ в том же потоке.

В каждом показанном HEADERS блок полей целиком завершён. Если он разделён между HEADERS и CONTINUATION, незаконченный блок нельзя перемежать кадрами другого потока. Начальный HEADERS сообщения идёт прежде его DATA. Мультиплексирование не означает произвольную перестановку любых кадров.

### Ход показа и границы

Для streams 1/3 использовать два цвета и обязательные текстовые номера. Последовательно раскрывать кадры. Вопрос: «Как клиент свяжет DATA с запросом?» Ответ: Stream ID. END_STREAM запроса не закрывает возможность ответа. Это отдельная иллюстрация: в реальном моке офис 43 не имеет прогноза, HTTP/2 не реализован. Оговорку HEADERS/CONTINUATION произнести одной фразой, не расширять блок.

## Слайд 13. HTTP — gRPC: вызов метода другого сервиса

Время: 09:15:00–09:17:00
Длительность: 120 с.

### На слайде

- Backend → ForecastService.GetForecast

- Взаимодействие сервисов, в том числе на разных языках.

- Контракт .proto; обычно Protobuf

- Генерация клиентских обёрток и серверных заготовок.

- Unary и streaming

- Один запрос/ответ или поток сообщений. RPC ≠ DATA-кадр.

### Пояснение преподавателя

gRPC предоставляет вызовы методов удалённых сервисов. Например, backend приложения обращается к `ForecastService.GetForecast(office_id=42, days=1)` и получает готовый прогноз. Описание в `.proto` задаёт методы и сообщения; генератор создаёт клиентские обёртки и серверные заготовки. Обычно сообщения сериализуются в Protocol Buffers. Общий контракт и генерация особенно полезны для взаимодействия сервисов на разных языках.[^grpc]

Unary RPC передаёт один запрос и один ответ. Есть также server streaming, client streaming и двунаправленный streaming: соответственно несколько ответов, несколько запросных сообщений или обмен в обоих направлениях. В рассматриваемом отображении gRPC один вызов использует HTTP/2 stream; внутри могут передаваться несколько прикладных сообщений. Граница сообщения gRPC не обязана совпадать с границей DATA-кадра.

HTTP/2 организует передачу, gRPC задаёт вызовы сервисов, Protobuf описывает и сериализует сообщения. `.proto` и документ OpenAPI относятся к разным способам описания интерфейса. Наш Swagger UI показывает HTTP API и не служит клиентом нативного gRPC. Обёртка вызова сохраняет сетевые задержки и возможность отказа; семантика «как вызвать обычную функцию» их не устраняет. Реализацию и выбор интеграционного стиля продолжим в лекции 3.

### Ход показа и границы

Не писать gRPC-сервер. Соединить с предыдущим слайдом: один RPC использует HTTP/2 stream, в котором могут идти несколько сообщений. Вызов похож на функцию, но сеть сохраняет задержки и отказы. Завершить переходом: сейчас подробно разбираем семантику HTTP API; выбор стиля продолжится в лекции 3.

## Слайд 14. HTTP — Метод выражает намерение

Время: 09:17:00–09:19:00
Длительность: 120 с.

### На слайде

- Готовый прогноз

- POST → Обработать переданное содержимое

- Новое наблюдение или создание задания

- PUT → Создать или полностью заменить

- Полное состояние по известному URI

- PATCH → Применить документ изменений

- Установить один порог

### Пояснение преподавателя

Метод выражает намерение клиента относительно целевого ресурса. Выбирать его следует по смыслу операции, а не механическим сопоставлением с SQL.[^http][^patch]

| Метод | Смысл | Пример в предметной области |
|---|---|---|
| GET | Получить представление | Прочитать готовый прогноз |
| POST | Обработать переданное содержимое по правилам ресурса | Передать наблюдение; в другом контракте — создать задание расчёта |
| PUT | Создать или заменить состояние целевого ресурса переданным представлением | Полностью заменить настройки по известному URI |
| PATCH | Применить документ частичных изменений | Установить один порог нагрузки |
| DELETE | Удалить связь ресурса с его текущей функциональностью | Убрать наблюдение из доступных через API |
| HEAD | Семантика GET без содержимого ответа | Получить метаданные выгрузки |
| OPTIONS | Получить сведения о вариантах взаимодействия | Узнать поддерживаемые операции; один частный сценарий — CORS preflight |

POST может не создавать новый ресурс. PUT не означает произвольное частичное обновление. DELETE не обещает физического удаления всех резервных копий. HEAD не передаёт содержимое ответа; некоторые заголовки, вычисляемые только при формировании содержимого, могут отсутствовать. OPTIONS не заменяет проверку доступа. CONNECT и TRACE также существуют, но не входят в набор проектируемых операций нашего примера.

### Ход показа и границы

Раздать четыре минуты: GET/POST 1; PUT/PATCH 1,5; DELETE/HEAD/OPTIONS 1,5. Для PUT назвать полное представление настроек; для PATCH — документ изменения. У DELETE отделить смысл HTTP от физического стирания диска. CONNECT/TRACE только назвать при вопросе.

## Слайд 16. HTTP — Почему не делать всё через GET?

Время: 09:21:00–09:22:00
Длительность: 60 с.

### На слайде

- Представьте

- GET удаляет подписку; параметры передаются в body.

- Вопрос

- Кто может пройти по ссылке, повторить запрос / или вернуть ответ из кэша?

### Пояснение преподавателя

Технически обработчик может удалить запись при любом имени метода. Но смысл HTTP читают не только две наши программы: его используют браузер, кэш, поисковый робот, прокси и библиотека повторов. GET обещает безопасное получение: клиент не запрашивает изменение бизнес-состояния. Поэтому переход робота или предварительная загрузка ссылки не должны удалять подписку. Скрытое удаление через `GET /subscriptions/sub-7?delete=true` нарушает это обещание; параметр не меняет семантику GET. Логирование чтения при этом допустимо.

Идемпотентность позволяет рассуждать о повторе после потери ответа. У GET/PUT/DELETE она предусмотрена семантикой, у произвольного POST общей гарантии нет. Кэш может ответить на GET без обращения к серверу — ещё одна причина не прятать в чтение обязательное бизнес-действие.

Тело GET не запрещено синтаксисом HTTP/1.1, но не имеет общепринятой семантики. Посредники и клиенты могут его отклонить; обычное кэширование не обязано учитывать тело как критерий выбора ответа. Частный договор с сервером не обеспечивает переносимость через всю цепочку. Для простого чтения используем path/query, для сложного запроса с телом можно определить отдельную POST-операцию поиска. Итак, «так договорились» — начало ответа; цель договора — совместимость независимо разработанных участников. [RFC 9110 §§9.2.1–9.3.1](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.1).

### Ход показа и границы

30 секунд — индивидуально подумать; 30 — собрать версии; 60 — разобрать кэш, автоматическое чтение и повтор. Ответ не раскрывать в студенческой части слайда до обсуждения. Развёрнутый ответ и дополнительные случаи — в методичке.

## Слайд 18. HTTP — Нужен ли полный CRUD на каждом URI?

Время: 09:23:00–09:25:00
Длительность: 120 с.

### На слайде

- Сценарий → Реализуем нужные потребителю операции

- 405 + Allow → Метод известен, но не разрешён ресурсу

- 501 → Метод не распознан или не реализуется сервером

### Пояснение преподавателя

Набор операций следует из целей потребителей и их прав. Для готового прогноза может быть достаточно чтения; для приёма наблюдений нужна операция передачи. Полный CRUD на каждом адресе не требуется.

RFC 9110 требует поддержки GET и HEAD от HTTP-сервера общего назначения. Это не требование написать семь собственных обработчиков для каждого бизнес-ресурса. Часть поведения обеспечивает сервер или framework, но его нужно проверять: например, добавление GET в конкретном framework само по себе не гарантирует автоматически работающий HEAD.

Если метод распознаётся сервером, но не разрешён целевому ресурсу, ответ — `405 Method Not Allowed` с заголовком `Allow`, перечисляющим поддерживаемые методы. `501 Not Implemented` относится к нераспознанному или не реализуемому сервером методу. Эти ответы описывают разные причины отказа.

### Ход показа и границы

Предложить ресурс «готовый прогноз»: самостоятельные PUT/DELETE могут вообще не иметь бизнес-смысла. GET/HEAD общего HTTP-сервера не превращать в семь обязательных обработчиков каждого endpoint. Не утверждать автоматическую поддержку HEAD конкретным framework без проверки.

- Прогноз / полное состояние threshold=100, notifications_enabled=true.

- POST

- Добавление нового наблюдения.

- PATCH

- «Установить 100» или «прибавить 10».

### Пояснение преподавателя

**Безопасный метод** не запрашивает изменение состояния как цель обращения. Сервер при этом может вести журнал или метрики. Это свойство семантики, а не обещание защиты от атак. GET, HEAD и OPTIONS безопасны; PUT, PATCH, POST и DELETE — нет.

**Идемпотентность** означает одинаковый предполагаемый эффект одного и нескольких одинаковых запросов. GET, HEAD, OPTIONS, PUT и DELETE идемпотентны по определению методов. POST и PATCH такого общего обещания не дают. Ответы при повторе могут отличаться: повторный DELETE может вернуть 404 после первого успешного удаления, сохраняя предполагаемый эффект — ресурса больше нет.[^http]

После таймаута клиент не знает, успел ли сервер выполнить действие. Повтор PUT с полным представлением настроек `{"threshold":100,"notifications_enabled":true}` снова устанавливает то же состояние, если именно эти поля составляют полное представление ресурса. Повтор POST «добавить наблюдение» может создать дубль. PATCH «установить threshold=100» можно спроектировать идемпотентным, а PATCH «увеличить threshold на 10» изменяет результат при каждом повторе.

Контракт может добавить защиту POST от повторов, но её условия и реализация должны быть определены отдельно. Одинаковый ответ учебного мока, который ничего не хранит, не является доказательством такой защиты. Идемпотентность также не решает автоматически проблему конкурирующих клиентов и потерянных обновлений.

### Ход показа и границы

Сервер уже обработал запрос, но ответ потерялся. Для каждой строки спросить, что произойдёт при повторе. Сравнить PATCH «установить» и «прибавить». Не сводить идемпотентность к одинаковому телу ответа.

## Слайд 25. HTTP — 5xx: почему запрос не выполнен

Время: 09:36:30–09:38:00
Длительность: 90 с.

### На слайде

![5xx: почему запрос не выполнен](../assets/lecture-002/cats-5xx.png)

- 500

- Сбой внутри нашего сервиса

- 502

- Некорректный ответ upstream

- 503

- Сервис временно недоступен

- 504

- Upstream не ответил вовремя

- upstream — сервер, куда мы отправляем запрос

### Пояснение преподавателя

**upstream — сервер, куда мы отправляем запрос**. В обсуждении 502/504 это сервер, к которому обращается наш шлюз или прокси.

500 — непредвиденное условие на сервере. 502 и 504 возвращает узел в роли шлюза/прокси: получил некорректный ответ от upstream или не дождался своевременного ответа. 503 применим при временной перегрузке или обслуживании; сервер может добавить Retry-After с датой или числом секунд. Заголовок не гарантирует восстановление точно в срок.

5xx не является командой бездумно повторить любую операцию. Сначала учитываем метод, возможный уже выполненный эффект, прикладную защиту от дублей и задержку между попытками. Различия 502/503/504 нужны, чтобы понять, где и почему оборвался путь запроса.

Источник семантики: [RFC 9110 §15](https://www.rfc-editor.org/rfc/rfc9110.html#section-15).

### Ход показа и границы

Показать котиков с технически верными подписями. Для 503 проговорить перегрузку/обслуживание; для 504 — ожидание зависимости. Не называть любой клиентский таймаут ответом 504.

## Слайд 27. REST — Ресурс и его представление

Время: 09:38:15–09:39:30
Длительность: 75 с.

### На слайде

- Ресурс

- Адресуемое понятие: прогноз офиса.

- Представление

- Переданные данные о ресурсе, например JSON.

- Внутреннее устройство

- Таблица, файл или вычисление не диктуют внешний интерфейс.

### Пояснение преподавателя

Мы прочитали сообщение, выбрали метод и поняли статус. Теперь поднимемся на уровень устройства интерфейса: какие понятия сделать ресурсами и как согласовать взаимодействие. REST (Representational State Transfer) — архитектурный стиль. **Ресурс** — адресуемое понятие интерфейса, например прогноз офиса. **Представление** — переданное описание его состояния, например JSON. Внутри ресурс может собираться из нескольких таблиц, файла или результата расчёта; структура хранения не определяет автоматически внешний интерфейс.[^rest]

Ограничения REST связаны с распределением ответственности:

| Ограничение | Зачем оно нужно |
|---|---|
| Клиент–сервер | Отделяет работу потребителя от предоставления ресурса |
| Stateless | Каждый запрос несёт необходимый контекст; серверу не нужен скрытый контекст предыдущего диалога |
| Кэширование | Ответ сообщает, можно ли повторно использовать его при заданных условиях |
| Единообразный интерфейс | Общие правила идентификации ресурсов, работы через представления и понимания сообщений |
| Слои | Клиент взаимодействует со своим непосредственным узлом; между ним и поставщиком могут быть посредники |
| Code-on-demand, необязательное | Сервер может расширить возможности клиента передаваемым исполняемым кодом |

Stateless позволяет хранить бизнес-данные и ресурсы. Ограничение относится к контексту взаимодействия, а не к запрету базы данных. В единообразный интерфейс входят идентификация ресурсов, изменение через представления, самодостаточные сообщения и гипермедиа — переходы по доступным действиям/связям.

Проектируемое расширение представления может содержать `links.office.href = "/offices/42"`. Клиент узнаёт связанную возможность из ответа, а не только угадывает адрес. Для полноценного контракта нужно также определить смысл связи и способ её использования. Одна ссылка не доказывает соответствие всей системы REST; набор URI, JSON и CRUD тоже не является таким доказательством. В текущем моке поля `links` нет.

### Ход показа и границы

Первые 2 минуты: ресурс/представление и контекст хранения. Следующие 2: ограничения, четыре составляющих единого интерфейса и пример связи. Подчеркнуть, что stateless не запрещает БД. Не превращать обзор в доказательство REST-полноты мока.

## Слайд 30. REST — Когда можно повторно использовать прогноз

Время: 09:42:00–09:45:00
Длительность: 180 с.

### На слайде

- max-age=60 → Срок свежести по выбранной политике

- no-cache → Проверить перед повторным использованием

- no-store → Не хранить

- stale в моке → Фиксированное учебное значение

### Пояснение преподавателя

Прогноз на завтра может быть создан вчера; это не автоматически ошибка, но потребитель должен понимать время подготовки и обновления источников.[^cache]

Мок не устанавливает эти правила кэширования и не вычисляет актуальность. Его `stale: false` — фиксированное учебное значение. Для реального API нужны политика свежести, определение этой метки и проверка поведения. Условные запросы, ETag и защита от потерянных обновлений требуют отдельного углублённого разбора.

### Пояснение преподавателя

JSON описывает объект, массив, строку, число, логическое значение и `null`. После чтения байтов JSON-парсер восстанавливает структуру языка, а схема проверяет ограничения. Дата не является отдельным типом JSON: строка с датой получает смысл по договору.[^json]

Для сравнения форматов возьмём авторский набор наблюдений, расширенный относительно минимального POST:

```json
{
  "office_id": 42,
  "observations": [
    {"hour":"2026-09-14T09:00:00Z","visitors":45,"note":"Офис, центр"},
    {"hour":"2026-09-14T10:00:00Z","visitors":0,"note":null}
  ]
}
```

Мобильному приложению удобно получить готовый прогноз как вложенный объект. Источнику статистики удобно отправить объект наблюдения. `application/json` сообщает тип содержимого. Имена полей, обязательность, единицы и смысл `null` уточняются отдельно.

В Python применяют `json.loads(text)`; результат обычно состоит из `dict`, `list` и простых значений. JSON не совпадает с синтаксисом словаря Python: нужны двойные кавычки, `true/false/null` вместо `True/False/None`. Разбор синтаксиса ещё не доказывает правильность типов по контракту. Для идентификаторов с ведущими нулями, точных денежных значений и очень больших чисел нужно отдельно договориться о представлении и возможностях читателя.

- application/xml /  / Элементы, атрибуты, пространства имён /  / XSD = XML Schema Definition /  / Схема XML: элементы, атрибуты и типы

### Пояснение преподавателя

XML описывает дерево элементов и атрибутов. Он полезен, когда партнёрская система или существующий корпоративный контракт требует именно XML. Те же наблюдения можно представить документом:[^xml]

```xml
<observations xmlns="urn:course:observations:v1" officeId="42">
  <observation hour="2026-09-14T09:00:00Z">
    <visitors>45</visitors><note>Офис, центр</note>
  </observation>
  <observation hour="2026-09-14T10:00:00Z">
    <visitors>0</visitors>
  </observation>
</observations>
```

Здесь `officeId` и `hour` — атрибуты, `visitors` — элемент. Namespace `urn:course:observations:v1` различает словари имён; он не обязан быть адресом скачивания файла. В этом конкретном соглашении отсутствие `note` означает неизвестную заметку — аналог `null` предыдущего набора. XML сам по себе не назначает такой смысл отсутствующему элементу.

**XSD (XML Schema Definition; в названии стандарта W3C — XML Schema Definition Language)** — язык описания схемы XML: допустимых элементов/атрибутов, их типов, порядка и количества. Например, `visitors` можно объявить как `xs:nonNegativeInteger`: значение `-5` будет нарушать схему, хотя XML синтаксически корректен. XSD — отдельный документ с правилами; XML содержит проверяемые данные. [W3C XSD 1.1](https://www.w3.org/TR/xmlschema11-1/).

XML-парсер читает дерево; затем XSD, если она задана, может проверять структуру и типы. Например, стандартный `xml.etree.ElementTree` в Python позволяет читать элементы, но сам не является XSD-валидатором. Учитывайте namespace при поиске элементов. Media type — `application/xml`. SOAP использует XML, однако XML-документ не обязан быть SOAP-сообщением.

### Ход показа и границы

На тех же значениях найти элемент, атрибут, namespace. Отсутствующий note означает неизвестность только по нашему соглашению. ElementTree — парсер, а не XSD-валидатор. XML не объявлять синонимом SOAP.


- text/csv /  / Кавычки защищают запятую внутри поля. /  / Диалект, кодировка, колонки и пропуски — договор.

### Пояснение преподавателя

CSV удобен для небольшого импорта, выгрузки аналитику или передачи плоских строк в ETL. В распространённом варианте первая строка содержит имена колонок:[^csv]

```csv
office_id,hour,visitors,note
42,2026-09-14T09:00:00Z,45,"Офис, центр"
42,2026-09-14T10:00:00Z,0,
```

CSV-reader должен распознать запятую внутри кавычек как часть одного значения. Если значение содержит кавычку, в варианте RFC 4180 её удваивают: `"Офис ""Центр"""`. Простое `line.split(',')` такой файл разбирает неправильно.

CSV обычно не хранит полноценную схему типов: после чтения поля часто являются строками. Нужно согласовать разделитель, кавычки, кодировку, заголовок, типы, даты и пропуски. В нашем соглашении пустая последняя ячейка означает неизвестную заметку; сам CSV не определяет её как `null`. Значение `0` остаётся известным числом посетителей, а не отсутствием данных.

Media type — `text/csv`. RFC 4180 имеет категорию Informational и описывает распространённый вариант; реальные системы используют разные диалекты. Вложенный массив нельзя без дополнительного соглашения поместить в одну обычную ячейку. В Python для этого формата есть `csv.DictReader`, после которого выполняют явное преобразование и проверку типов.

### Ход показа и границы

Вопрос: «Почему split по запятой испортит первую строку данных?» Ответ: запятая внутри quoted-поля. Пустую ячейку note сопоставить с неизвестностью в JSON/XML; visitors=0 остаётся известным значением. RFC 4180 не выдать за единственный диалект.

## Слайд 35. Форматы данных — Parquet: группы строк и блоки колонок

Время: 09:54:00–09:57:00
Длительность: 180 с.

### На слайде

- Row group 1

- office_id hour visitors note

- Row group 2 → аналогичные блоки колонок

- Читаем нужные колонки; используем метаданные и статистику.

- Источник: Apache Parquet — File Format

### Пояснение преподавателя

Parquet — бинарный формат с метаданными и типизированной схемой, ориентированный на аналитическое чтение колонок. Например, аналитик хочет изучить `hour` и `visitors` за год, не читая все поля расширенной истории наблюдений.[^parquet]

```text
Логическая таблица: office_id | hour | visitors | note | ...

Файл Parquet
  группа строк 1
    блок колонки office_id
    блок колонки hour       ← нужны аналитику
    блок колонки visitors   ← нужны аналитику
    блок колонки note
  группа строк 2
    аналогичные блоки колонок
  метаданные и схема
```

Это **схема устройства**, не текстовое содержимое Parquet. Внутри блоков колонок есть страницы данных и служебная структура. Файл читает библиотека или аналитический движок, например PyArrow. Проекция колонок позволяет не материализовывать ненужные столбцы; степень экономии зависит от устройства файла, движка и запроса. Статистика может помогать отбору частей данных, но универсального ускорения для любой таблицы нет.

Типы и логические аннотации нужно понимать согласованно: временная отметка, числовой идентификатор и строка с ведущими нулями имеют разные свойства. Парсер JSON или CSV-reader не прочтут Parquet как свой формат. При маленьком разовом обмене простота CSV может быть важнее преимуществ колонкового хранения.

Все четыре формата могут переноситься по HTTP. API может вернуть JSON со статусом выгрузки и ссылкой на Parquet, который аналитический клиент загрузит отдельно. Поддерживать все форматы на каждом endpoint не требуется. Выбор начинается с потребителя: приложение, партнёр с XML-контрактом, табличный импорт или аналитика истории. Затем учитываются инструменты, схема, вложенность и условия чтения.

Первые 4 минуты: реальный тип бинарного файла, схема, группы строк и блоки колонок; показать выбор hour/visitors без чтения всех колонок на схеме. ## Слайд 38. Схемы и валидация — Отсутствие, null и ноль

Время: 10:00:15–10:02:00
Длительность: 105 с.

### На слайде

```json
{
  "type": "object",
  "properties": {
    "office_id": {"type": "integer"},
    "visitors": {
      "type": ["integer", "null"],
      "minimum": 0
    }
  },
  "required": ["office_id", "visitors"]
}
```

- required — поле обязательно. /  / null — значение неизвестно. /  / 0 — известно: посетителей нет. /  / Поле отсутствует — значение не передано.

### Пояснение преподавателя

JSON Schema позволяет описать допустимые значения. Например, этот фрагмент задаёт учебное наблюдение с обязательными `office_id` и `visitors`; поле `visitors` допускает `null`:

```json
{
  "type":"object",
  "properties":{
    "office_id":{"type":"integer"},
    "visitors":{"type":["integer","null"],"minimum":0}
  },
  "required":["office_id","visitors"]
}
```

`properties` описывает свойства, `required` отдельно требует их присутствия. По этой схеме `{"office_id":42,"visitors":null}` допустим, а `{"office_id":42}` — нет. В этом договоре null — неизвестное число посетителей, 0 — известное отсутствие посетителей. Отсутствующее обязательное поле нарушает required; JSON сам не определяет предметный смысл null. Это проектируемый пример null-семантики; **минимальный POST мока допускает только целое visitors ≥ 0**, поэтому null туда отправлять нельзя.[^schema]

Ограничение типа ещё не отвечает, за какой период посчитаны посетители. Потребителю нужны единицы, границы интервала, временная зона и правила округления. Это часть контракта даже тогда, когда для правила нет удобного ключевого слова схемы.

Видимый пример — отдельная проектируемая схема, не схема реального POST мока. В ходе объяснения различить эти контракты; строку о моке на слайд не возвращать.

### Ход показа и границы

Различить отсутствие поля, null и число 0. Здесь договор трактует null как неизвестное число посетителей. required требует наличия поля, а type разрешает целое число или null. Ноль означает известное отсутствие посетителей. Не приписывать null универсальный предметный смысл.

## Слайд 44. OpenAPI — Спецификация, документ, интерфейс и сервер

Время: 10:06:15–10:06:42
Длительность: 27 с.

### На слайде

- OAS 3.2.1 → Правила описания интерфейса

### Пояснение преподавателя

**OpenAPI Specification (OAS)** задаёт правила машиночитаемого описания HTTP API. В этой лекции закреплена **OAS 3.2.1**, опубликованная 10 сентября 2026 года. Ссылка с конкретной версией позволяет читать именно те правила, по которым написан документ.[^oas]

```text
Правила OAS 3.2.1
      ↓ описываем интерфейс
Авторский YAML или JSON
      ↓ инструмент читает документ
Swagger UI: операции, схемы, примеры
      ↓ Execute формирует настоящий HTTP-запрос
API-сервер: выполняет запрос и возвращает фактический ответ
```

YAML — форма записи документа; JSON в теле запроса — форма передаваемых данных. Эти роли независимы. В YAML `ключ: значение` задаёт пару, отступы — вложенность, `-` — элемент списка. Для контракта используем пробелы и сохраняем структуру отступов. Документ OpenAPI допустимо записать также в JSON.

Верхний `openapi: 3.2.1` обозначает версию OAS. `info.version: 1.0.0` в нашем файле — версия самого описания. Она отличается от версии работающего учебного приложения 2.0.0. Schema Object опирается на JSON Schema Draft 2020-12 с диалектом OAS; старое правило `nullable: true` из примеров OAS 3.0 не следует механически переносить в новый документ.

Длительность: 120 с.

### На слайде

```yaml

```

- servers — базовый адрес /  / paths + get — операция /  / Сокращённый фрагмент, не полный YAML

### Пояснение преподавателя

Полный файл — [lecture02-openapi.yaml](../attachments/seminar-002/contracts/lecture02-openapi.yaml). Ниже учебная выписка для чтения, а не самостоятельный полный контракт: в ней опущены остальные ответы и определения из `components`.

```yaml
openapi: 3.2.1
info:
  title: Готовый прогноз и наблюдения — лекция 2
  version: 1.0.0
servers:
  - url: http://127.0.0.1:8000
paths:
  /offices/{office_id}/forecast:
    get:
      summary: Получение готового прогноза
      parameters:
        - name: office_id
          in: path
          required: true
          schema:
            type: integer
          example: 42
        - name: days
          in: query
          schema:
            type: integer
            enum: [1, 7]
            default: 1
      responses:
        '200':
          description: Готовый фиксированный прогноз.
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/Forecast'
```

`servers` задаёт базовый адрес. Ключ внутри `paths` — шаблон пути, а `get` — метод. В `parameters` различены path и query: параметр шаблона пути обязателен, а days можно опустить, получив серверное значение 1. `enum` здесь означает **1 или 7**, не диапазон от 1 до 7.

`responses` описывает обещанные варианты результата. В полном файле есть 200, 404 и 422. `content` связывает media type со схемой; `$ref` указывает на повторно используемое определение. Пример показывает одно допустимое значение, схема — множество допустимых значений. Успешная валидация файла с `paths: {}` ещё не означает, что команда описала все необходимые операции.

### Ход показа и границы

Открыть полный авторский YAML и по очереди показать перечисленные участки. Выписка из пояснения годится для навигации, не как самостоятельный валидный файл: определения и ошибки опущены. Сопоставить каждое поле с GET из слайда 4. Обязательно проговорить enum 1/7, а не диапазон.

- Тело описывается отдельно от path/query. /  / $ref переиспользует схему Observation. /  / POST читаем в UI; выполняем через curl.

### Пояснение преподавателя

В POST входное JSON-содержимое описывается через `requestBody`, отдельно от path/query-параметров. Выписка из полного документа:

```yaml
requestBody:
  required: true
  content:
    application/json:
      schema:
        $ref: '#/components/schemas/Observation'
      example:
        office_id: 42
        visitors: 45
```

Определение `Observation` в `components/schemas` содержит обязательные `office_id` и `visitors`, целочисленные типы, допустимые офисы 42/43 и `minimum: 0` для visitors. Ссылку используют вместо повторения одной схемы в нескольких местах. Символ `#` означает текущий документ; части после `/` — путь к определению.

В Swagger UI можно прочитать `Request body`, переключить Example Value/Schema и посмотреть 201. У POST задан собственный server на порту 8001. BankOffices не разрешает CORS для страницы Read API, поэтому в этом комплекте POST выполняют через curl, а в UI читают его контракт. Это ограничение браузерного показа, не запрет HTTP на запрос к другому сервису.

Три проверки отвечают на разные вопросы:

| Проверка | Что устанавливает | Чего не доказывает |
|---|---|---|
| Документ OpenAPI и ссылки | Описание соответствует правилам формата, ссылки разрешаются | Что описаны все нужные операции |
| Примеры по схемам | Выбранные значения удовлетворяют ограничениям | Что сервер возвращает именно их |
| Реальные обмены и поведение | Проверенные запросы согласуются с обещаниями | Корректность всех возможных входов, конкуренции и отказов |

В комплекте закреплены Swagger UI 5.32.15 и openapi-spec-validator 0.9.0. Учебный `validate_contract.py` дополнительно проверяет встроенные JSON-примеры по схемам и требует локальных ссылок в одном файле. Его область — использованные в этой лекции конструкции; он не объявляется универсальной проверкой всех новых streaming-возможностей OAS 3.2. Команды и зависимости приведены в README. Для ДЗ проектируется контракт своей команды; писать сервер только ради валидации документа не требуется.

## Слайд 54. OpenAPI — Совместимость для конкретного клиента

Время: 10:24:00–10:28:00
Длительность: 240 с.

### На слайде

- Запрос → Новое обязательное поле ломает отправителя

- Ответ → Удалённое обещанное поле ломает читателя

- Добавление → Поле или enum требуют проверки старого клиента

- Смысл → Те же типы, другие единицы — тоже нарушение

### Пояснение преподавателя

Новое обязательное поле **запроса** ломает старого отправителя, который о нём не знает. Удаление обещанного поля **ответа** ломает читателя, который на него рассчитывает. Добавление нового поля ответа допустимо, только если старый читатель переносит неизвестные поля. Строгая схема с запретом дополнительных свойств может его отклонить.[^compat]

Новое значение enum тоже требует осторожности: клиент мог исчерпывающе обрабатывать прежние варианты. Имена и типы могут оставаться неизменными при смене единиц или бизнес-смысла. Например, переход от посетителей за час к посетителям за сутки нарушит интерпретацию даже у читателя, допускающего дополнительные поля.

Практический порядок: назвать старого потребителя; выписать его запросы и ожидания от ответа; предложить изменение; проверить конкретные случаи и согласовать миграцию. Правила одной компании полезны как опыт, но не заменяют контракт вашего API. AIP-180 — пример такой практики, а не общий стандарт HTTP.

### Ход показа и границы

За первую минуту прочитать старый запрос/ответ; за вторую предложить обязательное поле запроса; за третью удалить поле ответа; за четвёртую сменить единицы. На первые два вопроса получить короткие ответы: ломает старого отправителя / ожидающего поле читателя. На третьем зафиксировать условность, особенно строгих клиентов. На четвёртом вернуться к часам/суткам. Не обещать автоматическую безопасность добавления поля.

Начните с «Основных абстракций», кадров, HEADERS/CONTINUATION и DATA; затем можно перейти к SETTINGS и WINDOW_UPDATE. После чтения объясните сообщение/поток/кадр, расположение метода/пути/статуса и различие END_HEADERS/END_STREAM. Уточнение по [RFC 9113 §8.2.2](https://www.rfc-editor.org/rfc/rfc9113.html#section-8.2.2): `Transfer-Encoding` в HTTP/2 запрещён, а не просто необязателен. Ориентир — 30–40 минут с вопросами; это дополнительное чтение, не новое оцениваемое ДЗ.

Дополнительная визуальная подача — [Carson, HTTP/2 and How it Works](https://cabulous.medium.com/http-2-and-how-it-works-9f645458e4b2), разделы Binary-Encoded Frames и Streams. Пользуйтесь уточнёнными схемами этого конспекта: Length измеряет байты payload, поля номера кадра нет, начальный HEADERS предшествует DATA своего сообщения.

### Ход показа и границы

Habr — основное дополнительное чтение: абстракции и кадры, затем HEADERS/CONTINUATION/DATA. Сказать «в конспекте есть вопросы и уточнения по RFC». Это не новое оцениваемое ДЗ. Не читать вслух длинную библиографию; завершить на 90:00.

# Лекция 2: HTTP и контракты данных

Методичка преподавателя • ПРБ • 14 сентября 2026 • Редакция 1

## Как читать за час

Материал дополняет лекционный сценарий: объясняет внутреннее устройство и даёт аргументы для вопросов аудитории. Это самостоятельный справочник; порядок страниц примерно повторяет занятие. Примеры, помеченные «проектирование», не приписывают новых возможностей учебному серверу.

**Входные знания:** клиент и сервер, API как интерфейс, объекты/списки/строки/числа, базовая идея сети. Знание бинарных протоколов, YAML, XSD или реализации REST не требуется. Перед занятием преподаватель самостоятельно репетирует демонстрацию.

| Маршрут | Страницы | Время с проверкой примеров |
|---|---|---|
| Сообщения, версии и внутреннее устройство | 2–9 | 20 минут |
| Методы, повторы, статусы, REST и кэш | 10–14 | 14 минут |
| Форматы, схема, смысл данных | 15–19 | 12 минут |
| OpenAPI, проверки, совместимость | 20–22 | 9 минут |
| Ответы и повторение | 23 | 5 минут |
| Источники и маршрут углубления | 24–25 | По необходимости |

**Опорная цепочка:** намерение потребителя → HTTP-операция → представление данных → проверяемый контракт → совместимость. HTTP определяет обмен; REST ограничивает устройство системы; формат определяет кодирование данных; OpenAPI описывает конкретный интерфейс. Это разные уровни одного решения.

Кейс: приложение руководителя офиса получает **готовый прогноз** клиентского потока. Получение не тождественно запуску расчёта модели. Источник статистики отправляет наблюдения. Требуемая скорость ответа, свежесть статистики и точность прогноза - три отдельные характеристики.

Рекап первой лекции занимает 2–3 минуты: распределение обязанностей в 1/2/3-tier, обзор CORBA/SOAP/REST/gRPC и место API в ML-системе. Для перехода достаточно спросить: «Как другая команда поймёт, что отправлять и какой результат ожидать?»

# 1. HTTP/1.1: от байтов к сообщению

HTTP удобно читать как сообщение с управляющей частью, метаданными и необязательным содержимым. Ниже условная запись; реальные окончания строк стартовой строки и заголовков - CRLF. Тело не обязано быть текстовым.

```http
GET /offices/42/forecast?days=1 HTTP/1.1
Host: api.example.edu
Accept: application/json

```

| Фрагмент | Название | Роль |
|---|---|---|
| GET | method | Что клиент просит сделать |
| /offices/42/forecast?days=1 | request-target | Цель обращения в origin-form |
| /offices/42/forecast | path | Адрес ресурса внутри сервера |
| days=1 | query | Параметры обращения по контракту |
| HTTP/1.1 | HTTP-version | Версия формата сообщения |
| Host, Accept | header fields | Адресат и метаданные |
| Пустая строка | header/body separator | Конец раздела заголовков |

```http
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 31

{"office_id":42,"visitors":120}
```

Content-Length: 31 означает число байтов ровно показанного тела без завершающего перевода строки. Длина считается в байтах, не символах. Reason phrase `OK` не заменяет числовой status code. Тело интерпретируется по Content-Type; прочитать JSON и проверить обещанную схему - разные операции.

Клиент собирает байты сообщения, сервер разбирает их, выбирает обработчик, формирует ответ. TCP может разбить запись на несколько сегментов или объединить записи; границы `send()` не являются границами HTTP-сообщений. Поэтому протоколу нужны правила определения конца тела.

**Как объяснить:** сначала обозначить method/path/query/headers/body на общей схеме. Затем найти эти поля в реальном GET. Это помогает студенту читать любой предметный пример, а не запоминать один адрес.

Источник: [RFC 9112, §§2–6](https://www.rfc-editor.org/rfc/rfc9112.html#section-2).

# 2. Заголовки, тело и посредники

**Content-Type отвечает «что отправлено», Accept - «какой ответ приемлем».** Клиент может отправить JSON и попросить CSV: в запросе Content-Type: application/json и Accept: text/csv. Сервер возвращает фактический Content-Type своего ответа. Наличие Accept не заставляет сервер реализовывать любую сериализацию.

Если отправитель заранее знает длину содержимого HTTP/1.1, он может передать Content-Length. Для неизвестной заранее длины существует chunked transfer coding: размеры порций в шестнадцатеричной записи и завершающая нулевая порция. Это разметка передачи, а не формат бизнес-данных. Получатель снимает её до разбора JSON. В HTTP/2 Transfer-Encoding запрещён: границы задаются кадрами и завершением потока.

```text
Business object
  -> JSON serialization
  -> HTTP content and framing
  -> TLS records (for HTTPS)
  -> TCP segments / network packets
```

Сжатие тела, например Content-Encoding: gzip, отличается от разметки передачи. HPACK в HTTP/2 относится к полям заголовков и тоже не заменяет сжатие JSON. Разделяйте три вопроса: «Какие данные?», «Как они закодированы?», «Как выделить их границы в соединении?»

**Посредник понимает стандартную семантику.** Кэш, reverse proxy, CDN, браузер и клиентская библиотека не знают внутренний код обработчика. Они принимают решения по method, URI, заголовкам, статусу. Это объяснит, почему удаляющий GET опасен даже тогда, когда две конкретные программы «договорились».

Сеть часто имеет несколько участков: browser → CDN → gateway → API. HTTP/3 на первом не означает HTTP/3 на остальных. TLS защищает канал между участниками данного соединения, а не автоматически весь путь данных после расшифрования у посредника.

**Практическая ошибка:** вручную задать длину, затем изменить Unicode-тело. Клиентские библиотеки должны вычислять её по передаваемым байтам. Ошибки границ опаснее опечатки в названии поля: два участника могут разобрать один поток по-разному.

Источники: [RFC 9112 §7.1](https://www.rfc-editor.org/rfc/rfc9112.html#section-7.1), [RFC 9110 §§8,12](https://www.rfc-editor.org/rfc/rfc9110.html#section-8), [RFC 9113 §8.2.2](https://www.rfc-editor.org/rfc/rfc9113.html#section-8.2.2).

# 3. Зачем HTTP менял передачу

| Версия | Первый RFC | Передача | Главное ограничение |
|---|---|---|---|
| HTTP/1.1 | Январь 1997, RFC 2068 | Текстовые начало и заголовки; TCP | Ответы pipelining идут в порядке запросов |
| HTTP/2 | Май 2015, RFC 7540 | Кадры и streams внутри TCP | Потеря TCP-данных задерживает доставку всем streams |
| HTTP/3 | Июнь 2022, RFC 9114 | Кадры поверх QUIC/UDP | Общие ресурсы и зависимости всё ещё есть |

Между первыми RFC прошло **18 лет 4 месяца**, затем **7 лет 1 месяц**. Это даты публикации стандартизующих документов, а не начала экспериментов или массового внедрения. RFC 9112 и 9113 (июнь 2022) обновляют описания 1.1 и 2; они не означают, что обе версии появились в 2022 году.

**HTTP/1.1:** переиспользование TCP-соединения избавляет от открытия нового на каждую операцию. Pipelining позволяет отправить следующие запросы, не дождавшись предыдущего ответа; однако сервер должен соблюдать порядок ответов. Длинный первый ответ мешает выдаче следующего. Несколько соединений дают параллелизм ценой дополнительных ресурсов.

**HTTP/2:** делит сообщения на кадры, маркирует их потоками и чередует. Быстрый ответ может закончиться до медленного в том же соединении. Но снизу TCP выдаёт приложению непрерывную последовательность байтов: пропущенный участок удерживает и более поздние данные других HTTP-потоков.

**HTTP/3:** переносит независимость потоков в QUIC, так что потеря в одном потоке не требует задерживать уже полученные байты другого. Это не обещание «всегда быстрее». Выигрыш зависит от потерь, RTT, размера передачи и реализации.

Выборка Cloudflare Radar от 14.09.2026, Worldwide / All traffic / 7 дней: HTTP/2 52,5%, HTTP/1.x 27,6%, HTTP/3 19,9%. Это сохранённый снимок курса, не все API Интернета; 1.x объединяет версии. HTTP/1.1 выбран для читаемой записи примеров, а не как объявленное большинство.

Источники: [RFC 2068](https://www.rfc-editor.org/rfc/rfc2068.html), [RFC 7540](https://www.rfc-editor.org/rfc/rfc7540.html), [RFC 9114](https://www.rfc-editor.org/rfc/rfc9114.html), [Cloudflare Radar](https://radar.cloudflare.com/adoption-and-usage?dateRange=7d#http1x-vs-http2-vs-http3).

# 4. HTTP/2: прочитать заголовок кадра

```text
                 FRAME HEADER: 9 BYTES
+------------------+---------+----------+
| Length: 24 bits  | Type: 8 | Flags: 8 |
+------------------+---------+----------+
| R: 1 bit | Stream Identifier: 31 bits |
+--------------------------------------+
| Payload: exactly Length bytes         |
+--------------------------------------+
```

| Поле | Как понимать | Пример |
|---|---|---|
| Length | Размер payload в байтах; 9 байт заголовка не включены | 5 означает: прочитать ещё 5 байт |
| Type | Какой формат и смысл у payload | 0x00 DATA; 0x01 HEADERS; 0x04 SETTINGS |
| Flags | Битовые признаки, значение зависит от Type | 0x01 для DATA - END_STREAM |
| R | Зарезервированный бит; отправитель ставит 0, получатель игнорирует | Это не часть Stream ID |
| Stream Identifier | Какому логическому потоку принадлежит кадр | 1 и 3 - разные обмены; 0 - уровень соединения |

```text
00 00 05 | 00 | 01 | 00 00 00 01 | 68 65 6C 6C 6F
Length=5  DATA END_STREAM  Stream=1   ASCII: hello
```

**Разбор примера:** после начальных HEADERS сервер отправляет 5 байт тела `hello` и заканчивает свою отправку по stream 1. Кадр занимает 14 байт. Это учебный DATA-пример, а не полный HTTP-ответ; начальные HEADERS здесь опущены. Его END_STREAM не закрывает TCP-соединение и соседние потоки.

В Length помещается до 2²⁴−1 байт, но по умолчанию допустимый максимум payload кадра - 16 384; больший предел объявляет получатель через SETTINGS_MAX_FRAME_SIZE. Ёмкость поля и согласованный предел - разные вещи. Также существуют ограничения длины отдельных типов кадров.

У кадра нет собственного поля «порядковый номер». Не путать Stream ID с порядковыми номерами TCP. Для type-specific payload правила различаются: DATA несёт содержимое, SETTINGS - настройки, WINDOW_UPDATE - пополнение окна.

Схема авторская. Идея подачи: [Carson, Binary-Encoded Frames](https://cabulous.medium.com/http-2-and-how-it-works-9f645458e4b2). Нормативные поля и размеры: [RFC 9113 §§4.1–4.2,6](https://www.rfc-editor.org/rfc/rfc9113.html#section-4.1).

# 5. HEADERS, HPACK и два завершения

HTTP/2 не передаёт буквальную строку `GET … HTTP/2`. Управляющие сведения представлены псевдозаголовками. Ниже **результат декодирования**, а не дамп сетевых байтов:

```text
:method    GET
:scheme    https
:authority api.example.edu
:path      /offices/42/forecast?days=1
accept     application/json
```

В ответе вместо стартовой строки используется `:status: 200`. Псевдозаголовки идут до обычных полей. HEADERS переносит блок полей в HPACK-представлении; тело передаётся DATA. Термин header field относится к HTTP-полю, frame header - к девятибайтовому заголовку кадра: это разные объекты.

**HPACK сокращает повторы.** Есть фиксированная таблица известных полей и значений, динамическая таблица для соединения, а также литеральные записи; строки могут использовать код Хаффмана. Вместо повторяющихся длинных значений отправитель часто передаёт ссылки. Это не шифрование: конфиденциальность даёт TLS. Состояние декодирования требует согласованности; произвольное удаление фрагмента блока не оставляет «независимый читаемый остаток».

| Признак | Что завершает | Чего не означает |
|---|---|---|
| END_HEADERS (0x04) | Блок полей | Тело тоже закончилось |
| END_STREAM (0x01) | Отправку в данном направлении потока | Соединение закрыто |
| HEADERS с обоими | Поля закончились, содержимого дальше нет | Сервер уже ответил |

**HEADERS/CONTINUATION:** если блок полей не вмещается, HEADERS не ставит END_HEADERS, далее идут CONTINUATION того же stream. До последнего CONTINUATION с END_HEADERS нельзя вставлять кадры другого потока или другой тип кадра. Иначе декодирование общей последовательности нарушается. DATA разных потоков чередовать можно.

Flags читаются вместе с Type: 0x01 означает END_STREAM для DATA/HEADERS, но ACK для SETTINGS/PING. Поэтому объяснение «первый бит всегда завершает поток» неверно. Неизвестные флаги обычно игнорируются по правилам типа; это пространство для расширений.

Источники: [RFC 9113 §§4.3,6,8.3](https://www.rfc-editor.org/rfc/rfc9113.html#section-4.3), [RFC 7541: HPACK](https://www.rfc-editor.org/rfc/rfc7541.html).

# 6. Streams: параллелизм и ограничение скорости

Поток - логическая двунаправленная последовательность кадров внутри соединения. Один обычный запрос и его ответ связаны Stream ID. Это не поток ОС, не соединение TCP и не последовательность кадров одного размера. Клиент инициирует потоки с нечётными идентификаторами.

```text
Client -> Server
HEADERS [1] END_HEADERS END_STREAM  GET forecast 42
HEADERS [3] END_HEADERS END_STREAM  GET forecast 43

Server -> Client
HEADERS [1] END_HEADERS             :status 200
HEADERS [3] END_HEADERS             :status 200
DATA    [1]                        part A
DATA    [3] END_STREAM              short response
DATA    [1] END_STREAM              part B
```

Схема - авторское проектирование HTTP/2. Текущий HTTP/1.1-мок не реализует эту трассу; office 43 в нём не выдаёт готовый прогноз. Идея визуальной подачи: [Carson, Streams](https://cabulous.medium.com/http-2-and-how-it-works-9f645458e4b2); правила: [RFC 9113 §§5,8.1](https://www.rfc-editor.org/rfc/rfc9113.html#section-5).

**Ключевой ответ аудитории:** получатель направляет DATA в нужное собираемое сообщение по Stream ID. Ответ 3 заканчивается раньше 1. TCP сохраняет порядок доставленных байтов, но прикладное завершение отдельных ответов не обязано повторять порядок запросов.

**Flow control защищает получателя.** Для DATA учитываются окна соединения и потока. Если доступно 10 000 байт на соединение и 4 000 на stream 1, по этому stream сейчас нельзя отправить больше 4 000. Получатель освобождает ёмкость и передаёт WINDOW_UPDATE. Размер кадра не равен размеру окна: одно окно может покрывать много кадров.

**Congestion control защищает сеть.** TCP регулирует передачу с учётом потерь и перегрузки; HTTP/2 flow control отражает готовность получателя принять DATA. Это два разных ограничения. HEADERS не расходует окно DATA; поэтому ограничения метаданных и числа потоков нужны отдельно.

Для завершения/ошибки отдельного обмена используется RST_STREAM; GOAWAY сообщает о завершении обслуживания соединения и помогает определить, какие потоки могли быть обработаны. Сетевой обрыв сам по себе не доказывает, что прикладное действие не произошло.

Источники: [RFC 9113 §§5.2,6.4,6.8–6.9](https://www.rfc-editor.org/rfc/rfc9113.html#section-5.2).

# 7. HTTP/3: что QUIC меняет внутри

HTTP/3 использует QUIC поверх UDP. QUIC сам обеспечивает установление защищённого соединения, надёжную доставку данных потоков, обнаружение потерь и управление перегрузкой. «UDP» в этой конструкции не означает, что HTTP-тело допускается безвозвратно терять.

```text
HTTP/2: HTTP streams -> one ordered TCP byte stream
          missing TCP bytes -> later bytes wait

HTTP/3: HTTP streams -> independent QUIC streams
          missing bytes in A -> A waits
          available bytes in B -> B can proceed
```

**Head-of-line blocking (HOL)** - ситуация, когда готовая работа ждёт более раннюю. HTTP/2 уменьшает блокировку порядка HTTP/1.1-ответов, но сохраняет TCP HOL. QUIC разделяет доставку по streams, уменьшая эту транспортную зависимость. Внутри одного stream порядок и ожидание пропуска сохраняются. Общий congestion control, окно соединения и работа приложения тоже способны задержать несколько потоков.

В HTTP/3 HTTP-кадр уже находится внутри конкретного QUIC stream: ему не требуется HTTP/2 Stream ID в каждом HTTP frame header. Нельзя переносить девятибайтовую структуру HTTP/2 на HTTP/3. Здесь другие формат кадра и кодирование целых чисел.

**Почему вместо HPACK - QPACK?** HPACK опирается на упорядоченное состояние декодирования. При независимой доставке QUIC чрезмерные зависимости заголовков свели бы на нет выигрыш. QPACK выделяет управление таблицей и ограничивает число потенциально блокируемых потоков. Динамические ссылки всё ещё могут требовать ожидания; независимость не абсолютна.

TLS 1.3 интегрирован в QUIC. Механизмы возобновления могут сократить задержку установления, но ранние данные 0-RTT имеют особенности повторного воспроизведения. Для преподавателя достаточно подчеркнуть: ускорение рукопожатия не отменяет требования к семантике безопасного повтора.

**Как ответить на «что лучше»:** сравнить RTT, потери, параллелизм, поддержку клиентов и посредников. Название новой версии не является измерением качества конкретного API. Семантика GET, 404, Content-Type и контракта приложения при смене транспорта сохраняется.

Источники: [RFC 9000: QUIC](https://www.rfc-editor.org/rfc/rfc9000.html), [RFC 9001: TLS](https://www.rfc-editor.org/rfc/rfc9001.html), [RFC 9114 §§2,6–7](https://www.rfc-editor.org/rfc/rfc9114.html), [RFC 9204: QPACK](https://www.rfc-editor.org/rfc/rfc9204.html).

# 8. gRPC: вызов метода поверх HTTP/2

В авторском варианте backend вызывает `ForecastService.GetForecast` у другого сервиса и получает готовый прогноз. `.proto` задаёт сервис и сообщения; генерация создаёт клиентские обёртки и серверные интерфейсы. Типичный выигрыш - согласованные типы и инструменты между разными языками. Сетевые задержки, недоступность и несовместимость за локально выглядящим вызовом остаются.

| Режим RPC | Клиентские сообщения | Серверные сообщения | Пример проектирования |
|---|---|---|---|
| Unary | Одно | Одно | Получить прогноз |
| Server streaming | Одно | Несколько | Читать обновления |
| Client streaming | Несколько | Одно | Передать серию наблюдений |
| Bidirectional streaming | Несколько | Несколько | Двусторонний обмен |

В стандартном отображении один RPC использует один HTTP/2 stream. Прикладной streaming не создаёт новый HTTP-stream для каждого сообщения. В DATA идёт последовательность gRPC сообщений с собственной разметкой:

```text
+------------------+-----------------------+----------------+
| Compressed: 1 B  | Message-Length: 4 B   | Message bytes  |
+------------------+-----------------------+----------------+
```

Первые 5 байт позволяют отделить сообщение. Длина - big-endian размер следующих байтов сообщения; флаг указывает применение согласованного сжатия. Одно сообщение может пересекать несколько DATA-кадров; один DATA может содержать части нескольких сообщений. HTTP framing, gRPC framing и Protobuf encoding - три уровня.

Protocol Buffers кодирует поля с номерами и wire types; обычные небольшие целые могут использовать varint. Порядок полей не заменяет номера: при эволюции нельзя переиспользовать старый номер для иного смысла. `.proto` не является OpenAPI; Swagger UI из лекции не клиент нативного gRPC.

**Ошибки:** HTTP 200 сам по себе ещё не подтверждает успех RPC; итоговый `grpc-status` обычно приходит в trailers. Deadline ограничивает ожидание, cancellation сигнализирует об отмене, но не откатывает автоматически уже выполненное бизнес-действие. Повторы всё равно требуют анализа операции.

Источники: [gRPC core concepts](https://grpc.io/docs/what-is-grpc/core-concepts/), [gRPC over HTTP2](https://grpc.github.io/grpc/core/md_doc__p_r_o_t_o_c_o_l-_h_t_t_p2.html), [Protobuf encoding](https://protobuf.dev/programming-guides/encoding/).

# 9. Почему нельзя «всё сделать через GET»

**Вопрос студентам:** «Сервер - моя программа. Могу ли я написать GET /delete?id=42 и прочитать тело GET? Зачем вообще другие методы?»

**Ответ преподавателю:** технически обработчик может выполнить почти любой код. Но метод - публичное обещание поведения всему HTTP-окружению. Это договорённость с эксплуатационными последствиями, а не условность ради красивых адресов. Кэш может удовлетворить GET без вызова сервера; crawler или prefetch - вызвать его без отдельного намерения пользователя удалить данные; библиотека - повторить безопасное обращение. Если GET удаляет, эти допустимые действия становятся разрушительными.

Безопасный метод означает, что клиент не запрашивает изменение состояния. Логи, метрики и учёт доступа могут изменяться как побочный эффект; это не делает обычный GET небезопасным. Безопасность здесь не про пароль, TLS или отсутствие уязвимостей.

Содержимое GET не имеет общепринятой семантики и не меняет смысл целевого ресурса. Частное соглашение origin и клиента не гарантирует, что его понимают посредники. Некоторые реализации отвергают такие запросы, в том числе из-за рисков неоднозначного разбора. Поэтому для сложного запроса с телом разумно спроектировать POST-поиск, описав его свойства, а не полагаться на body GET.

| Метод | Намерение | Идемпотентен по семантике |
|---|---|---|
| GET / HEAD | Получить представление / метаданные без тела ответа | Да |
| POST | Обработать присланное по правилам ресурса | Не гарантировано |
| PUT | Создать/заменить состояние указанного ресурса | Да |
| PATCH | Применить документ изменений | Не гарантировано |
| DELETE | Удалить связь ресурса с его текущей функциональностью | Да |
| OPTIONS | Узнать варианты взаимодействия | Да |

POST не означает только INSERT, а DELETE не обещает физическое стирание каждой записи и резервной копии. PUT не означает «любое обновление». Реализовывать полный набор на каждом URI не нужно: допустимые операции определяются задачей. HEAD может обеспечиваться framework; это следует проверить.

Источники: [RFC 9110 §§9.1–9.3.1](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2), [RFC 5789 §2](https://www.rfc-editor.org/rfc/rfc5789.html#section-2).

# 10. Повтор после потери ответа

Идемпотентность сравнивает предполагаемый эффект нескольких одинаковых запросов с одним, а не совпадение ответов. Первый DELETE может дать 204, следующий 404: ресурс остаётся отсутствующим. Повторный PUT полного состояния `{threshold:100}` оставляет порог 100. Сервер может вести отдельные записи аудита каждого обращения.

```text
Client -> Server: POST add observation
Server: saves observation
Server -> Client: response lost
Client: timeout; outcome is unknown
```

Таймаут означает отсутствие известного результата, а не «ничего не выполнено». Слепой POST-повтор может создать дубль. В учебном моке POST возвращает 201 без сохранения; по нему нельзя демонстрировать реальную дедупликацию.

**PATCH зависит от документа:** установить threshold=100 можно повторить с тем же эффектом; увеличить threshold на 10 - обычно нельзя. Даже повторяемое изменение может столкнуться с параллельной записью; идемпотентность не равна защите от lost update.

**Ключ идемпотентности - проектируемое соглашение.** Клиент использует один ключ для логической операции. Сервер связывает ключ с отпечатком запроса и результатом; повтор того же запроса получает прежний результат, другой payload с тем же ключом отклоняется. Нужны срок хранения, область уникальности, атомарность записи, поведение для запроса «ещё выполняется» и восстановления после сбоя. Простой check-then-write в памяти может пропустить два конкурентных запроса.

**Защита параллельного редактирования:** клиент получил представление с ETag "v4" и отправляет PUT с If-Match: "v4". Если состояние уже изменилось, сервер возвращает 412. Клиент перечитывает и решает конфликт. Это условие сравнения версии, а не магический механизм слияния.

Разбор с аудиторией: сначала спросить «Какой эффект мог уже произойти?», затем «Можно ли безопасно повторить?», затем «Какой дополнительный договор поможет?» Не начинать с универсального «поставим три retries». Повтор должен учитывать лимит времени, backoff и возможность усилить перегрузку.

Источники: [RFC 9110 §§9.2.2,13](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2), [RFC 5789 §2](https://www.rfc-editor.org/rfc/rfc5789.html#section-2). Схема ключа - авторский разбор требований, не заявленная функция мока.

# 11. Статусы: какое решение принять

| Группа | Опорные коды | Что сказать студенту |
|---|---|---|
| 1xx | 100 Continue | Промежуточная информация; не итог операции |
| 2xx | 200, 201, 202, 204 | Запрос принят/успешен в смысле конкретного кода |
| 3xx | 301, 302, 304, 307, 308 | Перенаправление либо условное использование кэша |
| 4xx | 400, 401, 403, 404, 405, 409, 412, 422, 429 | Запрос/права/состояние требуют решения клиента |
| 5xx | 500, 502, 503, 504 | Сбой сервера или участка инфраструктуры |

**200** - успешный ответ; **201** - создание; **202** - принято к обработке, завершение ещё не обещано; **204** - успех без содержимого. Из 202 нельзя заключить «прогноз рассчитан». Для долгой операции дополнительно проектируют наблюдаемое состояние задачи.

**304** - ответ на условный GET/HEAD: представление не изменилось, использовать сохранённое. Это не обычное перенаправление на новый URL. У 307/308 метод сохраняется; 301/302 имеют историческое поведение клиентов, допускающее замену POST на GET. Не учить все 3xx одним жестом «повтори запрос по адресу».

**400** - общая ошибка запроса; **422** - понятен media type, синтаксис верен, но инструкции не могут быть обработаны. Конкретное разделение ошибок документируют. **401** связано с аутентификацией, **403** - отказом в доступе. **404** может скрывать недоступный ресурс; он не раскрывает автоматически устройство БД. **405** сообщает о недопустимом методе ресурса и включает Allow; **501** - о нераспознанной/неподдерживаемой сервером функциональности метода.

**500** - непредвиденная серверная ошибка. **502** - посредник получил неподходящий ответ upstream; **504** - не дождался upstream. **503 Service Unavailable** - временная неспособность обслужить запрос, например перегрузка или обслуживание. Retry-After может подсказать ожидание; его отсутствие не означает безопасный немедленный повтор. Сам код 503 не делает POST идемпотентным.

Визуальные котики помогают запомнить группу, но подпись обязана сохранять семантику. К 503 подходит «сервис временно недоступен», к 504 - «шлюз не дождался ответа», к 404 - «ресурс не найден».

Источник: [RFC 9110 §15](https://www.rfc-editor.org/rfc/rfc9110.html#section-15).

**Углубление: Problem Details.** RFC 9457 задаёт общий JSON-формат ошибки с media type application/problem+json: type обозначает тип проблемы, title - краткое описание типа, detail - конкретный случай, instance - идентификатор случая, status - код. Расширения могут добавить прикладные сведения. Это необязательная модель для проектирования, не заявленный формат всех ошибок мока. [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html).

# 12. REST: зачем ограничения архитектуры

Переход в лекции: **HTTP описал обмен. REST объясняет, как организовать ресурсы и взаимодействие поверх такого обмена.** Набор URL с JSON не доказывает следование REST.

Ресурс - идентифицируемое понятие, например прогноз офиса на период. JSON-ответ - одно его представление. Внутри оно может собираться из нескольких таблиц, файлов и сервисов; URI не обязан повторять схему базы данных. Ссылка на готовый прогноз тоже может быть представлением отношения между ресурсами.

| Ограничение | Практический смысл |
|---|---|
| Client-server | Клиентский интерфейс и хранение/обработка развиваются раздельно |
| Stateless | Каждый запрос содержит достаточно контекста для обработки |
| Cache | Ясно, можно ли повторно использовать ответ |
| Uniform interface | Общие правила вместо отдельного протокола на каждую операцию |
| Layered system | Клиент работает через слои, не зная всех внутренних участников |
| Code-on-demand | Необязательная передача исполняемого поведения |

Uniform interface включает идентификацию ресурсов, действия через представления, самодостаточные сообщения и гипермедиа. Например, ответ содержит ссылку на доступный следующий ресурс, а клиент понимает её отношение и media type. Просто положить поле `url` в JSON недостаточно для доказательства всей архитектуры.

**Stateless не запрещает данные на сервере.** Сервер хранит пользователей, прогнозы и результаты задач. Ограничение касается скрытого состояния разговора, без которого очередной запрос невозможно понять. Токен аутентификации не превращает каждый API автоматически в stateful; нужно смотреть на модель обработки.

**Цена и польза:** единообразие упрощает посредников, кэш и независимое развитие, но может требовать дополнительных метаданных и обращения к нескольким ресурсам. RPC может быть удобнее для явно заданных удалённых команд. Выбирать нужно по взаимодействию и потребителю, а не по престижности ярлыка.

Для учебного проекта корректно говорить «HTTP API с ресурсной моделью и REST-принципами», если полный hypermedia-протокол не проработан. CRUD полезен как ориентир, но не определение REST и не обязательный набор операций.

Источник: [Fielding, глава 5](https://ics.uci.edu/~fielding/pubs/dissertation/rest_arch_style.htm). Объяснения и банковские примеры - учебная адаптация.

# 13. Кэш: свежесть и повторная проверка

Сохранённый ответ можно использовать по правилам контракта. Свежий HTTP-ответ не обязательно означает свежую статистику для модели: API может честно отдавать кэшированное представление прогноза, построенного на вчерашних наблюдениях. В описании полезно разделять время расчёта, период прогноза и время исходных данных.

```http
Cache-Control: private, max-age=60
ETag: "forecast-42-v4"
```

`max-age=60` задаёт допустимый возраст ответа для свежести. `private` запрещает хранение общим кэшем; персональный кэш может хранить его. `no-cache` разрешает хранение, но требует проверки перед использованием; `no-store` запрещает хранение согласно директиве. Эти два названия часто ошибочно считают синонимами.

```text
Client has cached representation + ETag "v4"
GET with If-None-Match: "v4"
Server: representation unchanged -> 304
Client: reuses stored body and updates metadata
```

ETag - непрозрачный валидатор: клиент сравнивает значения, а не вычисляет смысл по строке. Сервер отвечает 200 с новым телом, если условие неизменности не выполнено. 304 не переносит JSON со «свежим прогнозом»; без сохранённого представления один такой ответ не даёт клиенту данные.

**Vary** сообщает кэшу, какие поля запроса учитывать при выборе варианта. Если одна URI возвращает JSON или CSV в зависимости от Accept, игнорирование варианта может привести к выдаче неверного представления. Авторизация и персональные сведения требуют отдельного анализа правил общего кэширования.

**Условная запись:** If-Match с сильным ETag помогает не затереть чужое изменение. Два клиента читают v4; первый записывает и получает v5; второй с условием v4 получает 412. Это оптимистическая конкуренция: конфликт обнаружен в момент записи. В приложении нужно определить реакцию пользователя и возможность повторного вычисления изменения.

Источники: [RFC 9111 §§4–5](https://www.rfc-editor.org/rfc/rfc9111.html#section-4), [RFC 9110 §§8.8,13](https://www.rfc-editor.org/rfc/rfc9110.html#section-13).

# 14. JSON: структура не равна смыслу

Переход: **HTTP переносит представление; REST объясняет его роль; теперь выбираем, как закодировать данные для потребителя и хранения.** Data Store Formats в этом занятии - форматы сообщений и файлов, а не перечень СУБД. Один набор наблюдений может передаваться в JSON и храниться аналитически в Parquet.

```json
{
  "office_id": "0042",
  "visitors": 120,
  "generated_at": "2026-09-14T09:00:00Z",
  "confidence": null
}
```

JSON задаёт объекты, массивы, строки, числа, true/false и null. У него нет самостоятельного типа даты, двоичных данных или decimal с фиксированной точностью. После парсинга результат становится структурами конкретного языка; преобразования могут терять точность или различия типов, если клиент не подготовлен.

**Строковый идентификатор** сохраняет ведущие нули и не обещает арифметику. Это проектировочный пример, а не замена числового office_id действующего мока. **Время** требует договорённости о часовом поясе и смысле момента. **Null** в примере означает отсутствие значения confidence по договору; из JSON самого по себе причина неизвестна.

Деньги можно передавать целым числом минимальных единиц с указанием валюты либо согласованной decimal-строкой. Выбор зависит от точности, диапазона и клиентов. «Число есть число» - плохое основание, если один потребитель читает его через двоичную floating point арифметику.

**Как читать:** декодировать байты и разобрать JSON → проверить схему → проверить бизнес-условия → выполнить действие. Корректные скобки не доказывают, что office существует или visitors неотрицательно. Порядок полей объекта не следует использовать как бизнес-смысл; порядок массива может быть важен.

JSON удобен для небольших вложенных сообщений и доступен браузеру. Повтор имён полей и построчный разбор могут быть дорогими на больших аналитических объёмах. Это не делает JSON «плохим»: формат оценивают по задаче. Media type - application/json.

Источник: [RFC 8259](https://www.rfc-editor.org/rfc/rfc8259.html); проектировочные решения - авторские примеры по локальным материалам Lauret и Huyen.

# 15. XML и XSD: документ и его правила

![XML: прогноз офиса 42, число посетителей и время формирования](assets/xml-forecast.png)

XML описывает дерево элементов с атрибутами и текстом. Элемент `visitors` пока содержит текстовое значение: тип и допустимость задаются дополнительными правилами. Namespace отличает одноимённые элементы разных словарей; значима URI пространства имён, а не выбранный короткий префикс.

**XSD = XML Schema Definition.** Это язык описания допустимых XML-документов. Схема может задать корневой элемент, дочерние элементы и их порядок, атрибуты, типы, ограничения и количество повторений. XSD - не «ещё один формат ответа», а контракт для проверки XML.

![XSD: элемент visitors с типом xs:nonNegativeInteger](assets/xsd-visitors.png)

Это фрагмент схемы: при корректном включении в XSD он запрещает отрицательное число посетителей. Префикс `xs` должен быть связан с `http://www.w3.org/2001/XMLSchema`. Сам по себе фрагмент не является полной схемой для документа выше.

**Две проверки:** well-formed означает, что XML синтаксически корректен; schema-valid - что он соответствует выбранной схеме. XML-элемент visitors со значением −5 может пройти XML-парсер, но не ограничение XSD.

![XML: visitors со значением минус пять](assets/xml-negative-visitors.png)
 Наличие элемента не доказывает, что данные свежие или офис существует: это предметные правила.

Где применять: партнёрский документооборот, отраслевые схемы, интеграция с системами, уже работающими с XML. XML не равен SOAP; SOAP использует XML для собственного конверта и правил обработки. Для смешанного текста и элементов XML естественнее, чем попытка имитировать документ набором JSON-полей.

**Цена:** больше разметки и сложнее модель словарей; инструменты могут различаться по поддержке XSD 1.0/1.1. Не включать внешние сущности и сетевое разрешение ресурсов XML-парсера без осмысленной необходимости. Media type нашего примера - application/xml.

Источники: [W3C XML 1.0](https://www.w3.org/TR/xml/), [XML Namespaces](https://www.w3.org/TR/xml-names/), [XSD 1.1 Structures](https://www.w3.org/TR/xmlschema11-1/), [XSD Datatypes](https://www.w3.org/TR/xmlschema11-2/).

# 16. CSV: явный договор вокруг таблицы

```csv
office_id,date,visitors,note
42,2026-09-14,120,"promotion, morning"
43,2026-09-14,,"not received"
```

CSV записывает строки и поля с разделителем. Кавычки нужны, когда значение содержит разделитель, перенос строки или кавычку; сама кавычка по распространённому соглашению удваивается. Разбирать CSV простым `split(',')` нельзя: запятая внутри note не начинает новую колонку.

| Нужно согласовать | Почему это не мелочь |
|---|---|
| Заголовки и порядок колонок | Иначе значения попадут не в те поля |
| Кодировка и разделитель | UTF-8/другая кодировка, запятая/точка с запятой |
| Кавычки и переводы строк | Поле может занимать несколько физических строк |
| Типы, формат дат, единицы | Из текста «0042» нельзя угадать тип идентификатора |
| Null и пустая строка | Пустая ячейка не объясняет причину пропуска |
| Схема и версия выгрузки | Добавление/перестановка колонки меняет чтение |

CSV хорош для обмена плоской таблицей, ручного просмотра и ETL. Он не содержит универсальной встроенной типовой схемы. Автоопределение Excel или библиотеки - эвристика: идентификатор может стать числом, дата - локальной датой, большой номер - округлённым значением.

**Пропуск visitors во второй строке** нельзя автоматически заменить нулём. Ноль говорит «посетителей не было», пропуск - «значение не получено» по нашему соглашению. Если такая разница важна, описание столбца и правила импортёра должны сохранить её.

Вложенность требует решения: отдельные связанные таблицы, повтор строк или специально оговорённое кодирование внутри ячейки. Последнее усложняет стандартные инструменты. Для больших выгрузок CSV обычно читается последовательно и преобразуется в типизированные данные; это стоимость каждого нового чтения.

Media type - text/csv. RFC 4180 фиксирует распространённый вариант, но имеет статус Informational и не покрывает все реальные диалекты. Поэтому ссылка на RFC не заменяет конкретный договор об экспорте.

Источник: [RFC 4180](https://www.rfc-editor.org/rfc/rfc4180.html). Подробные практические ограничения: локальный Huyen, глава 3.

# 17. Parquet: почему колонки выгодны

```text
File
  Row group 1
    Column chunk: office_id -> pages
    Column chunk: date      -> pages
    Column chunk: visitors  -> pages
  Row group 2
    Column chunk: office_id -> pages
    Column chunk: date      -> pages
    Column chunk: visitors  -> pages
  Footer: schema + metadata + locations
```

Parquet - бинарный колонковый формат файла. Он хранит схему и метаданные. Row group объединяет диапазон строк, а внутри значения каждой колонки лежат в своём column chunk, разбитом на pages. Это не текстовая таблица и не самостоятельно работающая база данных.

**Пример задачи:** есть 100 колонок наблюдений за год, аналитик вычисляет среднее visitors по date. Поддерживающий Parquet движок может прочитать нужные колонки вместо всех. Статистика групп/страниц может помочь пропустить участки, которые не удовлетворяют фильтру. Эффект зависит от наличия метаданных, порядка данных и возможностей движка.

**Сжатие и кодирование - разные шаги.** Значения одной колонки похожи по типу и распределению, что удобно для словаря и других способов кодирования, затем для сжатия. Кодирование по словарю заменяет повторяющиеся значения короткими индексами. Сама колонковость ещё не гарантирует конкретный коэффициент экономии.

**Цена выбора:** точечное изменение одной записи не является естественной операцией обычного Parquet-файла. Много мелких файлов создаёт накладные расходы; большие группы улучшают пакетность, но требуют больше ресурсов. Нужны писатель и читатель формата. Для одного небольшого ответа браузеру JSON обычно проще.

Над Parquet могут строиться табличные системы с транзакциями и метаданными; эти свойства относятся к дополнительному слою, а не автоматически к файлу. В лекции достаточно показать схему чтения двух колонок. HTTP может отдать файл или JSON со ссылкой на выгрузку; API не обязан сериализовать каждую операцию всеми четырьмя форматами.

**Сравнение:** JSON - вложенное сообщение; XML - документ по словарю; CSV - простая переносимая таблица; Parquet - повторяемое аналитическое чтение типизированных колонок. Обоснованная альтернатива допустима, если назван потребитель и ограничение.

Источники: [Parquet file format](https://parquet.apache.org/docs/file-format/), [Encodings](https://parquet.apache.org/docs/file-format/data-pages/encodings/), [Metadata](https://parquet.apache.org/docs/file-format/metadata/).

# 18. Схема: где кончается валидатор

```json
{
  "type": "object",
  "required": ["office_id", "visitors"],
  "properties": {
    "office_id": {"type": "integer"},
    "visitors": {"type": "integer", "minimum": 0},
    "comment": {"type": ["string", "null"]}
  }
}
```

`properties` описывает поля, `required` требует их присутствия. Поле comment можно не передать; можно передать null; можно передать строку. Это три различимых состояния. Поле visitors обязательно и не допускает null; значение 0 проходит. Схема не утверждает, что офис существует или прогноз достоверен.

| Проверка | Пример отказа | Где искать исправление |
|---|---|---|
| Разбор формата | Незакрытая JSON-строка | Кодирование/синтаксис |
| Схема | visitors = "many" или −5 | Тип и ограничения |
| Предметные условия | office_id отсутствует в справочнике | Правила приложения/данные |
| Обещанное поведение | Принято наблюдение, но не сохранено | Реализация и проверка эффекта |

**Зачем этот блок в лекции:** студент перестаёт считать зелёную галочку валидатора доказательством работающего API. Он учится выбирать уровень проверки и сторону ответственности. Если сервер выдаёт ответ, нарушающий его собственную схему, это не следует оформлять как ошибку клиентского запроса.

**Required/null/default/format:** required не запрещает null сам по себе; это делает тип. default в JSON Schema не командует любому валидатору вставлять значение. Проверка format зависит от словаря и настройки; дата-строка без включённой проверки может пройти как строка. В OAS 3.2.1 Schema Object использует диалект на базе JSON Schema 2020-12; старый OAS 3.0 nullable не переносится механически.

Смысл следует закрепить словами и примерами: visitors - люди за какой период; generated_at - время расчёта или публикации; timezone - какая; capacity - максимум или текущая доступность. Число 120 с прежним типом может означать другое и сломать клиента без единой структурной ошибки.

Источник: [JSON Schema Validation 2020-12](https://json-schema.org/draft/2020-12/json-schema-validation), [JSON Schema Core](https://json-schema.org/draft/2020-12/json-schema-core).

# 19. OpenAPI 3.2.1: что именно описываем

| Сущность | Назначение | Чего сама не делает |
|---|---|---|
| OAS 3.2.1 | Правила описания HTTP-интерфейса | Не реализует сервер |
| Наш YAML/JSON | Конкретные операции, данные, ответы | Не гарантирует исполнение |
| Swagger UI | Показывает документ и отправляет запросы | Не доказывает полноту схем |
| API server | Обрабатывает обращения | Не обязан автоматически читать YAML |

```yaml
openapi: 3.2.1
info:
  title: Forecast teaching API
  version: 1.0.0
paths:
  /offices/{office_id}/forecast:
    get:
      parameters:
        - name: office_id
          in: path
          required: true
          schema: {type: integer}
      responses:
        '200':
          description: Ready forecast
```

Это сокращённая учебная иллюстрация, не полный контракт демонстрации: в полном документе есть servers, days, media type, схема ответа и ошибки. YAML-отступы выражают вложенность, дефис - элемент списка. YAML документа и JSON HTTP-тела относятся к разным уровням.

**Читать операцию:** соединить servers + path; найти метод; path/query/header-параметры; requestBody; responses; content/media type; schema и примеры. `$ref` переиспользует описание, например `#/components/schemas/Forecast`. Он не выполняет сетевой запрос к вашему API и не подставляет готовый объект данных.

В POST requestBody описывает передаваемое содержимое. GET не следует объяснять через body как универсальную альтернативу параметрам. Пример ответа помогает человеку; схема задаёт ограничения. Один удачный example не перечисляет весь диапазон допустимых ответов.

**Версия документа:** `openapi: 3.2.1` - язык описания; `info.version` - версия конкретного документа. Версия бизнес-API может согласовываться с ним, но равенство не требуется OAS. Обновление Swagger UI тоже отдельная версия инструмента.

В лекции фиксирована OAS 3.2.1, опубликованная 10.09.2026. Материалы книг для 3.0 требуют адаптации. Первоисточник: [OAS 3.2.1](https://spec.openapis.org/oas/v3.2.1.html).

# 20. Демонстрация: обещание и факт

Цель показа - провести одну операцию через четыре состояния: **документ → UI → реальный запрос → сравнение с обещанием**. Тогда Swagger UI не выглядит ещё одной картинкой YAML.

1. В авторском `lecture02-openapi.yaml` найти GET /offices/{office_id}/forecast, office_id и days. Показать, где разрешены 1 и 7: диапазон 1…7 был бы другой договорённостью.
2. Открыть локальную страницу `/lecture-02`: она показывает этот авторский документ. `/docs` и `/openapi.json` относятся к generated-описанию и могут быть неполными по бизнес-схемам.
3. Execute для office 42, days=1: найти фактические URL, статус, заголовки, тело. Отделить их от Example Value, существовавшего до вызова.
4. Показать серверную ошибку days=2. Если UI блокирует ввод, отдельно показать ограничение UI и запрос к серверу; не выдавать одно за другое.
5. Найти POST /observations и requestBody/Observation/$ref. Не утверждать, что мок сохраняет наблюдения или устраняет повторы.

| Проверка договора | Что обнаруживает | Что не доказывает |
|---|---|---|
| Валидность документа и ссылок | Ошибки структуры OAS, сломанные $ref | Что сервер работает |
| Примеры относительно схемы | Противоречивые example | Все возможные входы/выходы |
| Фактическое поведение | Расхождения ответа/эффекта с договором | Будущую безотказность |

**Ответ на вопрос «поправил YAML - сервер исправился?»** Обычно нет: документ и обработчик связаны выбранным процессом. Возможны design-first с генерацией или code-first с экспортом; в обоих случаях нужны проверки, иначе они расходятся. Автогенерация может хорошо описывать типы framework, но пропускать бизнес-семантику и последствия ошибок.

План репетиции преподавателя: убедиться, что локальный адрес доступен именно браузеру; проверить успешный и ошибочный запрос; приготовить резервный снимок YAML и реального ответа. Docker-проверка не выводится из успешного Python-запуска: это разные способы запуска.

Источник стандарта: [OAS 3.2.1](https://spec.openapis.org/oas/v3.2.1.html). Инструмент: [Swagger UI](https://swagger.io/open-source/swagger-ui/). Адреса и ограничения - из локального сценария/контракта, не обещание производственного сервиса.

# 21. Совместимость: кто именно сломается

Версионирование нужно для управления изменением обещаний. Номер сам ничего не сохраняет: старый клиент либо продолжает понимать обмен, либо нет. Рассматривайте отдельно старого отправителя запроса и старого читателя ответа.

| Изменение | Риск для старого клиента |
|---|---|
| Новое обязательное поле запроса | Он его не отправляет: прежний запрос отклонён |
| Удаление обещанного поля ответа | Он ожидает поле: чтение ломается |
| Новое поле ответа | Обычно терпимо только если читатель допускает неизвестные поля |
| Новое значение enum ответа | Может сломать исчерпывающий switch |
| Число стало строкой | Ломается тип/вычисление |
| Часы заменены минутами при том же числе | Структура проходит, бизнес-смысл нарушен |
| Новый расчёт модели | Требует оценки ожиданий качества и значения результата |

**Зачем объяснять версии:** отличить обновление языка OpenAPI от изменения API и модели. Если в YAML заменили номер OAS, не стало автоматически безопасно менять visitors с «за день» на «за час». Не нужно заставлять API передавать пять версий в каждом сообщении; достаточно определить, какие изменения и каким способом отслеживает команда.

**Expand-and-contract:** сначала добавить новый способ/поле и поддержать старое, затем обновить потребителей, измерить использование старого договора, объявить срок удаления и только затем удалить. Входящий API может некоторое время принимать обе формы, но должен явно разрешать конфликт, если клиент прислал обе. «Поддержим обе» без правила приоритета создаёт неоднозначность.

Контрактные проверки должны содержать реальные ожидания потребителя: допустимые запросы, используемые поля/enum, единицы, ошибки и повторы. Полная копия реализации в тесте плохо обнаруживает ошибку исходного обещания. Нужны независимые примеры и негативные случаи.

**Спросить студента:** «Добавили optional-поле в ответ. Всегда безопасно?» Верный ответ: нет, нужно проверить реальные десериализаторы и правила неизвестных полей. Слова «обратно совместимо» имеют смысл относительно конкретного множества потребителей и договорённостей.

Источники: [Google AIP-180](https://google.aip.dev/180) - практика одной экосистемы; локальные Newman, глава 5, и Lauret, глава 9. Примеры таблицы - учебная адаптация.

# 22. Ответы преподавателю и самопроверка

## Ключ к интерактиву о методах

**A. Размер готового CSV без скачивания → HEAD.** Ответ не содержит тела; метаданные соответствуют GET с оговорками стандарта. Content-Length может отсутствовать, поэтому HEAD не гарантирует размер для любой реализации.

**B. Полностью заменить расписание по известному /offices/42/schedule → PUT.** Передаётся полное желаемое представление. Если требуется защитить чужие изменения, добавить условие If-Match.

**C. Запустить долгую сборку отчёта → POST /report-jobs.** 202 подходит договору «принято, обработка не завершена»; нужен способ читать состояние. 201 тоже обоснован, если договор явно сообщает о создании ресурса job, а не о готовом отчёте.

**D. Отозвать /subscriptions/sub-7 → DELETE.** Повтор не должен возвращать подписку; различие 204/404 не нарушает идемпотентности. Это новые проектировочные ситуации, не дополнительные функции мока.

## Ключ к интерактиву о потерянном ответе

**GET готового прогноза:** повтор соответствует безопасной и идемпотентной семантике; сам прогноз может измениться со временем, это не нарушение идемпотентности.

**PUT полного состояния с threshold=100:** одинаковая желаемая запись даёт тот же эффект. Для защиты от чужого параллельного изменения дополнительно нужен, например, If-Match.

**POST добавить наблюдение:** эффект мог уже произойти; без соглашения о дедупликации повтор может создать дубль. Текущий мок без хранения не доказывает поведение будущего сервиса.

**PATCH установить 100 / прибавить 10:** первый вариант может быть идемпотентным, второй обычно нет. Метод сам не гарантирует семантику документа изменений.

## Короткие ответы на частые вопросы

**HTTP/2 - бинарный, значит JSON исчез?** Нет. Поля и разметка передаются иначе; JSON остаётся возможным содержимым DATA.

**END_HEADERS завершает ответ?** Только блок полей. Ответ без тела может завершаться HEADERS с END_STREAM; иначе ожидается продолжение согласно протоколу.

**503 означает «безопасно повторить POST»?** Нет. Учитываем возможный эффект, договор повторов и Retry-After.

**XSD или JSON Schema проверит правильность прогноза?** Проверит оговорённую структуру и ограничения. Точность модели и свежесть исходных данных требуют других проверок.

**Нужно всё хранить в Parquet?** Нет. Он полезен для аналитического чтения; транзакционная запись и маленькие сообщения имеют другие требования.

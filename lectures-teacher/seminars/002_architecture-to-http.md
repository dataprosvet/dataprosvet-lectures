## 5–15. Условие и рабочие допущения

### Нормализованное условие

Спроектировать систему прогнозирования клиентского потока в офисах банка. Она собирает почасовую статистику посещений, хранит историю, рассчитывает прогноз количества посетителей на выбранные интервалы, показывает нагрузку в течение недели и сравнение прошлого с текущим периодом. Численность сотрудников поступает из системы «Офисы банка». Внешняя система «Руководитель офиса» получает фактические и прогнозные сведения. Пользователи получают уведомления о превышении нормы посетителей на одного сотрудника.

Получение **готового прогноза** должно отвечать за одну секунду. Время загрузки данных и расчёта модели в эту секунду не включается. Интерфейс должен быть прост для внешнего потребителя.

### Допущения варианта C4-v3

Это учебные решения для обсуждения, а не дополнительные пункты исходного условия:

- По эталону архитектора единственный источник исходных данных — BankOffices («Офисы банка»). В учебном варианте он возвращает справочник, штат и число посещений по офису за завершённый час; последнее является допущением, поскольку эталон не детализирует набор данных. Персональных сведений посетителей нет.
- Загрузчик опрашивает источник после завершения каждого часа; ключ наблюдения — офис и час. Повторная загрузка не удваивает счётчик.
- Справочник офисов обновляется ежедневно и по ручному повторному запуску загрузчика при необходимости. Время последнего обновления сохраняется.
- Прогноз пересчитывается по расписанию после ожидаемой загрузки, только по новым успешно сохранённым данным. Рабочий горизонт — следующая неделя с почасовыми интервалами. Завершение расчёта фиксируется вместе с версией модели и временем среза входных данных.
- Проверка перегрузки использует готовый прогноз и численность сотрудников для того же офиса. Норма X задаётся в посетителях на сотрудника за час. Пример: X=10, сотрудников 3, прогноз 45 посетителей/час — нагрузка выше 30.
- По эталону добавлен EmailServer. Alert Worker сохраняет предупреждение и передаёт письмо этому внешнему серверу. SMTP с STARTTLS — учебный выбор протокола. Отправка выполняется вне запроса чтения прогноза; нужны учёт попыток и повтор после сбоя. Подтверждение почтового сервера не доказывает прочтение письма. Клиент использует Web UI, руководитель — внешнее приложение OfficeManager; правила видимости данных этих ролей уточняются при проектировании контрактов.
- Для примера численность сотрудников считается постоянной на горизонте прогноза. В реальной системе требуется график смен; отсутствие этого уточнения ограничивает точность вывода о перегрузке.
- Данные старше двух часов помечаются как устаревшие для учебного сценария; порог обсуждаем отдельно от времени ответа. Отсутствующий прогноз не заменяется нулём.

Вопрос группе: «Может ли ответ прийти за 20 мс и при этом быть бесполезным?» Ожидаемый ответ: да, если прогноз устарел, рассчитан не для того офиса/периода или сведения о сотрудниках неверны.

## 15–20. C4 за пять минут

C4 показывает архитектуру с разной степенью приближения:

1. **Context:** наша система, её пользователи и соседние системы.
2. **Containers:** приложения и хранилища внутри нашей системы, их ответственность и взаимодействие.
3. **Components:** устройство одного приложения внутри.
4. **Code:** детали реализации.

Контейнер C4 — приложение или хранилище, не обязательно Docker-контейнер. На первом уровне система — один блок; на втором раскрываем этот же блок. Не добавляем внутренний сервис в окружение только потому, что он вызывает API.

Покажите один и тот же объект в двух масштабах. Правила деталей студенты изучают самостоятельно: [контекст](https://c4model.com/diagrams/system-context), [контейнеры](https://c4model.com/diagrams/container). Уровни 3–4 не входят в сдачу.

### Почему такие границы

**API** обслуживает запросы чтения независимо от длительности расчёта. **Загрузчик** работает с частотой и ошибками внешних источников. **Расчёт** имеет собственный цикл и вычислительную нагрузку. **Проверка перегрузки** применяет бизнес-норматив к готовому прогнозу и может меняться независимо от модели. **UI** отвечает за представление, не читает БД напрямую.

Разделение расчёта и проверки норматива позволяет показать, почему хороший прогноз и решение «сотрудников недостаточно» — разные операции. Для небольшой реализации эти фоновые задачи можно объединить в одно приложение. Если выбрано объединение, оно должно быть отражено на C4; нельзя рисовать пять приложений, а затем незаметно назвать пять функций одного процесса пятью контейнерами.

### Почему HTTP/JSON и PostgreSQL

Для UI и внешних потребителей HTTP/JSON даёт понятный запрос и читаемый результат. Внешним источникам приписано HTTP API как учебное допущение; их реальный протокол неизвестен. Между приложениями и общей БД используется протокол PostgreSQL с SQL, а не HTTP.

Одна реляционная БД позволяет связать офис, час, штат и прогноз, хранить историю и выполнять запросы по офису/интервалу. На старте индекс по офису и времени полезнее необоснованного добавления нескольких типов БД. Общая БД упрощает разбор, но связывает приложения общей схемой: это не пример полностью независимых микросервисов. Для реализации потребуются отдельные права: API читает, загрузчик пишет исходные данные, расчёт — прогнозы, проверка — предупреждения.

Кэш, очередь и отдельное аналитическое хранилище не нужны для объяснения этого масштаба без измерений и объёмов. Их отсутствие — учебное упрощение, не универсальное правило.

### Проследить четыре сценария

1. **Обновление данных:** загрузчик запрашивает завершённый час и справочник → сохраняет согласованные записи. Ошибка источника не стирает прежнюю историю; фиксируются время последнего успеха и пробел данных.
2. **Расчёт:** фоновое приложение проверяет новый срез → читает историю → вычисляет прогноз → сохраняет новую версию атомарно. API продолжает читать предыдущую готовую версию, пока новая не опубликована.
3. **Получение за одну секунду:** UI или внешняя система → API → чтение готовой версии из БД → ответ. В этой цепочке нет обращения к внешним источникам или запуска модели. Индексы, нагрузка и измерения нужны для доказательства фактической задержки; схема её не доказывает.
4. **Предупреждение:** фоновая проверка читает новую версию прогноза и штат → вычисляет превышение → сохраняет предупреждение с ключом офис/интервал/версия → Alert Worker передаёт письмо в EmailServer. Приложение руководителя получает сохранённые предупреждения через Read API; учебный маршрут Read API — `GET /offices/{office_id}/alerts`. Внешний OfficeManager в демо реализует только чтение прогноза. Повторный проход не создаёт копий. При нулевом или неизвестном штате нужна отметка о неполных данных, а не деление на ноль.

История и текущий период сравниваются при одинаковой длительности интервалов и явном часовом поясе. Время расчёта, время исходных данных и прогнозируемый период — три разных значения. Для интерфейса они доступны вместе с готовым прогнозом.

## 45–55. Минимум HTTP перед лекцией

HTTP организует обмен запросом и ответом. У запроса есть метод и адрес, заголовки и иногда тело; у ответа — статус, заголовки и иногда тело. Метод выражает смысл обращения: GET читает представление ресурса, POST передаёт данные для обработки в соответствии с контрактом. JSON задаёт формат данных и сам по себе не делает API REST.

REST помогает описывать интерфейс через ресурсы, их представления и согласованную семантику операций. «Готовый прогноз офиса за период» — ресурс, понятный потребителю; имя внутреннего метода модели не обязано быть адресом API. OpenAPI описывает пути, методы, параметры, схемы и ответы; Swagger UI показывает это описание и позволяет отправлять запросы. Контракт не является реализацией, а документация не доказывает правильность ответа сервера.

Разберите `GET /offices/42/forecast?days=1`: `42` — параметр пути, `days=1` — query-параметр, тела нет. Ответ 200 содержит JSON с `points`, `generated_at`, `source_updated_at` и `stale`. `Content-Type` описывает формат тела. Сравните с `POST /observations` у BankOffices: здесь сведения о посещениях передаются JSON-телом. Имитация создания — 201; неправильные данные — 422. Это соглашения конкретного контракта, не правило «любой POST возвращает 201».

Покажите единый вид ошибки: `{"error":{"code":"forecast_not_ready","message":"..."}}`. Код HTTP сообщает класс результата, прикладной код уточняет причину. Неизвестный офис и известный офис без прогноза здесь оба возвращают 404, но разные `error.code`.

Вопрос: «Может ли успешный сетевой обмен означать ошибку запроса?» Ожидаемый ответ: да, сервер доступен, но вернул статус ошибки и объяснение. Вопрос: «Нужно ли делать POST, чтобы получить уже рассчитанный прогноз?» Ожидаемый ответ: простое чтение обычно выражается GET; запуск нового расчёта — отдельная операция с другим эффектом.

Быстрый ответ не доказывает SLA.

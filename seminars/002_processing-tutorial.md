## Банковский контур: откуда берутся данные

Предположите, из каких источников банк собирает данные, какие у них типы и для чего они могут использоваться.

| Мобильное приложение | события, клики, операции, технические логи |

| Сайт банка | посещения, поисковые запросы, действия |

Сквозная цепочка: источник → сбор → передача → хранение → обработка → анализ → решение. Цель — понять, почему разным банковским данным нужны разные способы сбора и хранения.

## Data Ingestion

**Data Collection / Ingestion** — сбор и загрузка данных. Вопрос: как данные попадают в информационную систему?

Подходы:

- API — обмен между приложениями
- Logs — журналы событий
- Files — CSV, JSON и другие файлы
- Batch — пакетная загрузка
- Streaming — непрерывный поток событий

Источники на входе: IoT, API, logs, streaming, batch.

## Batch и Streaming

**Batch.** Данные сначала накапливаются, затем обрабатываются пакетами. Пример банка: транзакции за сутки → файл → ночная обработка → отчёт.

Когда удобно: ежедневная отчётность, расчёт агрегатов, регулярная загрузка в DWH, задачи, где задержка в минуты или часы допустима.

Инструменты batch: Apache Spark (распределённая обработка больших объёмов), Apache Hadoop MapReduce (классическая пакетная обработка), Apache Airflow (оркестрация цепочек), Python/Pandas (небольшие и учебные наборы). Инструмент выбирают по объёму, скорости и архитектуре.

**Streaming.** Событие обрабатывается по мере поступления. Пример: покупка картой → событие → потоковая система → проверка → решение.

Особенно важен для обнаружения мошенничества, мониторинга операций, контроля безопасности и систем с малой задержкой.

Инструменты streaming: Apache Kafka (передача и хранение потоков событий), Apache Flink (real-time, пакет и поток), Spark Structured Streaming. Упрощённая схема: POS / приложение → Kafka → Flink / Spark → аналитика / сервис решения.

Ключевой критерий выбора: требуемая задержка между появлением данных и реакцией системы.

| | Batch | Streaming |
|---|---|---|
| Схема | накопление → пакет → обработка → результат | событие → обработка почти сразу → результат |
| Пример | ночной отчёт | проверка подозрительной операции |

### Мини-задача: Batch или Streaming?

Определите подход и объясните почему:

1. Ежемесячный отчёт по кредитному портфелю.
2. Проверка операции по карте на мошенничество.
3. Ежедневная загрузка истории платежей в аналитическое хранилище.
4. Мониторинг ошибок банкоматов.
5. Расчёт статистики по клиентам за предыдущий год.

Разбор:

1. Batch — отчёт формируется периодически.
2. Streaming — решение нужно во время операции.

4. Streaming — важно быстро реагировать на события.
5. Batch — исторический расчёт не требует обработки каждой записи в момент появления.

## Зачем разные хранилища

Одна система хранения не обязана одинаково хорошо решать все задачи. Выбор определяют скорость, структура, объём, стоимость и аналитика.

- **Operational БД** — текущие операции и транзакции: открыть счёт, проверить баланс, провести перевод, зарегистрировать платёж, изменить данные клиента. Приоритет — быстрые и надёжные транзакции.
- **DWH (Data Warehouse)** — структурированная аналитика и отчётность.
- **Data Lake** — большие объёмы разнородных данных.
- Дополнительные хранилища — специализированные задачи.

Цепочка операционной БД: клиент → мобильное приложение → API → операционная БД. Типичные таблицы: CLIENTS, ACCOUNTS, CARDS, TRANSACTIONS. Вопрос «каков текущий баланс счёта?» — не то же самое, что «как изменилось поведение миллионов клиентов за 5 лет?».

DWH: источники → ETL/ELT → DWH → BI / аналитика. Собирают согласованные структурированные данные из разных систем. Примеры вопросов: динамика выдачи кредитов, доходность продуктов, сегментация клиентов, показатели по регионам.

Почему аналитику не считают в operational БД: она заточена под много коротких транзакций. Аналитический запрос может читать миллионы строк, объединять таблицы, агрегировать и строить исторические срезы — нагрузку отделяют.

Data Lake хранит большие объёмы разных типов: таблицы, JSON/CSV, логи, тексты, изображения и документы, потоковые события. Идея: сначала сохранить, потом подготовить под конкретную задачу. Пример содержимого: транзакции (CSV/JSON), логи, документы (PDF/тексты) — дальше ML, Data Mining, поиск аномалий.

| | DWH | Data Lake |
|---|---|---|
| Данные | преимущественно структурированные, подготовленные | структурированные и неструктурированные, исходные и подготовленные |
| Задачи | отчётность и BI | ML, Data Mining, исследовательская аналитика |
| Структура | высокая согласованность | большое разнообразие форматов |

Кратко:

- операционная БД — «что происходит сейчас?»
- DWH — «что происходило и какие закономерности видны?»
- Data Lake — «какие данные мы сохранили и что ещё можно из них получить?»

Пример: транзакция → operational БД; история для отчёта → DWH; транзакции + логи + тексты + документы → Data Lake.

Специализированные классы (важно назначение, не конкретный продукт):

- Key-Value — быстрый доступ по ключу
- Document Store — JSON-подобные документы
- Graph Database — связи между объектами
- Time-Series Database — временные ряды и события
- Object Storage — большие файлы и объекты

Пять вопросов при выборе хранилища:

1. Данные структурированные или разнородные?
2. Нужна транзакция или аналитический запрос?
3. Какой объём данных?
4. Какую задержку допускает бизнес?
5. Как данные будут использоваться дальше?

## Связь с 7V

| V | В банковском контуре |
|---|---|
| Volume | миллионы и миллиарды транзакций |
| Variety | таблицы, JSON, логи, тексты, документы |
| Velocity | операции и события в реальном времени |
| Veracity | ошибки, пропуски, качество данных |

| Visualization | dashboards и отчёты |

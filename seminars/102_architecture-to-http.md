# Семинар 2. От архитектуры системы к HTTP API

Разберём, как перейти от требований к системе к понятной схеме взаимодействия, а затем прочитать запрос и ответ API. Совместный пример — прогноз клиентского потока в офисах банка. После занятия вы сможете объяснить границы системы, различить два уровня C4 и описать одно обращение к API своего командного проекта.

## Подготовка

Возьмите условие и текущую архитектуру своего кейса из [ДЗ 1](../homeworks/001_team-case-architecture.md). Если схемы ещё нет, начните с потребителей и нужных им данных. Предварительное знание C4 или HTTP не требуется. Для записи решения достаточно редактора текста и любого инструмента рисования; локальные сервисы показывает преподаватель. Используются только вымышленные данные.

## Банковский кейс

Система собирает почасовую статистику посещений офисов, сохраняет историю и готовые прогнозы. Пользователь видит нагрузку на неделе и сравнивает прошлый и текущий периоды. Сведения о численности сотрудников приходят из системы «Офисы банка». Система «Руководитель офиса» получает фактические и прогнозные данные. При превышении норматива посетителей на сотрудника пользователь получает предупреждение.

Получение уже готового прогноза должно занимать не более одной секунды. Время его расчёта и свежесть данных — отдельные характеристики.

## 2. Коротко о C4

C4 — четыре масштаба описания архитектуры:

- Context: система, люди и внешние системы вокруг неё.
- Containers: приложения и хранилища внутри выбранной системы.
- Components: устройство отдельного приложения.
- Code: детали реализации.

В этой работе используем уровни 1 и 2. Контейнер C4 означает приложение или хранилище; Docker для него не обязателен. На контексте система остаётся одним блоком, на следующем уровне этот блок раскрывается.

В совместном примере стрелка показывает, кто к кому обращается, а подпись — зачем. Ответ подразумевается. Если обозначаете именно потоки данных, поясните это в легенде и не смешивайте два смысла стрелок.

Самостоятельно изучите правила [контекстной](https://c4model.com/diagrams/system-context) и [контейнерной](https://c4model.com/diagrams/container) диаграмм и примените их к своему проекту. Уровни 3–4 сдавать не нужно.

Сначала — общая структура. `METHOD` обозначает метод (например, GET или POST), `/path` — путь, `?key=value` — необязательные параметры запроса. Значения в угловых скобках — места для подстановки, квадратные скобки у порта обозначают необязательную часть. Эти скобки не нужно отправлять буквально. `media-type` — тип данных, например `application/json`; `bytes` — число байт тела.

## 3. HTTP на практике

### Наш пример: передаём наблюдение в BankOffices

![Структура HTTP/1.1: метод POST, путь /observations, версия протокола, заголовки, пустая строка и JSON-тело](../assets/seminar-002/http-request.png)

1. **Стартовая строка:** метод, цель запроса и версия HTTP. В нашем примере цель — путь `/observations`; query-параметры при наличии тоже входят в эту часть, например `/offices/42/forecast?days=1`. Это не обязательно полный URL: здесь адрес сервера передаётся в `Host`.
2. **Заголовки:** `Host` указывает сервер и порт, `Accept` — желаемый формат ответа, `Content-Type` — формат отправляемого тела, `Content-Length` — его длину в байтах. `User-Agent` сообщает сведения о клиенте; в примере мы задаём учебное имя.
3. **Пустая строка** отделяет заголовки от тела. Строки HTTP/1.1 завершаются CRLF (`\r\n`); после последнего заголовка получается `\r\n\r\n`.
4. **Тело** содержит передаваемые данные. Здесь это JSON из 30 байт. Тело необязательно: в нашем GET его нет. `Content-Length` curl вычисляет самостоятельно; вручную задавать его не нужно.

Это текстовая структура **HTTP/1.1**. В HTTP/2 и HTTP/3 сообщения передаются кадрами, поэтому такой вид стартовой строки на проводе к ним не применяется. `Content-Length` не является обязательным заголовком каждого HTTP-запроса; здесь он описывает конкретный POST с известной длиной тела.

**Что означает `User-Agent: seminar-demo` в нашем запросе?** `User-Agent` — заголовок со сведениями о программе, которая отправляет запрос. Здесь запрос отправляет curl, а `seminar-demo` — произвольное учебное имя, которое мы задаём ему параметром `-A 'seminar-demo'`. Это не название сервера BankOffices, не имя пользователя и не средство авторизации. Без `-A` curl обычно отправляет `User-Agent: curl/<версия>`, где вместо `<версия>` стоит версия установленной программы. Наш мок не использует этот заголовок для выбора ответа; он нужен, чтобы в терминале и mitmweb было легко узнать учебный запрос.

### Как увидеть запрос и ответ в терминале

Сначала запустите локальное демо по README ниже. Команды рассчитаны на терминал macOS/Linux. Все данные вымышленные.

**Метод, путь, заголовки запроса и ответа:**

```sh
curl --http1.1 -v -sS \
  'http://127.0.0.1:8000/offices/42/forecast?days=1' 2>&1
```

В выводе `>` обозначает отправленные строки запроса, `<` — полученные строки ответа, `*` — диагностические сообщения curl. Это пометки программы, они не являются частью HTTP. JSON ответа выводится отдельно. `2>&1` объединяет диагностический вывод и тело ответа в одном потоке терминала.

**Полный обмен с телом POST — тот же запрос, что на схеме:**

```sh
curl --http1.1 --trace-ascii - --trace-time -sS -o /dev/null \
  -A 'seminar-demo' \
  -H 'Accept: application/json' \
  -H 'Content-Type: application/json' \
  --data-raw '{"office_id":42,"visitors":45}' \
  'http://127.0.0.1:8001/observations'
```

Найдите `> Send header`, `> Send data`, `<= Recv header` и `<= Recv data`. Так видны и заголовки, и JSON в обе стороны. Ожидаемый ответ мока — **201 Created**; при `visitors: -1` — **422**. Повтор корректного POST снова даёт 201, поскольку наш мок не сохраняет данные.

| Параметр          | Что делает                                                                                              |
| ----------------- | ------------------------------------------------------------------------------------------------------- |
| `--http1.1`       | Выбирает HTTP/1.1 для сопоставления со схемой                                                           |
| `-v`              | Показывает диагностику и заголовки обоих направлений; тело отправляемого JSON отдельно не распечатывает |
| `--trace-ascii -` | Выводит трассировку заголовков и тел в терминал; используется вместо `-v`                               |
| `--trace-time`    | Добавляет временные отметки к трассировке                                                               |
| `-i`              | Добавляет заголовки **ответа** к его телу; запрос не показывает                                         |
| `-sS`             | Убирает индикатор прогресса, сохраняя сообщения об ошибках                                              |
| `-H`              | Задаёт заголовок запроса                                                                                |
| `-A`              | Задаёт User-Agent                                                                                       |
| `--data-raw`      | Передаёт указанное тело и выбирает POST; дополнительный `-X POST` здесь не нужен                        |
| `-o /dev/null`    | Убирает отдельную повторную печать тела ответа; в трассировке оно остаётся                              |

Смещения вида `0000:` и служебные подписи трассировки не входят в HTTP-сообщение. Для побайтового просмотра, включая CRLF в шестнадцатеричном виде, замените `--trace-ascii -` на `--trace -`. Трассировка может содержать токены и персональные данные: для упражнения используйте только локальные моки.

Источники: [структура сообщения HTTP/1.1 — RFC 9112, разделы 2–3](https://www.rfc-editor.org/rfc/rfc9112.html#section-2.1), [параметры curl](https://curl.se/docs/manpage.html).

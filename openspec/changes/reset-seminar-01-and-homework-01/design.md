## Context

Мотивация и границы описаны в [proposal.md](proposal.md). Исследование от 2026-09-08 показало:

- В ветке `courses/api-technologies` опубликована только лекция 1; `seminars/` и `homeworks/` содержат `.gitkeep`.
- В рабочем дереве уже есть пользовательские изменения архива лекции 1. Они не относятся к этой миграции.
- Старые практические планы находятся в `author-lectures-3-4-and-first-practicals`, `author-first-four-api-learning-path`, `revise-first-two-api-lectures-and-prb-practicals`; старый контракт веток — в `extract-api-course-code-repository`. Некоторые изменения смешивают лекционную и практическую части.
- Репозиторий сдачи приватный; исследованы десять веток, без открытых PR и защищённых веток. Эти сведения требуют обновления перед удалением.
- Издатель разрешает карточки без `markdown`; объявленный Markdown обязан быть tracked. Поэтому игнорируемый файл нельзя объявлять в манифесте даже для закрытого материала.

Design необходим из-за миграции двух репозиториев, удаления веток и разделения публичных метаданных и локальных текстов.

## Goals / Non-Goals

**Goals:**

- Независимо проверять готовность локальных условий, состояние Git и фактическую публикацию карточек.
- Сохранить восстанавливаемость удаляемых веток и достоверность старых OpenSpec-отчётов.
- Сделать первый этап выполнимым как проектирование без запуска сервисов.

**Non-Goals:**

- Не создавать генератор распределения кейсов, автопроверку архитектуры или новый CI сдачи работ.
- Не добавлять языки реализации, модели, реальные банковские интеграции, обязательные шаблоны или готовые ответы.
- Не изменять приложение, общий README шаблона издателя, защищённые общие файлы publisher или преподавательский репозиторий.

## Decisions

### 1. Разделить карточки и полные условия

В Git идут `course.yaml`, точечные правила `.gitignore` и согласованные плановые изменения. Два полных Markdown остаются в обычных каталогах материала:

| Локальный файл | Карточка в course.yaml |
|---|---|
| `seminars/001_service-interaction-architecture.md` | `seminars`, slug `service-interaction-architecture`, sortOrder 2 |
| `homeworks/001_team-case-architecture.md` | `homeworks`, slug `team-case-architecture`, sortOrder 3 |

Обе карточки: `lifecycleStatus: published`, `availability: temporarilyUnavailable`, непустые `title` и `summary`, без `markdown`, `briefMarkdown`, assets и attachments. В `.gitignore` добавляются именно два пути, чтобы будущие задания не игнорировались автоматически. README сдачи содержит краткую организацию и результаты, но не дублирует полные условия.

Альтернатива с tracked закрытым Markdown нарушает требование не коммитить материалы. Объявление игнорируемого пути ломает чистый CI checkout. Отдельное локальное ручное размещение текстов в Appwrite не требуется и создало бы состояние вне манифеста.

### 2. Сохранить исходную задачу и ограничить результат первого этапа

Семинар включает краткое описание занятия, затем условие страницы 4. Название карточки и всего Markdown относится к архитектуре взаимодействия сервисов; ошибочный заголовок внутри исходного условия и пункт про серверы сохраняются с редакторским примечанием. Это обратимое редакторское допущение: пользователь пока не выбрал исправление текста. Никакого нового требования вместо спорного пункта не добавляется.

ДЗ включает вводное общее задание и три полных варианта со страниц 1–3 с двумя разделителями между ними. Каждая команда получает один вариант. Число участников, тайминг, дедлайн и конкретный способ жеребьёвки не заданы и не изобретаются. Фиксируется случайное назначение кейса каждой команде; при числе команд больше трёх допустимы повторяющиеся варианты, точная балансировка не требуется.

Пять результатов первого ДЗ берутся из секций «Задание». Функциональные и нефункциональные требования описывают проектируемую семестровую систему, а не обязательную работающую реализацию к первой сдаче. Звёздочки остаются у исходных пунктов; общая легенда сообщает о необходимости самостоятельно прийти к неочевидному решению без подсказки ответа.

Альтернатива с тремя отдельными домашними заданиями противоречит одному файлу с тремя вариантами; требование сразу реализовать систему расширяет первый этап сверх секции «Задание».

### 3. Оставить две ветки и простой командный путь сдачи

`main` остаётся основной веткой с коротким каталогом. `seminar/01-api-scenarios` сохраняет имя ветки, но получает новое содержимое и README; её актуальный URL после переименования — `https://github.com/TheTonyPub/api-technologies-2026/tree/seminar/01-api-scenarios`. Учебная ветка содержит только краткие инструкции и относящиеся к новому этапу служебные файлы; старые `profiles/`, contracts, synthetic-data и public-checks удаляются после проверки назначения. Новые пустые шаблоны не обязательны.

README учебной ветки описывает: на семинаре — общий разбор и начало назначенного кейса; дома — завершение архитектуры. Команда продолжает ту же работу в своём приватном fork/репозитории и фиксирует сдачу ссылкой на PR/MR и итоговый commit. Один набор результатов включает состав команды и назначенный кейс, потребителей, две диаграммы и краткий выбор протоколов/БД. Формат инструмента рисования не навязывается; диаграммы должны быть доступны рецензенту. Создание студенческих аккаунтов, репозиториев и PR не входит в эту миграцию.

Удаляемый список:

- `lecture/01-api-interface-layer`
- `lecture/02-http-rest-openapi`
- `lecture/03-integration-styles`
- `lecture/04-fastapi-services`
- `seminar/02-rest-openapi-contract`
- `seminar/03-http-diagnostics`
- `seminar/04-integration-style-selection`
- `seminar/05-fastapi-service`

Резервная копия — локальный `git bundle` актуальных refs, проверенный `git bundle verify`, вне tracked-дерева курса и вне раздаваемого репозитория. Никаких backup-веток на GitHub: они нарушили бы требование двух веток. Изменения README и очистка выполняются обычными коммитами без force-push и переписывания истории. Удаление refs не обещает стирание исторических объектов Git.

Альтернатива с удалением `main` отменена пользователем. Дополнительное переименование учебной ветки не требуется.

### 4. Вывести старые планы практики из действующего контекста

Перед изменениями составляется точечный список старых практических файлов и конфликтующих дельт. Только действующие старые материалы практики удаляются; исходные РПД, локальные книги, лекции и исторические отчёты сохраняются. В смешанных changes сохраняются лекционные задачи и требования.

В затронутых proposal/design/tasks фиксируется замена практической части новым change. Отменённые требования выносятся из активных delta specs, чтобы последующий sync/archive не вернул их. Исторические результаты сохраняются как исторические, а невыполненные отменённые задачи обозначаются как заменённые, не как выполненные. Старые changes не архивируются автоматически в рамках этого сброса.

`openspec/config.yaml` обновляется только в отношении новой организации практики, двух текущих веток и локальных текстов. COMMON используется во внутренних артефактах как единый организационный охват, а не заявление о тождестве двух РПД; в студенческой выдаче профилей нет. Профильное содержание лекций и нормативный корпус остаются. Прямое поручение преподавателя заменяет старую модель первого ДЗ; непроверенное соответствие номеру работы РПД не заявляется. При необходимости нормативной трассировки проверяются соответствующие исходные РПД, без импорта дополнительных заданий.

Альтернатива с удалением смешанных changes целиком потеряла бы лекционные решения; сохранение конфликтующих дельт без изменений способно восстановить отменённую практику при будущем архивировании.

### 5. Переименовать существующий репозиторий в api-technologies-2026

Целевой адрес — `https://github.com/TheTonyPub/api-technologies-2026`. Перед переименованием проверить доступность имени и записать repository ID и текущие права доступа. Переименовать существующий репозиторий через GitHub, сохранив владельца и приватность; не создавать новый репозиторий и не переносить историю между двумя независимыми проектами.

Локальная папка остаётся `/Users/ripper/projects/api-technologies-code`; её `origin` меняется на `git@github.com:TheTonyPub/api-technologies-2026.git`. Актуальные ссылки в двух README, новых локальных материалах и `openspec/config.yaml` переводятся на новый адрес. Исторические отчёты сохраняют исходное имя в историческом контексте. Содержимое лекций и преподавательский репозиторий остаются вне этой правки.

После переименования проверить прежний repository ID, права, приватность, `main` как default branch и доступ к двум остающимся веткам по новому URL. Не полагаться на перенаправление старого адреса как на способ обновления инструкций.

Альтернатива с новым репозиторием потребовала бы отдельной миграции истории и прав и не соответствует просьбе переименовать существующий.

## Risks / Trade-offs

- Целевое имя занято другим репозиторием → проверить до переименования, не заменять существующий репозиторий; при конфликте сообщить точное препятствие.
- Новые коммиты или PR после исследования → повторно сверить refs, рабочие деревья, PR и защиты; сохранить всё новое до удаления, пересмотреть затронутые операции.
- Случайный commit полных заданий → точечный ignore до авторинга, `git check-ignore`, проверка индекса и точного набора файлов коммита; не использовать общий `git add .`.
- Повторное восстановление старых требований → проверить все затронутые активные дельты и текущий config, не переписывая исторические отчёты.
- Потеря лекций при очистке → сравнить hashes лекционных файлов, assets/attachments и семантические записи лекций манифеста с исходным состоянием; возникающие ссылки на удаляемые ветки отдельно проверить и сообщить, без скрытого редактирования лекций.
- Локальные условия не восстанавливаются из Git → явно выдать пользователю их локальные пути; не обещать Git-backup для игнорируемых файлов.
- Две карточки в YAML ещё не означают публикацию → завершение требует успешного workflow и проверки сайта; при блокировке отчёт оставляет этот этап открытым.

## Migration Plan

1. Обновить исходный снимок двух репозиториев и перечень удаляемых материалов. Зафиксировать пользовательские правки и лекционное содержимое, проверить доступность четырёхстраничного источника. Сохранить и проверить bundle репозитория сдачи.
2. Согласовать действующие старые планы практики и config. Добавить точечные ignore-правила; создать два локальных Markdown, проверить по источнику, обозначить противоречия и легенду `*`.
3. Подготовить две карточки без Markdown; провалидировать publisher и отсутствие полных условий в отслеживаемых изменениях. Подготовить оба README и очистку учебной ветки; проверить свежий отдельный checkout.
4. Проверить целевое имя, переименовать существующий GitHub-репозиторий в `api-technologies-2026`, проверить repository ID/доступ и обновить локальный `origin`. Опубликовать изменения README/учебной ветки с новыми ссылками и проверить refs по новому адресу. После повторной проверки исходных SHA удалить восемь согласованных remote/local веток, сохранить `main` основной и проверить точное совпадение двух остающихся head SHA.
5. Отправить только необходимые отслеживаемые изменения курса через существующий процесс `courses/api-technologies`; проверить успешную публикацию и две недоступные карточки. Не смешивать ранее существующие изменения архива лекции 1 с коммитом этой задачи.
6. Зафиксировать проверки содержимого, сохранения лекций, публикации и Git. Отдельно сообщить локальные пути материалов и любые непроверенные пункты.

Восстановление имени при необходимости: проверить доступность прежнего имени, переименовать тот же репозиторий обратно и согласованно вернуть `origin` и актуальные ссылки; если имя занято, не заменять чужой репозиторий. Удалённые refs восстанавливаются из проверенного bundle; изменения содержимого отменяются отдельными revert-коммитами. Карточки откатываются возвратом прежнего манифеста с повторным штатным publish. Массовый reset пользовательского дерева не используется. Восстановление после фактической ошибки выполняется по необходимости, не как обязательный учебный тест.

## Уточнение при реализации

Publisher требует уникальный sortOrder для всех видов материалов: лекция сохраняет 1, семинар получает 2, ДЗ — 3. Нумерация семинара в UI определяется положением внутри раздела; для ДЗ используется название «ДЗ 1. Архитектура командного проекта». Локальные необъявленные Markdown сохраняют учебный номер 001; перед будущим объявлением их в манифесте имя потребуется согласовать с sortOrder. Это не меняет учебное содержание или доступность карточек.

## Context

В репозитории уже существуют два полных внутренних сценария лекций, но нет студенческих семинаров, домашних заданий и исполняемого учебного контура. Оба РПД совпадают по общему API-ядру первых четырёх лекций, но используют разные предметные области и компетенции. Практические встречи 1–6 соответствуют пяти нормативным работам: работа № 5 длится четыре часа и делится на две встречи. Домашние задания в РПД не выделены как отдельная категория и могут только поддерживать те же 12 практических результатов.

Модель публичного выпуска двух профилей не решена. Поэтому change может создать внутренние teacher scripts и student-ready материалы, но не меняет allowlist `course.yaml`.

## Goals / Non-Goals

**Goals:**

- завершить непрерывную преподавательскую последовательность лекций 1–4;
- связать объяснение с воспроизводимым кодом и наблюдаемыми HTTP-сценариями;
- дать шесть полноценных семинарских встреч и пять связанных ДЗ для работ № 1–5;
- сохранить общее ядро и нормативно раздельные траектории `PRB` и `SII`;
- обеспечить согласованность prose, контрактов, клиентов, reference API и критериев приёмки;
- оставить созданные student-facing материалы непубликуемыми до отдельного профильного решения.

**Non-Goals:**

- создавать полные студенческие версии лекций, краткие конспекты или презентации;
- реализовывать практические работы № 6–12, кейсы, контрольные работы или итоговый тест;
- преподавать CMake, библиотеки C++-клиента или конкурентность до лекции № 5;
- строить production-сервис, подключать реальные базы, брокеры, модели, GPU или внешние endpoints;
- выбирать модель публикации PRB/SII или менять `course.yaml`.

## Decisions

### 1. Два новых сценария продолжают существующий единый teacher-script формат

Лекции создаются как `lectures-teacher/003_integration-styles-api.md` и `lectures-teacher/004_python-api-services-fastapi.md`. Они повторяют каркас лекций 1–2: scope, литература, непрерывный тайминг 0–90, подробные блоки, демонстрация, взаимодействие, ошибки, итог, мост к практике, покрытие РПД и карта источников.

Альтернатива — четыре отдельных профильных файла — увеличила бы дублирование общего материала и риск расхождения контрактов.

### 2. Каждая лекция имеет наблюдаемую вертикальную демонстрацию

Лекция 1 показывает путь запроса через контрактную границу; лекция 2 — протокольную семантику успешного и ошибочного вызова; лекция 3 — представление одного сценария разными стилями; лекция 4 — последовательную сборку FastAPI-сервиса. Встроенные фрагменты остаются читаемыми в тексте, а исполняемые версии и README размещаются в `attachments/first-four-lectures/`.

Для `PRB` клиентские примеры пишутся на Python. Для `SII` в лекциях 1–3 допускается готовый C++-клиент преподавателя, но он не становится студенческим пререквизитом. В лекции 4 сервер написан на Python/FastAPI для обеих групп, поскольку это общая нормативная тема; различается предметный контракт.

### 3. Профили используют параллельные, но не искусственно универсальные домены

`PRB` ведёт сквозной сценарий прогноза спроса или урожайности с длительным расчётом и интеграцией бизнес-систем. `SII` ведёт сценарий инференса компьютерного зрения с запросом, статусом, результатом и возможным потоком событий. Общими остаются форма ошибки, принципы версионирования, request correlation и критерии технической сверки.

Один универсальный payload отклонён: он скрыл бы различия между табличным прогнозом и инференсом изображения.

### 4. Лекция 3 сравнивает четыре стиля, но исполняет только минимально полезные срезы

Все четыре стиля получают контрактную форму и разбор отказов. Полностью воспроизводимый путь обязателен для REST и одного профильного альтернативного стиля: event-driven или long-running operation для `PRB`, gRPC или WebSocket для `SII`. Остальные варианты показываются через компактный контракт и трассу сообщений, чтобы 90 минут не превратились в обзор четырёх фреймворков.

Каждая рекомендация сопровождается предпосылками нагрузки; заявления о превосходстве без latency/throughput/операционного контекста запрещены.

### 5. Шесть семинаров реализуют пять нормативных работ

Планируемые файлы:

- `seminars/001_api-scenarios-and-context.md` — ПР № 1;
- `seminars/002_rest-openapi-contract.md` — ПР № 2;
- `seminars/003_http-api-diagnostics.md` — ПР № 3;
- `seminars/004_integration-style-selection.md` — ПР № 4;
- `seminars/005_fastapi-service-foundation.md` — ПР № 5, часть 1;
- `seminars/006_fastapi-validation-openapi.md` — ПР № 5, часть 2.

Каждый файл содержит `COMMON`-инструкции и явно взаимоисключающие `PRB`/`SII` варианты. Семинар 6 принимает один накопительный репозиторий работы № 5, а не новую работу.

### 6. Пять ДЗ являются накопительным продолжением работ № 1–5

Планируемые файлы:

- `homeworks/001_api-scenarios.md`;
- `homeworks/002_rest-openapi-contract.md`;
- `homeworks/003_http-api-diagnostics.md`;
- `homeworks/004_integration-style-decision.md`;
- `homeworks/005_fastapi-service.md`.

ДЗ последовательно уточняют одну профильную предметную область: контекст → контракт → наблюдаемое поведение → архитектурный выбор → прототип. В критериях различаются нормативный результат РПД и авторская методическая детализация. Домашняя работа не получает отдельные часы или новый номер практики.

### 7. Reference API предшествует студенческой реализации сервера

Для семинаров 2–3 предоставляется локальный reference API с фиксированными успешными и ошибочными сценариями. Это устраняет циклическую зависимость: студенты исследуют HTTP до того, как строят FastAPI-сервис на семинарах 5–6. Затем тот же наблюдаемый контракт служит ориентиром для собственного прототипа, но готовое решение работы № 5 студентам не выдаётся.

Стартовые файлы разделяются на демонстрацию преподавателя, student starter и эталонные acceptance-сценарии, чтобы не раскрывать скрытые ответы в студенческом Markdown.

### 8. Проверка выполняется по четырём независимым контурам

1. Нормативный: номер, часы, компетенции и профиль сверяются с соответствующим РПД и производным планом.
2. Контрактный: prose, HTTP, OpenAPI, данные и код сверяются по paths, methods, schemas, required fields, statuses, errors и versions.
3. Воспроизводимость: Python и C++ примеры запускаются по README; фиксируются команды, версии, ожидаемый вывод и CPU-only ограничения.
4. Безопасность и публикация: выполняется поиск секретов и реальных данных; `course.yaml` остаётся неизменным.

## Risks / Trade-offs

- [Смешение пяти работ и шести семинаров] → в заголовках и критериях семинаров 5–6 повторять «ПР № 5, часть 1/2» и принимать один итоговый артефакт.
- [Слишком ранний C++ отвлекает от API] → использовать его только как готовую профильную демонстрацию преподавателя до лекции № 5; семинары 1–6 не требуют написания C++.
- [Лекция 3 перегружена технологиями] → исполнять REST и один профильный альтернативный стиль, остальные проверять на уровне контракта и message trace.
- [Reference API превращается в готовое решение ПР № 5] → отделить наблюдаемое поведение от исходника student task и использовать другой минимальный внутренний состав реализации.
- [Общие файлы заставляют студента читать чужой профиль] → дать короткий общий блок и самостоятельные маркированные маршруты `PRB`/`SII`; перед публикацией повторно оценить разделение по веткам.
- [OpenAPI и код расходятся при редактуре] → использовать одну coverage matrix и запускать контрактные проверки после каждого содержательного изменения.
- [Новые student-facing файлы случайно публикуются] → не менять `course.yaml` и проверить отсутствие всех новых путей в publication plan.

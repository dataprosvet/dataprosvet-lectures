## Purpose

Определить второе командное домашнее задание ПРБ как самостоятельное проектирование согласованного HTTP/REST API после лекции 2 и до следующего семинара.

## ADDED Requirements

### Requirement: Homework follows lecture two and continues the team case

`homeworks/002_team-rest-api-design.md` SHALL задавать работу после лекции 2 до следующего семинара с сохранением команды и назначенного кейса ДЗ 1. Scope SHALL быть PRB; связь с темой 1.2 и ПР 2 SHALL описываться как проверенная по источнику методическая адаптация, а не автоматическая эквивалентность. Преподавательская источниковая карта SHALL находиться в `lectures-teacher/seminars/002_architecture-to-http.md`. Задание SHALL указывать необходимые знания HTTP/REST/JSON/OpenAPI и ссылки на реально доступные материалы без выдуманной даты или несуществующего файла лекции.

#### Scenario: Begin homework after the lecture
- **WHEN** команда приступает к ДЗ 2 после лекции
- **THEN** она продолжает свой кейс и архитектуру ДЗ 1, понимает ожидаемые результаты и срок относительно следующего семинара.

### Requirement: Design a coherent REST API for core scenarios

Команда SHALL определить внешнюю границу своего API, потребителей, ресурсы и операции для основных сценариев своего кейса. Задание MUST NOT ограничиваться одной произвольной карточкой запроса и MUST NOT требовать искусственного числа endpoint или полного CRUD для каждой сущности. Операции SHALL быть связаны с требованиями; фоновая обработка и внешние зависимости SHALL быть объяснены без обязательного проектирования чужих API и всех внутренних интеграций.

#### Scenario: Review API coverage
- **WHEN** преподаватель сопоставляет проект API с назначенным кейсом
- **THEN** основные пользовательские сценарии имеют операции, а требования вне HTTP-границы объяснены; качество не оценивается количеством endpoint.

### Requirement: Specify HTTP semantics and data contracts

Для каждой операции результат SHALL задавать метод и путь, path/query-параметры, необходимые заголовки, тело при наличии, обязательность и ограничения полей, успешные статусы и ответы, применимые ошибки в едином формате. Примеры SHALL использовать синтетические данные. Выбор методов SHALL учитывать их безопасность и идемпотентность; фильтрация, пагинация и асинхронный результат SHALL описываться при необходимости сценария. Выбор ресурсов SHALL основываться на целях потребителей.

#### Scenario: Inspect an operation
- **WHEN** проверяющий читает любую описанную операцию
- **THEN** он может составить корректный запрос, определить допустимый ответ и хотя бы один применимый ошибочный случай без догадок о типах и обязательных полях.

### Requirement: Deliver a validated OpenAPI contract

Сдача SHALL содержать `api-design.md`, `openapi.yaml` с явно закреплённой OpenAPI 3.1.0 и примерами, состав команды, кейс, ссылку на архитектуру ДЗ 1 и GitHub pull request с итоговым commit SHA. Контракт SHALL описывать все проектируемые операции и проходить совместимую проверку структуры и ссылок; примеры SHALL соответствовать схемам. Задание SHALL давать воспроизводимую инструкцию проверки и незаполненный каркас из `attachments/seminar-002/openapi-template.yaml` без решения командного кейса.

#### Scenario: Validate a submission without a server
- **WHEN** команда сдаёт описание и OpenAPI с корректными ссылками, схемами и примерами
- **THEN** проверяющий может проверить контракт без запуска реализации; отсутствие командного сервера не является нарушением.

### Requirement: Preserve case constraints without overgeneralization

Проект SHALL сохранять существенные ограничения своего кейса из ДЗ 1 и различать требования, проектные решения и непроверенные предположения о производительности. Банковский пример получения готового прогноза MUST NOT автоматически подменять online-цикл антифрода или требования NRT серверного прогноза. От студентов MUST NOT требоваться доказательство production SLA без реализации и измерений.

#### Scenario: Review the antifraud variant
- **WHEN** команда проектирует антифрод API
- **THEN** описание учитывает исходный цикл проверки транзакции с ограничением 100 мс, а не заменяет его банковским чтением готового недельного прогноза.

### Requirement: No mandatory table or implementation

Таблица интерфейсов, реализация сервера, обучение модели и развёртывание MUST NOT быть обязательными результатами ДЗ 2. Понятные диаграммы и контракт SHALL быть достаточны без дополнительной таблицы. При сложной архитектуре таблица SHALL оставаться добровольной.

#### Scenario: Evaluate a complete design-only submission
- **WHEN** работа содержит согласованное описание, OpenAPI и примеры, но не содержит таблицы и серверного кода
- **THEN** эти отсутствующие элементы не снижают оценку и не препятствуют приёмке.

### Requirement: Local authoring and safe handoff

Полный текст ДЗ 2 SHALL оставаться локальным с точечным Git-ignore; `course.yaml` и ДЗ 1 MUST NOT изменяться. README комплекта SHALL описывать единое продолжение семинара и ДЗ; отдельная homework-ветка MUST NOT вводиться. Будущий учебный перенос SHALL использовать одну ветку `seminar/02-architecture-to-http` только после отдельной разрешённой публикации; несуществующая удалённая ссылка MUST NOT выдаваться за действующую.

#### Scenario: Deliver the local homework material
- **WHEN** автор завершает change без публикации
- **THEN** полный текст доступен локально и исключён из коммитов, требования сдачи ясны, а README не ссылается на несуществующую опубликованную ветку.

### Requirement: GitHub homework submission

ДЗ 2 SHALL сдаваться через GitHub: в репозитории команды с доступом преподавателя, через ссылку на pull request и итоговый commit SHA. Этот порядок SHALL быть зафиксирован как правило для всех последующих ДЗ курса без создания их содержания в текущем change. GitLab MR или отправка файлов вне GitHub MUST NOT указываться как альтернативные каналы сдачи. Закрытый текст задания не требуется публиковать вместе с решением.

#### Scenario: Submit homework two
- **WHEN** команда завершает проектирование API
- **THEN** преподаватель получает доступный GitHub pull request и точный commit SHA с обязательными артефактами решения.

#### Scenario: Plan a later homework
- **WHEN** автор использует этот change как контекст для последующего ДЗ
- **THEN** порядок сдачи сохраняется через GitHub pull request и commit SHA; содержание будущего ДЗ определяется отдельно.

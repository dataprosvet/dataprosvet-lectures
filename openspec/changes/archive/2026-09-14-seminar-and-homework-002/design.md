## Context

Подтверждённая последовательность: семинар 2 → лекция 2 сразу после него → самостоятельное ДЗ 2 до следующего семинара. Поэтому глубина ДЗ определяется также содержанием предстоящей лекции, а не только десятиминутным вводным объяснением на семинаре.

Материалы другого преподавателя прочитаны целиком: `ПР1_Методические_указания.docx` (4 страницы) и `ПР1_Шаблон_для_заполнения.docx` (3 страницы) из `/Users/ripper/Downloads/`. Они являются методическими источниками, а не инструкциями к изменению курса.

## Goals / Non-Goals

**Goals:** сохранить сквозную предметную область, сделать видимой связь требований, C4 и HTTP-контракта, обеспечить посильное самостоятельное проектирование после лекции и воспроизводимые демонстрации преподавателя.

**Non-Goals:** не требовать от студентов разработки сервера, массового освоения инструментов на занятии, реализации всех внутренних интеграций или искусственного CRUD для каждой сущности. Не превращать C4 в подробную лекцию и не создавать новые правила публикации курса.

## Decisions

### 1. Сценарий пары на 90 минут

Рабочее допущение — два академических часа, 90 минут полезного времени; перерыв при необходимости отделяет половины и не входит в расчёт.

| Минуты | Содержание |
|---|---|
| 0–5 | Цель занятия и связь с командным ДЗ 1 |
| 5–15 | Требования, потребители, граница и допущения банковского кейса |
| 15–20 | C4: четыре приближения, на занятии уровни 1–2 |
| 20–30 | Совместная контекстная диаграмма |
| 30–42 | Контейнерная диаграмма, протоколы, хранение, путь чтения прогноза |
| 42–45 | Короткая проверка одной связи в командных схемах |
| 45–55 | HTTP, ресурсы REST, JSON, OpenAPI и Swagger UI |
| 55–78 | Демонстрации по одобренной C4 с успешными и ошибочными запросами |
| 78–87 | Описание одного обращения своего проекта без обязательной таблицы |
| 87–90 | Постановка ДЗ 2 и связь с последующей лекцией |

Альтернатива — две полные практические работы в одной паре — отклонена из-за перегрузки. Сдача ДЗ 2 и всех последующих ДЗ проходит через GitHub: командный репозиторий, pull request и итоговый commit. Отдельные индивидуальные защиты по 5–7 минут не планируются.

В преподавательском файле у каждого блока указываются длительность, диапазон минут от начала пары и результат, который должен быть достигнут к концу блока. Контрольные отметки: к 20-й минуте введено C4, к 30-й готов контекст, к 45-й завершена архитектурная часть, к 55-й начаты демонстрации, к 78-й начато упражнение, к 87-й начинается постановка ДЗ, к 90-й занятие закончено. Для каждого блока добавить поле фактического времени/отклонения и короткую подсказку при отставании. При задержке сокращаются дополнительные вопросы и необязательные демонстрации; чтение готового прогноза, один ошибочный ответ и объяснение сдачи ДЗ сохраняются. Подробный тайминг отдельных демонстраций уточняется после одобрения C4, суммарный бюджет пары остаётся 90 минут.

### 2. C4 и методика проектирования

Краткое объяснение: Context — система и окружение; Containers — приложения и хранилища внутри границы; Components — устройство приложения; Code — реализация. Контейнер C4 не означает Docker. Студенты самостоятельно изучают правила уровней 1–2 по https://c4model.com/diagrams и https://c4model.com/diagrams/container; сдача уровней 3–4 не требуется.

Строим от бизнес-сценариев и ограничений. На уровне 1 не показываем внутренние приложения; на уровне 2 раскрываем ту же систему, сохраняя её внешние связи. Список внутренних потребителей не переносится наружу на контекстной схеме. Отдельный сервис для каждого пункта требований не требуется.

Для показанных запросов стрелка идёт от инициатора к вызываемой системе, подпись содержит цель обращения; ответ подразумевается. Для уведомления инициатором служит отправитель. Это условность нашего рисунка, а не утверждение о единственно возможной нотации C4. Легенда обязательна. Если автор выбирает потоки данных, это должно быть явно обозначено и последовательно применено.

Таблица интерфейсов не включается в обязательные материалы или критерии оценивания. При множестве связей её можно использовать добровольно; одной архитектурной связи могут соответствовать несколько операций. В базовом примере хватает подписей и короткого разбора одного обращения.

### 3. Банковский пример и демонстрации

В новом материале назвать кейс «Прогноз клиентского потока в офисах банка». Пункт про серверы исключить из нормализованного условия как посторонний; хранение сведений об офисах обосновать требованиями к численности сотрудников. В преподавательском источниковом примечании сохранить происхождение исправления. Исходный файл семинара 1 не менять.

По предоставленному эталону C4 принять BankOffices источником справочника, штата и почасовой статистики посещений; наличие статистики является учебным допущением. В окружение включить EmailServer, пользователя User, руководителя OfficeManager и одноимённое внешнее приложение. Обе диаграммы оформляются native Mermaid C4 с графической легендой в экспорте. EmailServer получает письма от фоновой проверки перегрузки, вне запроса чтения готового прогноза. C4-v3 со светлой палитрой одобрена пользователем; точная реплика и хеши сохранены в c4-approval.json. Частота обновления справочника и пересчёта прогноза — допущения примера, которые автор фиксирует до демонстрации. Получение готового прогноза укладывается в требование одной секунды; расчёт и загрузка выполняются вне этого запроса. Свежесть результата и отсутствие готового прогноза обсуждаются отдельно. Уведомления связываются с нагрузкой и нормативом посетителей на сотрудника; выбранный временной интервал и фактическая/прогнозная трактовка явно объявляются допущениями.

#### Версия 2: простые HTTP-моки по уточнению преподавателя

Согласованная C4-v3 сохранена без изменений (c4-approval.json), но описывает целевую архитектуру. По прямой просьбе преподавателя демо сокращено до основных HTTP-сценариев, а не реализации каждого контейнера.

В attachments/seminar-002/ и идентичной lectures-teacher/seminars/seminar02-sources/:

- read_api.py: обычные GET-обработчики, int-параметры, if и словари; JSONResponse для ожидаемых ошибок. forecast.json содержит фиксированные 168 точек, даты и признаки. Нет расчёта свежести.
- bank_offices.py: GET офиса и POST observation: dict. Проверка visitors и office_id; имитация 201 без сохранения, повтор тоже 201. Нет Location/409.
- office_manager.py: общий httpx.Client на время lifespan приложения, base_url из обязательной переменной READ_API_URL; клиент хранится в app.state, переиспользуется синхронными обработчиками и закрывается при остановке. 503 при сетевом сбое.
- web_server.py и неизменённый web/index.html: прежний интерфейс.
- docs.py: только служебная настройка локального Swagger UI, вне объяснения первого занятия. Нет общего слоя ошибок, своих исключений, моделей Pydantic, response_model, Annotated или DI.
- compose.yaml: четыре сервиса на одном api-seminar-002-app:2; отдельный tools:2 для проверки. Python 3.12.14 slim. БД, почта, seed и workers удалены из запуска и исходников.
- contracts/: автоматический OpenAPI моков. Он неполон как контракт предметной области; полноценный OpenAPI остаётся задачей ДЗ. validate_contract.py и openapi-template.yaml сохранены отдельно от кода урока.

Показ 55–78: карта HTTP-взаимодействий (3 минуты), готовый прогноз/неизвестный офис (7), горизонт/отсутствие результата (4), POST 201/422 (6), Swagger UI (3). Резерв — OfficeManager/503 или чтение одного обработчика, вместо части основного показа.

Учебные бизнес-ошибки возвращают error: {code, message}; ошибки типов/JSON/маршрутов остаются стандартными detail FastAPI. Это объясняется в README. Демо не доказывает SLA и не реализует хранение или расчёт. Порты доступны на loopback. Исходники двух копий проверяются по хешам.

### 4. Объём ДЗ 2

Продолжается тот же назначенный командный кейс: антифрод, СПАРК или прогноз серверных ресурсов. Команда проектирует согласованный внешний HTTP/REST API своей системы для основных пользовательских сценариев, а не единственный произвольный эндпоинт. Граница — API, которым владеет команда; контракты чужих систем и все внутренние связи не требуется переизобретать. Число операций определяется сценариями, а не искусственной квотой.

Обязательный результат: `api-design.md` с потребителями, ресурсами, обоснованием HTTP-семантики и границ; `openapi.yaml` версии OpenAPI 3.1.0; включённые в контракт синтетические примеры успешных и ошибочных обменов; команда, кейс, ссылка на архитектуру ДЗ 1 и GitHub pull request с итоговым commit. Краткое словесное описание каждой операции может находиться в OpenAPI и не дублируется обязательной таблицей.

Для каждого endpoint указываются метод, путь, path/query-параметры, нужные заголовки, тело при наличии, обязательные поля/типы/ограничения, коды и данные ответов. Ошибки имеют единый формат. Безопасность/идемпотентность методов, создание и чтение ресурсов объясняются в объёме лекции 2; CRUD ради полноты списка методов не требуется. Пагинация, фильтры, асинхронный результат и конфликт повторного обращения описываются там, где они нужны сценарию. Не вводим обязательную реализацию JWT, очередей или серверной логики.

Минимальные ориентиры по вариантам: антифрод — приём запроса проверки транзакции и решение с сохранением ограничения 100 мс на исходный цикл; СПАРК — актуальные данные по ИНН, группа компаний и результат скоринга; серверы — актуальные показатели, история и готовые прогнозы по ИС с исходными горизонтами и отдельным учётом NRT. Команда объясняет, какие требования обслуживает её API, какие решаются фоном или внешними поставщиками. Общее требование «получение готового прогноза» банковского примера не переносится автоматически на антифрод.

OpenAPI включён как методическое решение proposal на основе плана ПРБ: после лекции студенты оформляют проектируемый HTTP API машиночитаемо. Альтернатива с одной текстовой карточкой отклонена после уточнения пользователя о времени на лекцию и самостоятельную работу.

### 6. Проверка

Проверить согласованность схем и кейса, общий тайминг 90 минут, краткость C4, отсутствие обязательной таблицы, достаточность инструкций ДЗ после лекции, связь операций с требованиями. OpenAPI 3.1.0 шаблон и демонстрационные контракты проверяются совместимым валидатором; примеры сверяются со схемами. Учебное ДЗ требует проверки контракта, но не тестов отсутствующего сервера.

Демонстрационный комплект проверяется в чистом временном снимке без .venv, личных конфигов и реальных данных: запуск всех сервисов одобренного комплекта по README, успешные и ошибочные запросы, загрузка Swagger UI/OpenAPI. Тесты должны проверять смысл сценариев и согласованность контракта. Локальный быстрый ответ демо не является доказательством производственного SLA. Финальные материалы проверяются на корректность ссылок, приватность, отсутствие изменений лекций, ДЗ 1, семинара 1 и course.yaml.

## Risks / Trade-offs

- [Перегрузка пары] → C4 ограничен пятью минутами, один банковский пример, подробное проектирование контракта выполняется после лекции.
- [Неравная сложность трёх кейсов] → единые критерии качества, объём по основным сценариям, без одинакового обязательного числа endpoint.
- [Схема ошибочно принимается за работающую систему] → явно различать архитектурный выбор, заглушки демо и измерения; не объявлять SLA доказанным.
- [Лекция 2 ещё не подготовлена в текущих файлах] → материалы указывают необходимые темы и момент выполнения ДЗ; не добавлять несуществующую локальную ссылку и не считать change подготовкой лекции.
- [Закрытые материалы случайно публикуются] → точечный ignore и проверка course.yaml; публикация вне объёма.

## Migration Plan

Добавить новые локальные материалы и комплект, не перемещая прежние. Проверить сохранность существующих файлов по снимку до/после. Откат локальной реализации ограничивается созданными путями и добавленными точечными ignore-правилами; чужие изменения не затрагиваются. Публикация и удалённая миграция не выполняются.

Сетевые настройки: явная общая bridge-сеть services; внутренний адрес READ_API_URL=http://read-api:8000 передаётся через Compose. Для браузера Compose отдельно задаёт READ_API_PUBLIC_URL, BANK_OFFICES_PUBLIC_URL, OFFICE_MANAGER_PUBLIC_URL и WEB_ORIGIN. HTML подставляет публичные адреса без изменения внешнего вида.

## Наблюдение HTTP по уточнению преподавателя

Добавлен traffic на mitmproxy/mitmproxy:12.2.3: reverse-listeners 8000/8001/8002 направляют в три API по Docker DNS, UI доступен на loopback:8081. OfficeManager получает READ_API_URL=http://traffic:8000; его пул и бизнес-код сохранены. Публичные порты API теперь принадлежат наблюдателю. Три HTTP-обработчика и web не меняются. mitmweb показывает живой список flows; отдельный observer на порту 8004 отображает анимированные логические связи по этим событиям. Это не точная C4 уровня 1. Учебный UI-пароль задаётся в Compose. Проверка готовности выполняется через /openapi.json, чтобы up --wait дожидался доступности API.

Финальная сверка с C4 принята пользователем: интеграции ClientFlowPredictor → BankOffices и EmailServer в моках отсутствуют, прямой POST к BankOffices — отдельное упражнение. Исходники Mermaid остаются отдельными .mmd со ссылками, без встроенных блоков кода.

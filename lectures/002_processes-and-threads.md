# Процессы и потоки

Лекция 2: абстракция выполняющейся программы, состояния процесса, таблица процессов и модель потоков (threads).

## Процесс

Процесс (process) — абстракция выполняющейся программы. Процессы позволяют (псевдо)параллельную работу даже при одном CPU.

Примеры: веб-сервер обслуживает много запросов разных пользователей одновременно; на ПК одновременно работают почтовый клиент, антивирус, текстовый процессор.

В системе мультипрограммирования CPU быстро переключается между процессами. В каждый момент выполняется только один процесс; за короткий промежуток он может поработать над несколькими. Эта иллюзия параллелизма — **псевдопараллелизм (pseudo-parallelism)**.

## Модель процессов

Всё исполняемое ПО, иногда включая OS, организовано в набор последовательных процессов. Процесс — экземпляр выполняющейся программы, включая текущие значения счётчика команд, регистров и переменных.

Концептуально у каждого процесса свой виртуальный CPU. На деле реальный CPU переключается между процессами — это и есть мультипрограммирование.

Физический счётчик команд (PC) один. Когда процесс работает, его логический PC загружается в реальный. Когда квант закончен, физический PC сохраняется как логический PC процесса в памяти.

![[assets/lecture-002-process-switch.png]]

Четыре программы в памяти, один PC, переключения (process switch).

![[assets/lecture-002-four-pcs.png]]

Концептуально у каждого процесса свой поток управления и свой логический PC; они работают независимо. В каждый момент активна только одна программа.

Разница между программой и процессом:

- программа — набор инструкций, сама ничего не делает (как рецепт в книге);
- процесс — деятельность: программа, ввод, вывод и состояние (как повар, следующий рецепту).

Если программа запущена дважды — это два разных процесса.

## Создание и завершение

Четыре основных события, порождающих процессы:

- инициализация системы;
- системный вызов создания процесса от уже работающего процесса;
- запрос пользователя на новый процесс;
- запуск пакетного задания (batch job).

В UNIX создание — один вызов `fork`: точный клон вызывающего процесса. У родителя и потомка одинаковые образ памяти, строки окружения и открытые файлы. Обычно потомок затем вызывает `execve` (или аналог), меняет образ памяти и запускает новую программу. Между `fork` и `execve` потомок может менять file descriptors — для перенаправления stdin, stdout и stderr.

Типичные причины завершения:

- нормальный выход (добровольно);
- выход по ошибке (добровольно);
- фатальная ошибка (невольно);
- убийство другим процессом (невольно).

## Иерархии процессов

В части систем родитель и потомок остаются связанными; потомок может создавать процессы дальше. В UNIX процесс со всеми потомками образует **process group**. Сигнал с клавиатуры доставляется всем членам текущей группы, связанной с клавиатурой. Процесс может перехватить сигнал, игнорировать его или быть убитым (действие по умолчанию).

## Состояния процесса

Три базовых состояния:

| Состояние | Смысл |
|---|---|
| Running | сейчас использует CPU |
| Ready | готов к запуску; временно остановлен, чтобы дать CPU другому |
| Blocked | не может идти, пока не случится внешнее событие |

Процесс блокируется, когда логически не может продолжать (ждёт ввод, которого ещё нет). Другая ситуация — когда OS решает на время отдать CPU другому процессу.

![[assets/lecture-002-three-states.png]]

Переходы:

1. **Running → Blocked.** OS обнаруживает, что процесс сейчас не может продолжать. В части систем процесс выполняет системный вызов вроде `pause`; в UNIX и других системах блокировка бывает автоматической.
2. **Running → Ready.** Планировщик решает отдать CPU другому процессу.
3. **Ready → Running.** Снова очередь первого процесса: остальные уже достаточно поработали.
4. **Blocked → Ready.** Произошло ожидаемое событие (например, пришёл ввод). Если никто другой сейчас не работает, сразу сработает переход 3 — процесс начнёт выполняться.

Нижний слой процессной OS обрабатывает прерывания (interrupts) и планирование. Выше — последовательные процессы.

Более детальный взгляд:

- процесс выполняется в пользовательском режиме (user mode);
- процесс выполняется в режиме ядра (kernel mode);
- не выполняется, но готов — как только выберет планировщик;
- процесс спит (sleeping) — сам ушёл в сон, например ждёт завершения I/O.

![[assets/lecture-002-user-kernel-states.png]]

## Девять состояний UNIX

Полный список:

| Состояние | Смысл |
|---|---|
| User running | выполняется в user mode |
| Kernel running | выполняется в kernel mode |
| Ready to run in memory | не выполняется, но готов; ядро может запланировать его |
| Asleep in memory | спит и находится в основной памяти |
| Ready to run swapped | готов, но swapper (process 0) должен сначала подкачать процесс |
| Sleep, swapped | ждёт события и вытеснен во вторичную память |
| Preempted | возвращается из ядра в user mode, но ядро вытесняет его и делает переключение контекста |
| Created | только создан; ещё не ready и не sleeping (начальное для всех, кроме process 0) |
| Zombie | выполнил `exit` и уже не существует, но оставил запись для родителя |

![[assets/lecture-002-unix-states.png]]

Типичный путь:

1. Вход в модель в состоянии **created** (после `fork` у родителя). Затем — одно из «ready to run» (в памяти или swapped).
2. Допустим, **ready to run in memory**. Планировщик выберет процесс → **kernel running** и доделает свою часть `fork`.
3. Завершив системный вызов, процесс может перейти в **user running**.
4. Через время системный таймер прерывает процессор → снова **kernel running**.
5. Ядро может запланировать другой процесс → первый уходит в **preempted**. Preempted по сути то же, что ready to run in memory, но важно: в kernel mode процесс вытесняют только перед возвратом в user mode.
6. Системный вызов: user running → kernel running. Если нужен I/O с диска — процесс ждёт → **asleep in memory**. По завершении I/O аппаратура прерывает CPU, обработчик прерываний будит процесс → ready to run in memory.
7. Не все процессы помещаются в основную память; swapper (process 0) вытесняет процесс, чтобы дать место другому из **ready to run swapped**. Процесс снова попадает в ready to run in memory, планировщик выбирает его → kernel running. По завершении — `exit` → kernel running и наконец **zombie**.

## Реализация: таблица процессов и прерывания

OS держит таблицу (массив структур) — **process table**, по записи на процесс (иногда **process control block**, PCB). В записи — состояние процесса: счётчик команд, указатель стека, распределение памяти, статус открытых файлов, учёт и данные планировщика.

С каждым классом I/O связан **interrupt vector** — адрес процедуры обслуживания прерывания. Пример: работает user process 3, приходит прерывание диска:

- аппаратура кладёт на стек PC, PSW и иногда регистры;
- прыжок по адресу из вектора прерываний — дальше всё делает программное обеспечение, в частности interrupt service procedure.

Скелет нижнего уровня OS при прерывании:

1. Аппаратура сохраняет PC и другие данные на стек.
2. Аппаратура загружает новый PC из interrupt vector.
3. Процедура на ассемблере сохраняет регистры.
4. Процедура на ассемблере настраивает новый стек.
5. Работает C interrupt service (обычно читает и буферизует ввод).
6. Планировщик решает, какой процесс запускать дальше.
7. C-процедура возвращается в ассемблерный код.
8. Процедура на ассемблере запускает новый текущий процесс.

## Моделирование мультипрограммирования

Лучшая модель — вероятностный взгляд на загрузку CPU. Процесс долю \(p\) времени ждёт завершения I/O. При \(n\) процессах в памяти вероятность, что все ждут I/O (CPU простаивает), равна \(p^n\).

**CPU utilization** = \(1 - p^n\).

Зависимость загрузки от \(n\) — степень мультипрограммирования.

![[assets/lecture-002-cpu-utilization.png]]

## Потоки

В классических OS у процесса есть адресное пространство (address space) и один поток управления. Часто нужны несколько потоков (threads) в одном адресном пространстве, работающих квазипараллельно — как отдельные процессы, но с общей памятью.

Зачем «мини-процессы» — threads:

- разбиение приложения на последовательные потоки, работающие квазипараллельно, упрощает модель программирования;
- создавать и уничтожать быстрее, чем процессы;
- потоки позволяют перекрывать I/O и вычисления;
- потоки на нескольких CPU дают настоящий параллелизм.

### Текстовый процессор

Три потока: ввод с клавиатуры, форматирование документа, периодическое сохранение на диск. Пока один поток ждёт диск или клавиатуру, остальные продолжают работу.

![[assets/lecture-002-word-processor-threads.png]]

### Многопоточный веб-сервер

Диспетчер принимает сетевое соединение и отдаёт работу worker-потокам. Страницы лежат в общем кэше процесса (user space); ядро обрабатывает сеть и диск.

![[assets/lecture-002-web-server-threads.png]]

Модель позволяет писать сервер как набор последовательных потоков:

- **Dispatcher:** бесконечный цикл — взять запрос и отдать worker.
- **Worker:** бесконечный цикл — принять запрос, проверить кэш; страница есть — отдать клиенту и ждать новый запрос; нет — взять с диска, отдать клиенту, ждать новый запрос.

![[assets/lecture-002-dispatcher-worker.png]]

(a) Dispatcher thread. (b) Worker thread.

Три способа построить сервер:

| Модель | Характеристики |
|---|---|
| Threads | параллелизм, блокирующие системные вызовы |
| Single-threaded process | нет параллелизма, блокирующие системные вызовы |
| Finite-state machine | параллелизм, неблокирующие системные вызовы, прерывания |

## Классическая модель потоков

Модель процесса опирается на два независимых понятия: группировку ресурсов и выполнение. Иногда их полезно разделить — тут появляются потоки. Сначала классическая модель; затем модель потоков Linux, где граница процессов и потоков размыта (эта лекция останавливается на классической).

У процесса есть адресное пространство (текст программы и данные) и другие ресурсы: открытые файлы, дочерние процессы, отложенные alarms, обработчики сигналов, учётная информация. Собранные в процесс, ими проще управлять.

Второе понятие — поток выполнения (thread of execution). У потока есть:

- счётчик команд — какая инструкция следующая;
- регистры — текущие рабочие переменные;
- стек — история вызовов: кадр на каждую вызванную, но ещё не вернувшуюся процедуру.

Из-за сходства с процессами потоки называют **lightweight processes**. **Multithreading** — несколько потоков в одном процессе. У части CPU есть аппаратная поддержка multithreading; переключение потоков занимает наносекунды.

![[assets/lecture-002-processes-vs-threads.png]]

(a) Три процесса по одному потоку. (b) Один процесс с тремя потоками.

| Общее для процесса | Личное для потока |
|---|---|
| адресное пространство | счётчик команд |
| глобальные переменные | регистры |
| открытые файлы | стек |
| дочерние процессы | состояние |
| отложенные alarms | |
| сигналы и обработчики сигналов | |
| учётная информация | |

Как и у однопоточного процесса, у потока есть состояния: **running** (сейчас на CPU), **blocked** (ждёт событие), **ready** (в очереди на запуск), также может быть **terminated**. Переходы те же, что у процессов.

У каждого потока свой стек: кадр на каждую вызванную, но не вернувшуюся процедуру. В кадре — локальные переменные и адрес возврата. Если процедура X вызывает Y, а Y — Z, пока работает Z, на стеке кадры X, Y и Z.

![[assets/lecture-002-thread-stacks.png]]

Потоки усложняют модель программирования:

- если у родителя несколько потоков — должны ли они быть у потомка?
- что, если поток родителя блокирован на `read` с клавиатуры?
- когда введут строку — получат ли оба потока копию?
- что, если один поток закрыл файл, а другой ещё читает?

## Из однопоточного кода в многопоточный

Много программ писали под однопоточные процессы. Перевод в multithreading труден. Ловушки:

- глобальные переменные процесса;
- многие библиотечные процедуры не **reentrant**;
- сигналы (не thread-specific; в user space даже thread-specific сложны);
- управление стеком.

Конфликт потоков из-за глобальной переменной. Поток 1 делает Access и записывает `errno`; поток 2 делает Open и перезаписывает `errno`; поток 1 затем смотрит `errno` — и видит чужое значение.

![[assets/lecture-002-errno-race.png]]

Решения первой проблемы:

- запретить глобальные переменные;
- ввести private global variables на поток;
- библиотека create / set / read threadwide globals, например `create_global("bufptr")`, `set_global("bufptr", &buf)`, `bufptr = read_global("bufptr")`.

![[assets/lecture-002-thread-globals.png]]

У потоков могут быть «личные» глобальные переменные.

Остальные проблемы сложнее. Например, для не-reentrant библиотек: переписать библиотеку или jacket (wrapper) с битом «занято», который не даёт вызвать процедуру, пока бит установлен — сильно режет параллелизм.

Проблемы более или менее управляемы, но показывают: просто «добавить потоки» в существующую систему без серьёзной переработки не выйдет.

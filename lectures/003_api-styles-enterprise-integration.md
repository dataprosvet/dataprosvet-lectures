# Лекция 3. Архитектурные стили API и паттерны корпоративной интеграции

Полный конспект. API-технологии, 2 курс, 3 семестр.

**Цель:** научиться выбирать способ взаимодействия по потребностям потребителя и нефункциональным требованиям, а затем объяснять, как интеграция обрабатывает сбои и повторные операции и как наблюдать за её работой.

Во второй лекции мы познакомились с HTTP, REST, форматами данных и контрактами интерфейсов. Теперь сравним REST с GraphQL, gRPC, WebSocket и событийным обменом, а затем свяжем эти подходы с паттернами интеграции. Сквозной пример — система обработки транзакций: клиент передаёт транзакцию, сервис скоринга оценивает её риск, а другие сервисы получают события обработки.

## 1. Зачем системам разные способы взаимодействия

Разделение системы на сервисы создаёт сетевые границы. Локальный вызов превращается в удалённое взаимодействие с сериализацией, задержками, возможными обрывами связи и независимыми отказами компонентов. Интерфейс должен определять, какие данные пересекают эту границу и на что может рассчитывать вызывающая сторона.

Публичный API мобильного приложения, внутренний вызов скоринга и фоновое уведомление предъявляют разные требования. Мобильному клиенту нужен поддерживаемый и понятный интерфейс; скорингу может требоваться немедленный результат; уведомление часто можно отправить позже. Высокая интенсивность запросов важна для части систем, но миллионы запросов в секунду не являются универсальным требованием бизнеса.

Перед выбором технологии нужно выяснить, кто вызывает сервис, нужен ли результат немедленно, какой объём данных передаётся, должен ли сервер сам отправлять обновления и что произойдёт при недоступности одного из участников.

## 2. REST: ресурсы и стандартное взаимодействие по HTTP

REST организует взаимодействие вокруг ресурсов и их представлений. В HTTP API клиент обращается к ресурсу и использует семантику методов: например, GET для чтения или POST для обработки переданного содержимого. Идентификаторы ресурсов и документированный контракт позволяют отделить потребителя от способов хранения данных и деталей реализации.

REST удобен для внешней интеграции благодаря широкому распространению инструментов HTTP. Ответы, допускающие кэширование, можно сохранять и повторно использовать, сокращая вычисления и трафик. Для этого нужны корректные директивы кэширования и правильная обработка приватных данных.

Две проблемы заставляют искать другие способы формирования ответов:

- **Overfetching — избыточная выборка:** клиент получает ненужные поля. Например, ответ с профилем содержит контактные данные, хотя экран показывает только имя.
- **Underfetching — недостаточная выборка:** одного ответа не хватает. Для заполнения экрана могут понадобиться отдельные запросы транзакции, её счёта и результата оценки риска.

Эти проблемы зависят от устройства эндпоинтов. Их можно решать с помощью представлений для конкретных задач, агрегации или выбора полей. REST не требует использования JSON/XML и не мешает строгой проверке схем через контракт OpenAPI. Архитектурные ограничения REST и выбор формата данных — отдельные решения.

## 3. GraphQL: клиент выбирает поля

GraphQL позволяет клиенту запрашивать поля из типизированной схемы. Сервис обычно предоставляет один HTTP-эндпоинт, например `/graphql`. Схема определяет доступные выборки; свобода клиента остаётся в пределах этого контракта.

Запрос данных пользователя можно записать так:

```graphql
query {
  user(id: "42") {
    name
    email
  }
}
```

Пример ответа:

```json
{
  "data": {
    "user": {
      "name": "Ivan",
      "email": "ivan@example.com"
    }
  }
}
```

Клиент выбирает `name` и `email`, а сервер получает значения этих полей. Вложенные выборки позволяют собрать связанные данные одним клиентским запросом. Операция query читает данные, а mutation выражает операцию изменения. [Документация запросов GraphQL](https://graphql.org/learn/queries/).

Один запрос всё равно может вызвать множество обращений к внутренним сервисам или базе данных. Поэтому GraphQL требует контроля стоимости запросов и продуманной реализации резолверов — функций, получающих значения полей. Выбор меньшего числа полей ответа не обязательно делает выполнение дешевле, а схема не заменяет проверку прав доступа.

## 4. RPC, gRPC и Protocol Buffers

**RPC (Remote Procedure Call)** — удалённый вызов процедур: взаимодействие представляется как вызов удалённого метода с аргументами и возвращаемым значением. **gRPC** — фреймворк для этой модели. Обычно он использует HTTP/2 и Protocol Buffers, а сервисы и сообщения описываются в файлах `.proto`. Сгенерированные клиентские заглушки отправляют вызовы, серверные реализации их обрабатывают. Для удалённых вызовов по-прежнему нужны предельные сроки ожидания и обработка сбоев. [Основные понятия gRPC](https://grpc.io/docs/what-is-grpc/core-concepts/).

В примере пакетного скоринга транзакций используются следующие сообщения. Учебное описание сохраняет поля из презентации и дополняет их определением сервиса:

```proto
syntax = "proto3";

message Transaction {
  string id = 1;
  double amount = 2;
  bool international = 3;
  double merchant_risk = 4;
}

message PredictBatchRequest {
  repeated Transaction transactions = 1;
}

message TransactionPrediction {
  string id = 1;
  double risk_score = 2;
  string risk_label = 3;
}

message PredictBatchResponse {
  repeated TransactionPrediction predictions = 1;
}

service TransactionInference {
  rpc PredictBatch(PredictBatchRequest) returns (PredictBatchResponse);
}
```

Числа идентифицируют поля в передаваемом сообщении. `repeated` объявляет коллекцию. Метод `PredictBatch` принимает одно сообщение с транзакциями и возвращает одно сообщение с прогнозами. Обработчик на Python перебирает `request.transactions`, оценивает каждый элемент и формирует `PredictBatchResponse`.

Схема проверяет структуру, но оставляет открытыми предметные вопросы: валюту и единицы `amount`, смысл `merchant_risk`, допустимые диапазоны оценок и способ представления ошибок отдельных транзакций. Число с плавающей точкой подходит для этого учебного входа модели; реальный платёжный контракт требует явно определённого представления денежных сумм.

Protocol Buffers использует бинарную сериализацию и поддерживает генерацию кода. Для совместимого развития схемы нужны стабильные номера полей, допустимые изменения и резервирование удалённых номеров и имён. Произвольное удаление полей или изменение типов всё равно может нарушить работу потребителей. [Руководство Protocol Buffers для proto3](https://protobuf.dev/programming-guides/proto3/).

Для файла `service.proto` генерацию кода Python можно выполнить командой:

```bash
python -m grpc_tools.protoc -I. --python_out=. --grpc_python_out=. service.proto
```

Команда предполагает, что инструменты компиляции доступны. В исходном примере указан `subprocess.system`, которого нет в модуле Python `subprocess`; команда выше передаёт задуманный шаг генерации без этой ошибки. Генерация создаёт классы сообщений и код для вызова и реализации сервиса, но не сам алгоритм скоринга.

Бинарное кодирование может уменьшить размер сообщений и затраты на сериализацию. Выигрыш зависит от структуры сообщения, среды выполнения, сжатия и нагрузки. Выбор Protobuf сам по себе не гарантирует фиксированного ускорения или универсального уменьшения размера на 60–80%.

## 5. Четыре модели взаимодействия в gRPC

| Модель | Клиент отправляет | Сервер отправляет | Учебный пример |
|---|---|---|---|
| Unary — унарный вызов | Одно сообщение | Одно сообщение | Оценка одной транзакции или одного пакета |
| Server streaming — серверный поток | Одно сообщение | Последовательность сообщений | Подписка на показания датчика |
| Client streaming — клиентский поток | Последовательность сообщений | Одно сообщение | Загрузка наблюдений с получением сводного результата |
| Bidirectional streaming — двунаправленный поток | Последовательность сообщений | Независимую последовательность сообщений | Передача транзакций с одновременным получением оценок |

Это модели обмена сообщениями в рамках одного RPC. Список внутри запроса не превращает вызов в потоковый: `PredictBatch` из примера выше остаётся унарным. Двунаправленные потоки позволяют каждой стороне отправлять сообщения независимо, сохраняя порядок внутри каждого направления. [Типы методов gRPC](https://grpc.io/docs/what-is-grpc/core-concepts/).

## 6. WebSocket: постоянное двустороннее соединение

WebSocket поддерживает передачу текстовых или бинарных сообщений в обоих направлениях по установленному соединению. При рукопожатии HTTP/1.1 клиент отправляет запрос на смену протокола, сервер отвечает `101 Switching Protocols`, после чего стороны обмениваются сообщениями до закрытия соединения. Такой подход подходит для чатов, обновляемых панелей, котировок и других сценариев, где сервер должен отправлять обновления без отдельного запроса опроса.

Накладные расходы кадра невелики. Диапазон 2–10 байт относится к заголовку без клиентского маскирования: маскированные кадры добавляют ещё четыре байта. Протокол уже определяет кадры Ping, Pong и Close. Приложения и библиотеки выбирают правила проверки активности соединения и поведение при переподключении. [RFC 6455 §§5–7](https://www.rfc-editor.org/rfc/rfc6455.html#section-5).

Постоянное соединение занимает ресурсы на протяжении всей своей жизни. При расчёте ёмкости учитывают открытые сокеты, файловые дескрипторы, память, буферы отправки и медленных клиентов. Переподключение поднимает и предметный вопрос: должен ли клиент получить обновления, пропущенные во время обрыва?

WebSocket обеспечивает передачу сообщений, а приложение определяет их типы, правила доступа, подписки и идентификаторы запросов. Например, панель оценки рисков может различать сообщения `subscribe`, `risk_updated` и `error`. Эти имена относятся к прикладному контракту.

Когда клиенты подключены к разным репликам, для доставки обновлений нужному соединению может потребоваться общая маршрутизация или слой обмена сообщениями. HTTP-прокси с поддержкой WebSocket способен обработать смену протокола; балансировка L4 и привязка клиента к одной реплике, или sticky sessions, нужны не всегда. Сама по себе привязка к реплике не восстанавливает потерянное состояние после отказа сервера.

## 7. Событийная интеграция: публикация факта

В событийно-ориентированной архитектуре производитель публикует событие, а потребители реагируют через брокер или шину событий. Событие сообщает о факте, например `TransactionScored` — «транзакция оценена»; команда запрашивает действие, например `ScoreTransaction` — «оценить транзакцию».

Издатели отправляют сообщения в темы, а подписчики получают сообщения из нужных тем. Производителю не требуется напрямую вызывать каждого подписчика. При этом он зависит от контракта событий и инфраструктуры публикации. Потребители зависят от смысла событий, идентификаторов и гарантий порядка, если они предусмотрены.

Производитель может завершить публикацию раньше, чем закончится обработка у потребителей. Однако он может ждать подтверждения приёма от брокера. «Принято брокером» и «обработано всеми подписчиками» — разные этапы.

Сохранение сообщений позволяет продолжить обработку после некоторых сбоев с учётом настроек брокера и сроков хранения. Обратная сторона — отложенная согласованность данных, обработка дублей и более сложная диагностика независимых потребителей. Одного сохранения сообщения недостаточно для гарантии каждого бизнес-эффекта.

## 8. Сравнение по нефункциональным требованиям

Сравним транспорт, формат данных, связанность и модель обмена:

| Подход | Типичные транспорт и данные | Модель взаимодействия | Зависимость от контракта |
|---|---|---|---|
| REST | HTTP; часто JSON | Запрос и ответ для ресурса | Контракт ресурсов и представлений |
| GraphQL | Часто HTTP и JSON | Выбор полей из типизированной схемы | Схема и поведение резолверов |
| gRPC | Обычно HTTP/2 и Protobuf | Вызовы методов и потоки | Определения сервисов и сообщений |
| WebSocket | Установленное соединение; текст или бинарные данные | Постоянный двусторонний обмен | Прикладной протокол сообщений |
| Событийный обмен | Протокол конкретного брокера; JSON/Avro/Protobuf | События или задачи в очереди | Схема событий и правила доставки |

Здесь сопоставляются архитектурные стили, модели запросов, фреймворки и протоколы. Они могут сосуществовать. HTTP/3 может передавать запросы с семантикой REST; протокол брокера отличается от формата его сообщений. Строгая типизация и сильная связанность во время работы — разные свойства: типизированный контракт не обязательно требует одновременного развёртывания производителей и потребителей.

**Задержка (Latency)** — время до определённого результата, например оценки риска. Нужно учитывать передачу по сети, сериализацию, ожидание в очереди и обработку. Быстрое подтверждение брокера не означает быстрого завершения операции. HTTP позволяет переиспользовать соединения, поэтому REST не обязан открывать новую TCP/TLS-сессию для каждого запроса. Безусловного лидера по задержке нет.

**Пропускная способность (Throughput)** — объём работы за единицу времени, например число транзакций или байтов в секунду. Компактное кодирование и пакетная обработка могут помочь. Более крупные пакеты способны увеличить время ожидания. HTTP/2 мультиплексирует потоки, но использует TCP, поэтому потеря пакетов может задержать потоки, разделяющие одно соединение. [RFC 9113 §1](https://www.rfc-editor.org/rfc/rfc9113.html#section-1).

**Масштабируемость (Scalability)** описывает поведение системы при росте числа клиентов и объёма работы. Обработка запросов без скрытого состояния диалога — stateless — облегчает распределение нагрузки, но базы данных и зависимости могут ограничить рост. Долгоживущие соединения требуют продуманного распределения. gRPC может использовать балансировку на стороне клиента или прокси; прокси уровня L7 — один из вариантов. [Балансировка gRPC](https://grpc.io/blog/grpc-load-balancing/).

**Сопровождаемость (Maintainability)** включает документирование контрактов, диагностику сбоев, тестирование взаимодействий и координацию изменений. Привычные инструменты REST могут снизить порог входа. Сгенерированные типы gRPC обнаруживают часть структурных ошибок, но не доказывают правильность бизнес-смысла. Для событийных потоков и постоянных соединений нужно проверять временное поведение и восстановление, а не только содержимое сообщений.

**Совокупная стоимость владения (TCO)** включает вычисления, трафик, память, хранение, эксплуатацию инфраструктуры и работу разработчиков. Уменьшение стоимости передачи сообщений может оказаться полезным, но не перекрыть расходы на брокер или инструменты. Название технологии не определяет итоговый счёт.

Перед выбором нужно превратить приоритеты в измеримые условия. Например, задать ожидаемое число одновременных клиентов, максимальный размер сообщения, задержку завершения p95/p99, допустимые потери или дублирование и бюджет эксплуатации. Сравнительная матрица служит отправной точкой для обсуждения, а не доказательством результатов нагрузочного теста.

## 9. Внешняя интеграция: контракты и обработка сбоев

Внешним API должно быть возможно пользоваться без знания внутренней топологии поставщика. Для этого описывают операции, аутентификацию, авторизацию, ошибки, квоты и политику совместимости. REST/JSON — распространённый выбор; итоговый интерфейс зависит от возможностей партнёра и нагрузки.

Механизмы безопасности решают разные задачи. OAuth 2.0 поддерживает делегированную авторизацию; OpenID Connect добавляет слой аутентификации; mTLS аутентифицирует стороны с помощью сертификатов. Интеграция не обязана использовать все три механизма одновременно. Выбор зависит от модели доверия. [OpenID Connect Core 1.0](https://openid.net/specs/openid-connect-core-1_0.html#Introduction).

Версия может обозначаться в пути, например `/v1/`, или через согласование представлений. Новая метка версии сама по себе не предотвращает несовместимые изменения. Нужно документировать поддерживаемые версии, порядок перехода и прекращения поддержки. OpenAPI и интерактивная документация помогают потребителям понять и проверить контракт.

### Повторные запросы: экспоненциальная пауза и случайный разброс

Временный сбой может оправдывать повторную попытку. Между попытками увеличивают паузу — exponential backoff — и добавляют случайный разброс, или jitter, чтобы клиенты не повторяли запросы одновременно. Ограничивают число попыток и общее время ожидания, а также соблюдают документированные правила повторов сервера.

Таймаут оставляет неопределённость: сервер мог выполнить операцию, но ответ потерялся. Повторять запрос следует только тогда, когда семантика операции или контракт устранения дублей делают повтор безопасным. Слепой повтор платёжного POST может привести к повторному платежу.

### Circuit Breaker — предохранитель

Circuit Breaker временно прекращает обращения к сбоящей зависимости. В состоянии **closed — замкнут** он пропускает вызовы; в состоянии **open — разомкнут** сразу возвращает локальный отказ; в состоянии **half-open — полуоткрыт** разрешает пробные обращения для проверки восстановления. Это защищает локальные ресурсы и избавляет от повторного ожидания заведомо проблемного сервиса. Возвращать кэшированные данные допустимо, только если контракт разрешает их возраст и смысл.

### Ограничение частоты и регулирование потока

Rate limiting ограничивает объём принимаемой работы; throttling регулирует темп её выполнения. Лимиты защищают ресурсы и могут различаться по тарифам. Token Bucket — «корзина токенов» — накапливает токены до заданного предела и допускает ограниченные всплески. Leaky Bucket — «протекающее ведро» — регулирует скорость выхода. Счётчики скользящего окна учитывают недавнее использование по правилам выбранного алгоритма.

HTTP-статус `429 Too Many Requests` указывает на превышение частоты запросов. Ответ может содержать `Retry-After`; этот заголовок не обязателен для каждого ответа 429. [RFC 6585 §4](https://www.rfc-editor.org/rfc/rfc6585.html#section-4).

## 10. API Gateway и Backend-for-Frontend

**API Gateway — API-шлюз** предоставляет клиентам общую точку входа и направляет трафик к сервисам. Типичные общие функции — аутентификация, общие политики доступа, лимиты запросов, журналирование и завершение TLS-соединений. Шлюз может преобразовывать внешний интерфейс HTTP/JSON во внутренние методы gRPC, если такое соответствие явно определено. Предметные сервисы по-прежнему должны обеспечивать принадлежащие им правила доступа.

**Backend-for-Frontend (BFF)** адаптирует данные внутренних сервисов под конкретный клиентский интерфейс. Мобильному экрану может требоваться краткая сводка транзакции, а веб-панели — подробные объяснения риска. Отдельные BFF позволяют собирать эти представления, не заставляя всех потребителей зависеть от одного перегруженного ответа.

| Вопрос | API Gateway | BFF |
|---|---|---|
| Основная ответственность | Общая точка входа, маршрутизация и политики трафика | Сбор данных и формирование ответа под клиента |
| Область применения | Общий периметр сервисов | Конкретный клиентский интерфейс или группа клиентов |
| Пример | Проверить учётные данные и направить `/transactions` | Объединить транзакцию и оценку риска для мобильного экрана |

За эти компоненты часто отвечают соответственно инфраструктурные и продуктовые команды, но распределение ответственности — организационное решение. BFF оправдан различиями потребностей клиентов; создавать его для каждого устройства необязательно.

Агрегация сокращает число сетевых обращений клиента, но добавляет зависимости на стороне сервера. Если BFF вызывает пять сервисов, он должен определить предельное время ожидания и решить, означает ли отсутствие одного результата частичный ответ или отказ всей операции.

## 11. Внутреннее межсервисное взаимодействие

Прямой запрос подходит, когда вызывающей стороне нужен результат для завершения текущей операции. Например, разрешение транзакции может требовать немедленной оценки риска. Асинхронная работа подходит, если обработку можно завершить позже: например, отправить уведомление после выполнения основной операции.

gRPC полезен для типизированных внутренних вызовов, но внутренний REST тоже остаётся допустимым выбором. **Service Discovery — обнаружение сервисов** — находит актуальные адреса через Consul, Eureka, Kubernetes DNS или другие механизмы. Обнаружение сообщает, где находится экземпляр; балансировка определяет, как вызовы распределяются между доступными экземплярами.

Нахождение во внутренней сети не доказывает доверие. Для межсервисного трафика могут применяться идентификация сервисов, шифрование и авторизация. Service Mesh — инфраструктурный слой управления межсервисным обменом — может обеспечивать защиту транспорта и управление трафиком; затраты на его эксплуатацию должны соответствовать потребностям системы.

## 12. Брокеры, гарантии доставки и Transactional Outbox

Очередь накапливает работу во время пика. Производители передают задачи, а обработчики выполняют их с устойчивой скоростью. Если интенсивность поступления постоянно выше скорости обработки, очередь и время ожидания продолжают расти: буферизация не создаёт неограниченную производительность.

| Гарантия | Значение | Следствие для проектирования |
|---|---|---|
| At-most-once — не более одного раза | Сообщение не доставляется повторно; возможна потеря | Подходит только тогда, когда потеря работы допустима |
| At-least-once — не менее одного раза | В пределах определённой гарантии доставка может повторяться | Потребители должны обрабатывать дубли |
| Exactly-once — ровно один раз | Обработка даёт один эффект в определённых границах | Нужно указать участвующие системы и предположения о сбоях |

Транзакции Kafka могут согласовать записи Kafka и позиции чтения потребителей. Платёж во внешней системе требует участия этой системы; одной гарантии брокера недостаточно, чтобы обеспечить единственный платёж. [Семантика доставки Kafka 4.1](https://kafka.apache.org/41/design/design/#message-delivery-semantics).

### Transactional Outbox — транзакционный исходящий журнал

Раздельная запись бизнес-состояния и публикация события создают возможность рассогласования: транзакция базы данных может завершиться успешно, а публикация — нет. Паттерн Outbox записывает бизнес-изменение и исходящее событие в одной транзакции базы данных. Отдельный процесс затем публикует сохранённое событие и отмечает продвижение. После сбоя этот процесс может опубликовать событие повторно, поэтому потребителям всё ещё нужно устранять дубли. [Паттерн Transactional Outbox](https://microservices.io/patterns/data/transactional-outbox.html).

Например, сохранение решения о риске одновременно добавляет в outbox запись `TransactionScored`. Обработка уведомлений происходит позже и не блокирует ответ сервиса скоринга.

### RabbitMQ и Kafka

RabbitMQ часто используют для очередей задач с маршрутизацией. В его модели обменников `direct` использует точное совпадение ключа маршрутизации, `topic` — шаблоны ключей, а `fanout` рассылает сообщения во все связанные очереди. Подтверждение потребителя позволяет брокеру удалить сообщение из его очереди; подтверждение публикации отдельно относится к приёму сообщения брокером. [Подтверждения потребителей и публикаций RabbitMQ](https://www.rabbitmq.com/docs/confirms).

Kafka организует сохраняемые записи в журналы, разделённые на партиции. Потребители отслеживают позиции через смещения — offsets; чтение или фиксация смещения не удаляют запись немедленно. Правила хранения позволяют прочитать её позже, пока она доступна. Группы потребителей распределяют партиции, поэтому добавление обработчиков не даёт неограниченного параллелизма при фиксированном числе партиций. [Устройство Kafka](https://kafka.apache.org/41/design/design/).

Здесь сопоставляются доставка задач и сохраняемые потоки событий. Выражения «умный брокер» и «умный потребитель» — учебные упрощения, а не полные описания продуктов. Event Sourcing — хранение состояния через последовательность событий — является отдельным решением в устройстве приложения; выбор Kafka сам по себе не означает использование Event Sourcing.

## 13. Идемпотентность: защита от повторных бизнес-эффектов

Идемпотентность означает, что повтор операции имеет тот же предполагаемый эффект, что и однократное выполнение. Ответы могут различаться; определение из второй лекции для HTTP остаётся в силе. Для платежа цель — одно списание, даже если клиент повторяет запрос после потери ответа.

Один из возможных контрактов использует заголовок `Idempotency-Key`. Клиент создаёт ключ для одной задуманной операции и переиспользует его при повторных попытках. Сервер связывает ключ с вызывающей стороной, содержимым запроса, состоянием обработки и результатом.

```http
POST /payments HTTP/1.1
Host: api.example.com
Content-Type: application/json
Idempotency-Key: 8b804f83-2d94-46db-8987-0f7f98a16601

{"account_id":"42","amount_minor":12500,"currency":"RUB"}
```

Это учебный контракт, включая заголовок и поля денежной суммы. Сервер должен атомарно закрепить ключ за операцией и согласовать его с бизнес-эффектом. Простая последовательность «посмотреть в Redis, затем выполнить платёж» может привести к гонке при одновременном поступлении двух запросов. Нужно определить поведение при изменении тела запроса под тем же ключом, параллельных запросах, сбоях и истечении срока хранения ключа. Новый ключ для каждой повторной попытки делает устранение дублей неработоспособным.

## 14. Наблюдаемость и гибридная архитектура

**Метрики** обобщают поведение: частоту запросов, долю ошибок, размер очереди и задержку. **Логи** фиксируют отдельные события с контекстом, достаточным для расследования. **Распределённые трассировки** связывают операции разных сервисов. В качестве инструментов можно использовать Prometheus, ELK/Loki и Jaeger/Tempo, а OpenTelemetry — для инструментирования приложения, сбора и экспорта телеметрии.

Идентификатор корреляции позволяет объединять связанные записи при расследовании. Контекст трассировки связывает отдельные участки выполнения — spans — и имеет более строгую структуру, чем произвольная строка корреляции. Подходящий контекст передают через HTTP, gRPC и метаданные сообщений. Ключ идемпотентности платежа идентифицирует задуманную операцию, а идентификаторы корреляции и трассировки служат диагностике.

Измерять нужно результат, важный пользователям. Задержка p95 — процентиль: 95% наблюдений имеют значение не выше указанного; p99 описывает более дальнюю часть распределения. Быстрый ответ о приёме события может сочетаться с растущей очередью обработки. Измеренные показатели сервиса сравнивают с согласованной целью качества обслуживания или SLA.

![Гибридная система обработки транзакций](../assets/lecture-003/hybrid-transaction-architecture.png)

Эта учебная архитектура сочетает способы взаимодействия под разные потребности. Не каждому приложению нужны все её компоненты. На каждой границе определяют контракт, момент завершения операции, таймаут, поведение при дублях, правила доступа и телеметрию.

Основной вывод лекции: выбор способа взаимодействия нужно обосновывать требованиями и измерениями. Типизированные контракты уменьшают неоднозначность; асинхронный обмен помогает сгладить всплески нагрузки; постоянные соединения поддерживают интерактивный обмен. Каждый выбор также требует работы над обработкой сбоев, развёртыванием и наблюдаемостью.

# Краткий конспект Лекции 1. Введение в API-технологии

## Одна главная мысль

API — это не адрес и не технология. Это понятное обещание между программами: что можно попросить, что для этого передать, какой результат получить и что произойдёт при ошибке. Пока это обещание сохраняется, поставщик может менять базу данных, язык или модель, не ломая клиента.

Представьте кнопку «Получить прогноз». Клиенту нужен прогноз и понятная ошибка, а не путь к файлу модели и название таблицы. Хороший API оставляет внутреннюю кухню внутри.

## Словарь человеческим языком

- **API (Application Programming Interface)** — граница, через которую одна программа пользуется возможностями другой.
- **API-контракт** — обещание об операциях, входах, результатах, ошибках и ограничениях.
- **1-Tier** — экран, логика и данные находятся в одном локальном приложении.
- **2-Tier** — толстый клиент выполняет основную логику и напрямую работает с сервером базы данных.
- **3-Tier** — клиент обращается к серверу приложений через API, а уже сервер работает с данными.
- **CORBA** — способ вызывать распределённые объекты; интерфейс описывается на IDL, вызовы передаёт ORB.
- **SOAP** — протокол структурированных XML-сообщений.
- **WSDL** — машиночитаемое описание операций, типов данных и адресов SOAP-сервиса.
- **REST** — стиль, в котором API строится вокруг ресурсов и единого интерфейса. REST часто использует HTTP и JSON, но не равен им.
- **gRPC** — удалённые вызовы по контракту `.proto` с Protocol Buffers и HTTP/2.
- **API инференса** — вход в ML-сервис: проверяет запрос, запускает нужную версию модели и возвращает результат.
- **Feature store (хранилище признаков)** — место, откуда обучение и инференс получают согласованные признаки.
- **Model registry (реестр моделей)** — каталог версий моделей и их статусов: какая тестируется, какая развёрнута, какая устарела.
- **Дрейф** — данные или их связь с результатом изменились, поэтому прежняя модель может работать хуже.
- **DataOps** — всё, что помогает надёжно получать, обрабатывать и контролировать данные.
- **ModelOps** — всё, что помогает обучать, регистрировать, развёртывать и обновлять модели.
- **Жизненный цикл модели** — повторяющийся путь от постановки задачи до мониторинга и следующего обновления.

## Как росла система

Сначала всё помещалось в одной программе. Затем общие данные вынесли на сервер. Когда прямой доступ множества клиентов к базе стал мешать развитию, между ними появился сервер приложений.

### Три архитектурные схемы

| Модель | Где находится логика | Как доступны данные | Главный компромисс |
|---|---|---|---|
| 1-Tier | В локальном приложении | Локально | Автономность, но ограниченная совместная работа |
| 2-Tier | На клиенте и частично в СУБД | Прямое соединение клиента с БД | Простота, но сильная связь и нагрузка на БД |
| 3-Tier | На сервере приложений | Через API | Централизованное управление, но сложнее эксплуатация |

Важно: три слоя не делают систему автоматически быстрой или безопасной. Они лишь помогают разделить ответственность. Всё остальное подтверждается измерениями и проверками.

## Как программы договаривались

За названиями CORBA, SOAP, REST и gRPC стоит один и тот же вопрос: как двум программам точно описать запрос и ответ. Ответы получились разными, потому что технологии создавались в разное время и для разных задач.

| Подход | Контракт | Типичный контекст |
|---|---|---|
| CORBA | IDL | Унаследованные распределённые корпоративные системы |
| SOAP | WSDL + XSD | Строгие XML-схемы и корпоративные политики |
| REST API | HTTP-семантика, часто OpenAPI | Публичные, веб- и мобильные API |
| gRPC | Protocol Buffers (`.proto`) | Межсервисные и потоковые вызовы |

Здесь нет победителя «на все случаи жизни». Подход выбирают под потребителей, инфраструктуру и требования. HTTP, REST и OpenAPI подробно разбираются в лекции 2, а осознанный выбор между стилями API — в лекции 3.

## Что происходит после нажатия «Получить прогноз»

```text
клиент → балансировщик → API инференса
       → признаки/предобработка → кэш (если допустим)
       → сервер модели → результат и метаданные
       → журналирование и мониторинг
```

Снаружи это выглядит как один запрос. Внутри API инференса проверяет входные данные, выбирает версию модели, запускает предобработку и собирает стабильный ответ. Кэш может ускорить работу, но только если правильно заданы ключ, срок жизни и правила повторного использования. А в логах нельзя бездумно сохранять персональные или конфиденциальные данные.

## Почему моделью нельзя заняться один раз

Модель работает с меняющимся миром: приходят новые данные, меняется поведение пользователей и со временем возникает дрейф. Поэтому её путь — не прямая до релиза, а цикл.

1. **Бизнес-анализ:** цель, потребитель, ограничения и измеримые критерии успеха.
2. **Работа с данными:** сбор, очистка, разметка и построение признаков.
3. **Разработка:** выбор алгоритма, обучение и настройка модели.
4. **Валидация:** качество, устойчивость, переобучение и соответствие KPI.
5. **Внедрение:** регистрация версии, развёртывание и доступ через API или пакетный процесс.
6. **Мониторинг:** ошибки, задержка, качество, дрейф и решение об обновлении.

Названия вроде DataOps, ModelOps, AnalyticOps и low-code помогают распределить эту работу между процессами и командами. RAISA из презентации — один из способов разложить платформу на такие части, а не готовый рецепт для любой компании.

## Пять ловушек

- API — не просто URL: без входов, результатов, ошибок и ограничений нет полноценного контракта.
- Прямой доступ клиента к БД связывает клиента со схемой хранения и бизнес-правилами.
- REST и gRPC решают разные задачи; выбор зависит от потребителей, совместимости, потоков, задержки и эксплуатации.
- Масштабирование требует измерений: очередь, кэш, добавление экземпляров и разбиение модели имеют собственную цену.
- Точность модели недостаточна без контроля задержки, доступности, данных, дрейфа и версий.

# Лекция 2 — краткий конспект

HTTP, REST, форматы данных и OpenAPI. ПРБ. Для повторения; объяснения и полные примеры — в [полном конспекте](../lectures/002_http-rest-openapi-data-contracts.md).

Маршрут лекции: **HTTP** (структура, версии, методы, повторы и статусы) → **REST** (ресурсы, представления и кэш) → **форматы данных** (JSON, XML, CSV, Parquet) → **схемы и валидация** → **OpenAPI 3.2.1 и Swagger UI** (описание и проверка настоящих запросов).

## Центральная связь

```text
Цель потребителя → операция → HTTP-запрос → проверка → ответ/ошибка
                             ↕ описание обещаний
                         OpenAPI 3.2.1
```

Контракт задаёт операции, входы, результаты, ошибки и ограничения. Успешная проверка схемы не доказывает правильность смысла или выполнения действия.

## HTTP: что читать

```http
GET /offices/42/forecast?days=1 HTTP/1.1
Host: 127.0.0.1:8000
Accept: application/json

```

GET — намерение; путь — ресурс; 42 — path-параметр; days=1 — query. В этом GET тела нет. `Content-Type` описывает переданное содержимое, `Accept` — предпочтения клиента для ответа. Заголовков может быть много; каждый записывается отдельной строкой. Пустая строка отделяет заголовки от содержимого. `Content-Length` измеряет байты.

**Версии:** 1.1 — текстовые начальные строки/заголовки и TCP; 2 — бинарные кадры и несколько потоков внутри TCP; 3 — потоки поверх QUIC/UDP. Методы и статусы сохраняют смысл. HTTP/3 обеспечивает надёжную передачу средствами QUIC; универсального ускорения не обещает.

**Первые RFC:** 1.1 — январь 1997 → 18 лет 4 месяца → 2 — май 2015 → 7 лет 1 месяц → 3 — июнь 2022. RFC 9112/9113 от июня 2022 — обновления правил 1.1/2. В снимке Cloudflare Radar (Worldwide, All traffic, 7 дней до 14.09.2026 14:30 UTC) чаще HTTP/2: 52,5%; 1.x — 27,6%; 3 — 19,9%. Это наблюдаемая выборка, не статистика всех API.

## HTTP/2 и gRPC

```text
Одно соединение → streams 1 и 3 → HEADERS и DATA
Кадр: Length24 | Type8 | Flags8 | R1 | StreamID31 | payload
```

Идея схемы: [Carson](https://cabulous.medium.com/http-2-and-how-it-works-9f645458e4b2); правила: [RFC 9113 §§4–5](https://www.rfc-editor.org/rfc/rfc9113.html#section-4). Числа у полей — биты; заголовок занимает 9 байт, Length задаёт байты payload. Stream ID связывает ответ с запросом, а не нумерует кадры. HEADERS/HPACK переносит поля; DATA — тело. `END_HEADERS` заканчивает блок полей, `END_STREAM` — отправку в данном направлении. Начальный HEADERS предшествует DATA; незаконченный HEADERS/CONTINUATION не перемежают другими потоками.

gRPC — вызовы методов удалённых сервисов по `.proto`, обычно с Protobuf. Подходит, например, для backend → сервис готовых прогнозов. Unary: один запрос/ответ; streaming: сообщения клиента, сервера или обоих. Один RPC использует HTTP/2 stream, но границы сообщений gRPC и DATA не обязаны совпадать. `.proto`, OpenAPI и HTTP/2 описывают разные уровни.

## Методы и повторы

| Метод | Назначение | Идемпотентен по семантике метода |
|---|---|---|
| GET | Получение представления | Да |
| HEAD | Как GET, без содержимого ответа | Да |
| OPTIONS | Варианты взаимодействия | Да |
| PUT | Полная замена/создание по целевому URI | Да |
| DELETE | Удаление связи ресурса с функциональностью | Да |
| POST | Обработка содержимого по правилам ресурса | Общей гарантии нет |
| PATCH | Документ частичных изменений | Зависит от изменений и контракта |

Безопасные GET/HEAD/OPTIONS не запрашивают бизнес-изменение; логирование допустимо. «Безопасный» здесь не означает защиту от атак. Идемпотентность — одинаковый предполагаемый эффект повторов, а не одинаковые ответы. PATCH «установить 100» и «прибавить 10» ведут себя по-разному. Таймаут не доказывает, что действие не выполнено.

Полный CRUD на каждом URI не нужен: операции следуют сценариям. 405 + Allow — метод не разрешён ресурсу; 501 — не распознан/не реализуется сервером. Мок без хранения не доказывает защиту POST от дублей.

GET не предназначен для удаления: кэши, роботы и предварительная загрузка полагаются на безопасное чтение. Тело GET не имеет общепринятой семантики и может быть отклонено; частный договор не обеспечивает совместимости посредников. Для сложного поиска с телом можно определить POST.

## Ответы и ошибки

200 — успех с представлением; 201 — создан новый адресуемый объект API (например, подписка, URI может быть указан в Location); 202 — принятие без обещания завершения; 204 — успех без тела; 400 — клиентская ошибка запроса; 404 — не найдено; 422 — понятное и синтаксически корректное содержимое, инструкции которого нельзя обработать; 500 — внутренняя ошибка; 502 — неверный ответ upstream; 503 — временная недоступность (возможен Retry-After); 504 — upstream не ответил вовремя.

**upstream — сервер, куда мы отправляем запрос**. В обсуждении 502/504 это сервер, к которому обращается наш шлюз или прокси.

1xx — промежуточная информация (100 Continue). 301 — постоянный новый URI; 307/308 сохраняют метод при временном/постоянном перенаправлении. 304 — условное чтение: можно использовать сохранённое представление, тела нет. 401 — нет действительных credentials; 403 — отказ в доступе; 405 — метод не разрешён. Статус 5xx сам по себе не гарантирует безопасность повтора POST.

В Swagger UI проверяем `days=1/7`; `days=2` отправляем через `curl`, потому что enum в UI предлагает только 1 и 7. POST в UI читаем, а выполняем через `curl` из-за CORS между портами сервисов.

В демо `days=1/7` → 200 и 24/168 точек; `days=2` → 422 `error.code=invalid_request`; `days=abc` → стандартный `detail` FastAPI. Офис 43 → 404 `forecast_not_ready`; 999 → 404 `office_not_found`.


## HTTP → REST: устройство интерфейса и кэш

Ресурс — адресуемое понятие; представление — переданное состояние, например JSON. Ограничения REST: клиент–сервер, stateless, кэширование, единообразный интерфейс, слои, необязательный code-on-demand. Единообразие включает идентификацию ресурсов, представления, самодостаточные сообщения и гипермедиа.

Гипермедиа подсказывает из ответа, куда перейти и какие действия доступны. Например, `links.office.href = "/offices/42"` — проектируемая связь; в текущем моке её нет.

Stateless допускает бизнес-данные на сервере, но запрос не зависит от скрытого диалога. URI+JSON не доказывают REST. `no-cache` требует проверки перед повторным использованием; `no-store` запрещает хранение в рамках директивы. Свежесть определяется договором, а не самим фактом получения 200.

## REST → Data Store Formats: как выбрать формат

| Формат | Потребитель и чтение | Условие/ограничение |
|---|---|---|
| JSON | Приложение или сервис; JSON-парсер | Вложенная структура; даты и единицы задаются договором |
| XML | Партнёр с XML-контрактом; XML-парсер, при необходимости XSD | Дерево, атрибуты, namespace; XML не равен SOAP |
| CSV | Аналитик/ETL; CSV-reader | Плоская таблица; согласовать диалект, типы, кодировку, пропуски |
| Parquet | Аналитика истории; библиотека/движок читает колонки | Бинарный формат со схемой; выигрыш зависит от файла и запроса |

**XSD (XML Schema Definition)** описывает допустимую структуру и типы XML; например, `xs:nonNegativeInteger` запрещает отрицательное число. XML-парсер и XSD-валидатор выполняют разные задачи.

Все четыре можно передавать по HTTP; каждой операции не нужны все четыре. Пустая ячейка CSV не получает смысл null автоматически. JSON `null`, отсутствие поля и 0 различаются: в примере `visitors: null` означает неизвестное число, `visitors: 0` — известное отсутствие посетителей. Отсутствующее обязательное поле нарушает `required`. Это отдельная проектируемая схема; реальный POST мока принимает только целое `visitors ≥ 0`.

## Схема и OpenAPI

`properties` описывает поля, `required` требует их наличия. Разрешение null задаётся отдельно, например `type: [integer, 'null']` в YAML-схеме. `default` не заставляет любой валидатор вставлять значение; проверка `format` зависит от инструмента. Верный тип не подтверждает единицы и бизнес-смысл.

Вход проходит парсинг → проверку схемы → предметные правила **до действия**; затем проверяется ответ. Корректный integer `office_id=999` не доказывает существование офиса.

**OAS → документ → Swagger UI → сервер.** `openapi: 3.2.1` — версия формата; `info.version` — версия описания. `servers` задаёт базовый адрес; `paths` + метод — операцию; `parameters` — path/query; `requestBody` — тело; `responses` — результаты; `components/schemas` и `$ref` — повторное использование схем.

Схема задаёт допустимые значения, Example Value показывает одно значение, Server response после Execute — реальный ответ. Проверяют отдельно документ/ссылки, примеры/схемы и поведение сервера. Изменение YAML само не исправляет сервер.

## Совместимость и самопроверка

Новое обязательное поле запроса ломает старого отправителя. Удаление поля ответа ломает ожидающего его читателя. Добавление поля или enum безопасно только при совместимости реального читателя. Смена «посетители за час» на «за сутки» нарушает смысл даже при прежней структуре. **Вывод: в договоре фиксируем единицы и период измерения; одной проверки типов недостаточно.**

Проверьте себя: объясните маршрут одного запроса, обоснуйте метод, формат и ошибку, затем назовите изменение, которое сломает старого клиента.

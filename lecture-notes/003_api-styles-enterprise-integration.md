# Лекция 3 — краткий конспект


## Главная идея

Способ взаимодействия выбирают по потребностям потребителя, требуемому времени завершения, нагрузке, поведению при сбоях и бюджету эксплуатации. Система может сочетать разные подходы на разных границах. Названия технологий не гарантируют производительность или надёжность.

## Стили API

| Подход | Основная идея | Типичное применение | Что нужно учитывать |
|---|---|---|---|
| REST | Обращение к ресурсам и обмен представлениями по HTTP | Внешние API и обычные операции «запрос — ответ» | Структуру ответов, кэширование, совместимость |
| GraphQL | Выбор полей из типизированной схемы | Экраны с разными сочетаниями связанных данных | Стоимость работы резолверов и правила доступа |
| gRPC | Вызов методов из `.proto`; обычно HTTP/2 и Protobuf | Типизированные внутренние вызовы и потоки | Предельное время ожидания, развитие схем, балансировку |
| WebSocket | Постоянное двустороннее соединение для текста и бинарных данных | Чаты, панели мониторинга, оперативные обновления | Ресурсы соединений, переподключение, пропущенные обновления |
| Событийный обмен | Публикация событий или передача задач через брокер | Фоновые реакции и сглаживание всплесков нагрузки | Дубли, накопление очереди, отложенную согласованность |

**Overfetching — избыточная выборка:** получение ненужных полей. **Underfetching — недостаточная выборка:** необходимость нескольких запросов для получения нужных данных. GraphQL позволяет выбирать поля, но один запрос всё равно может вызвать множество внутренних обращений. REST тоже может предоставлять ответы для конкретных задач или агрегированные представления.

## gRPC и Protobuf

`.proto` определяет сообщения и методы сервиса. Сгенерированный код связывает приложение с контрактом. Номера полей Protobuf идентифицируют поля при передаче: их сохраняют стабильными, а удалённые номера и имена резервируют. Типы не определяют единицы измерения и бизнес-смысл. [Руководство proto3](https://protobuf.dev/programming-guides/proto3/).

| Модель RPC | Вход | Выход |
|---|---|---|
| Unary — унарный вызов | Одно сообщение | Одно сообщение |
| Server streaming — серверный поток | Одно сообщение | Последовательность сообщений |
| Client streaming — клиентский поток | Последовательность сообщений | Одно сообщение |
| Bidirectional streaming — двунаправленный поток | Последовательность сообщений | Независимая последовательность сообщений |

`PredictBatch` — унарный вызов: `repeated Transaction` означает коллекцию внутри одного запроса, а не поток сообщений. [Основные понятия gRPC](https://grpc.io/docs/what-is-grpc/core-concepts/).

## WebSocket и события

WebSocket позволяет каждой стороне отправлять сообщения после установления соединения. В примере HTTP/1.1 используются Upgrade и ответ `101 Switching Protocols`. Ping/Pong уже предусмотрены протоколом; приложение определяет их использование, переподключение и восстановление. Клиентское маскирование добавляет четыре байта к заголовку немаскированного кадра. [RFC 6455](https://www.rfc-editor.org/rfc/rfc6455.html#section-5).

**Событие** сообщает о факте (`TransactionScored`); **команда** запрашивает действие (`ScoreTransaction`). Производители могут публиковать сообщения без прямого вызова каждого подписчика. Подтверждение брокера не означает завершения обработки подписчиками. Участники по-прежнему зависят от схем и правил доставки.

## Нефункциональные требования (NFR)

- **Задержка (Latency):** время до нужного результата с учётом очереди и обработки. Приём брокером и завершение бизнес-операции — разные этапы.
- **Пропускная способность (Throughput):** сообщения, транзакции или байты за единицу времени. Пакетная обработка может увеличить производительность, добавив время ожидания.
- **Масштабируемость (Scalability):** поведение при росте нагрузки. Базы данных, соединения и число партиций могут ограничить рост.
- **Сопровождаемость (Maintainability):** затраты на изменения, тесты, диагностику и координацию команд.
- **Совокупная стоимость владения (TCO):** вычисления, трафик, память, хранение, инфраструктура и работа разработчиков.

Измеряйте работу с реалистичными сообщениями и числом одновременных обращений. Protobuf не гарантирует фиксированный процент экономии байтов. REST может переиспользовать соединения; gRPC не является безусловным лидером по задержке. Мультиплексирование HTTP/2 не устраняет задержки из-за потерь в TCP. [RFC 9113](https://www.rfc-editor.org/rfc/rfc9113.html#section-1). Балансировка gRPC может выполняться на стороне клиента или через прокси. [Балансировка gRPC](https://grpc.io/blog/grpc-load-balancing/).

## Внешняя интеграция

Документируйте операции, ошибки, правила доступа, квоты и совместимость. OAuth 2.0 поддерживает делегированную авторизацию; OpenID Connect добавляет аутентификацию; mTLS аутентифицирует стороны через сертификаты. Механизмы выбирают по модели доверия. [OpenID Connect Core](https://openid.net/specs/openid-connect-core-1_0.html#Introduction).

**Повторные запросы (Retry):** ограниченное число попыток с экспоненциальным увеличением паузы и случайным разбросом — jitter. Таймаут не доказывает, что операция не выполнена. Изменяющие запросы повторяют только при наличии безопасного контракта повторов.

**Circuit Breaker — предохранитель:** closed пропускает вызовы; open прекращает обращения и возвращает локальный отказ; half-open проверяет восстановление. Запасной ответ должен сохранять документированный смысл результата.

**Ограничение частоты и регулирование потока:** ограничивают принимаемую работу или её темп. Token Bucket допускает ограниченные всплески; Leaky Bucket регулирует скорость выхода; скользящее окно учитывает недавнее использование. `429` означает превышение частоты запросов; `Retry-After` может указывать время ожидания. [RFC 6585 §4](https://www.rfc-editor.org/rfc/rfc6585.html#section-4).

Обозначение версии, например `/v1/`, требует политики совместимости и перехода. OpenAPI описывает интерфейс, но не реализует поведение сервера.

## API Gateway и BFF

**API Gateway — API-шлюз:** общая точка входа, маршрутизация, аутентификация, лимиты трафика, журналирование и обработка TLS. Преобразование протоколов требует определённого соответствия; сервисы сохраняют свои предметные проверки доступа.

**Backend-for-Frontend:** агрегация данных и форма ответа под конкретный клиентский интерфейс. Мобильная сводка и подробная веб-панель могут использовать разные BFF. Агрегация сокращает сетевые обращения клиента, но требует предельного времени ожидания и правил обработки частичных отказов внутренних вызовов.

## Внутренняя интеграция и брокеры

Прямой вызов используют, когда текущей операции нужен немедленный результат. Асинхронная работа подходит, если завершение можно отложить. Обнаружение сервисов находит адреса; балансировка распределяет вызовы. Внутреннему трафику тоже нужны подходящие механизмы идентификации и контроля доступа.

Очереди сглаживают всплески, но длительная перегрузка увеличивает накопленную работу. **RabbitMQ** часто подходит для задач с маршрутизацией; ACK потребителя и подтверждение публикации относятся к разным этапам. [Подтверждения RabbitMQ](https://www.rabbitmq.com/docs/confirms). **Kafka** сохраняет журналы, разделённые на партиции; потребители отслеживают смещения, а чтение не удаляет записи немедленно. [Устройство Kafka 4.1](https://kafka.apache.org/41/design/design/).

- **At-most-once — не более одного раза:** без повторной доставки; возможна потеря.
- **At-least-once — не менее одного раза:** возможны повторы; нужна обработка дублей.
- **Exactly-once — ровно один раз:** один эффект в определённых границах; внешние эффекты требуют участия системы назначения.

**Transactional Outbox:** бизнес-состояние и исходящее событие сохраняют в одной транзакции базы данных; отдельный процесс публикует событие позже. Это устраняет рассогласование между записью в базе и публикацией, но после сбоя процесс может опубликовать событие повторно. [Паттерн Outbox](https://microservices.io/patterns/data/transactional-outbox.html).

## Идемпотентность и наблюдаемость

**Идемпотентность:** повторы имеют тот же предполагаемый эффект, что и одно выполнение; ответы не обязаны совпадать. Один ключ переиспользуют для одного задуманного платежа. Сервер должен атомарно согласовать закрепление ключа за операцией, содержимое запроса, обработку и результат. Отдельный поиск в кэше с последующим изменением может привести к гонке. Нужно определить поведение параллельных попыток, изменённого тела, истечения срока хранения ключа и сбоев.

**Метрики** обобщают поведение; **логи** фиксируют события; **трассировки** связывают операции разных компонентов. Идентификаторы корреляции и контекст трассировки передают через синхронные вызовы и метаданные сообщений. Ключ идемпотентности служит устранению дублей.

Отслеживайте долю ошибок, задержки p95/p99, использование соединений, размер очереди и задержку обработки. Быстрый приём задачи может скрывать медленное завершение. Измерения сравнивают с согласованной целью качества обслуживания или SLA.

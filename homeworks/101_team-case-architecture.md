# Домашнее задание 1. Архитектура командного проекта

Спроектируйте архитектуру одного кейса, случайно назначенного вашей команде на семинаре. Продолжите начатую на занятии работу; этот кейс станет проектом команды на весь семестр.

## Задание

1. Выделить внешних потребителей системы.
2. Разработать контекстную диаграмму C4, уровень 1.
3. Разработать контейнерную диаграмму C4, уровень 2.
4. Выбрать протоколы взаимодействия сервисов между собой и с внешними потребителями.
5. Выбрать базы данных для хранения информации.*

К диаграммам приложите краткое объяснение выбора протоколов и баз данных. Учитывайте функциональные и нефункциональные требования своего кейса при проектировании. Первое ДЗ завершается архитектурным решением; реализация системы выполняется в течение семестра.

`*` — пункт, в котором необходимо самостоятельно прийти к неочевидному решению.

## Что сдать

Один результат от команды: состав команды и назначенный кейс, внешние потребители, две диаграммы C4 и решения по протоколам и хранению. Диаграммы должны быть доступны для просмотра. Продолжайте ту же работу в приватном fork или репозитории команды; передайте ссылку на PR/MR с результатами и итоговый commit.
Инструкции — в [ветке семинара 2](https://github.com/TheTonyPub/api-technologies-2026/tree/seminar/01-api-scenarios)

## Задача 1. Антифрод система.

> Спроектировать информационную систему противодействия мошенничеству.

### Функциональные требования

1. Нужно сформировать online витрину данных с историческим данными клиентов (заранее)
2. Загрузить данные в Online витрину
3. Нужно получить событие из системы АБС (транзакция)
4. Обогатить ее информацией о клиенте (возраст, пол, место проживания)
5. Получаем агрегаты из online витрины по средней транзакции клиента
6. Вызываем модель на основе полученных данных
7. С помощью правил принимаем решение
8. В случае подтверждения отвечаем 1, иначе 0.

### Нефункциональные требования

1. Время ответа 100 мс на весь цикл\*

## Задача 2. Получение данных из СПАРК Интерфакс.

> Спроектировать информационную систему загрузки, хранения и предоставления доступа к данным по юридическим лицам

### Функциональные требования

1. Данные из системы доступны для CRM, АБС, аналитического контура
2. Нужно загрузить данные по клиентам из внешнего источника – Спарк Интерфакс и сохранить в историческое хранилище (формат хранения SCD2)\*
3. Обогатить данные из внутреннего исторического хранилища
4. Загрузить данные с актуальным срезом в Online витрину
5. Разработать сервис получения актуальной информации о клиенте по ИНН
6. Разработать сервис получения всех клиентов из группы компаний
7. Разработать сервис скоринг потенциального клиента банка (вероятность того, что ЮЛ станет клиентом банка) с использованием модели
8. Редко изменяющиеся данные должны кэшироваться с заданным временем жизни

### Нефункциональные требования

1. Цикл загрузки данных по 1 клиенту – 10 сек
2. Время ответа на запросы системы – 1 сек
3. Должно быть обеспечено максимальная простота использования сервиса внешними потребителями

## Задача 3. Прогноз требований к мощности серверов для ИС.

> Спроектировать информационную систему  прогнозирования потребления ресурсов (CPU, RAM, диск)

### Функциональные требования

1. Необходимо собирать информацию о нагрузке на сервера ИС каждую минуту.
2. Необходимо загружать данные в долгосрочное хранилище.
3. Пользователю нужно обеспечить UI для доступа системе.
4. Необходимо реализовать сервис применения модели для прогноза нагрузки на сервера выбранной ИС в горизонте – 1 день, 1 мес, 6 мес, 1 год
5. Система должна хранить информацию о серверах и принадлежности их к ИС.
6. Система должна уведомлять пользователей системы о том, что нагрузки на сервер в перспективе 1 дня и 1 месяца превысит допустимую
7. При прогнозе на 1 день данные должны браться near real time (NRT)
8. К данной системе должны быть подключен ситуационный центр, в котором есть dashboard, показывающий актуальное и прогнозируемое состояние\*

### Нефункциональные требования

1. Время ответа на запросы системы – 1 сек
2. Должно быть обеспечено максимальная простота использования сервиса внешними потребителями

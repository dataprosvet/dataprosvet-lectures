# Домашнее задание 2. Проектирование REST API командного проекта

После лекции 2 спроектируйте HTTP/REST API основных сценариев своего командного кейса. Продолжайте ту же команду и архитектуру из [ДЗ 1](001_team-case-architecture.md). Завершите работу до следующего семинара.

Результат — описание проектных решений и OpenAPI-контракт с примерами. Реализация сервера, обучение модели и развёртывание пока не требуются. Нужны знания ресурсов REST, методов и статусов HTTP, параметров, JSON и OpenAPI из лекции 2; начальное упражнение выполнено на [семинаре 2](../seminars/002_architecture-to-http.md).

## 1. Определите границу API

Укажите, кто обращается к вашей системе и какую задачу решает. Перечислите основные сценарии и ресурсы, которые нужны потребителям. Спроектируйте интерфейс, которым владеет ваша команда; чужие API и все внутренние интеграции заново описывать не нужно.

Для каждого требования своего кейса объясните, где оно выполняется: через внешнюю операцию вашего API, фоновую обработку или внешнего поставщика. Можно использовать короткие пункты с ссылками на операции OpenAPI. Таблица интерфейсов не обязательна. Число эндпоинтов определяется задачей: один случайный запрос не заменяет проект, но создавать CRUD для каждой сущности тоже не нужно.

## 2. Опишите HTTP-операции

Для каждой операции задайте:

- назначение, потребителя, метод и путь;
- параметры пути и query-параметры с типами и ограничениями;
- необходимые заголовки, включая формат передаваемых данных;
- тело запроса, если оно предусмотрено, обязательные поля и допустимые значения;
- успешный статус и данные ответа;
- применимые ошибки и единый формат их описания;
- пример корректного обращения, успешного ответа и хотя бы одного ошибочного случая.

Выбор методов объясните через смысл операции и последствия повторения запроса. Чтение не должно незаметно запускать изменение бизнес-состояния. Если есть списки, обоснуйте фильтрацию и необходимость пагинации. Если операция длительная, объясните получение статуса и результата. Не вводите асинхронную задачу только для наличия дополнительного endpoint.

Не заменяйте ошибку пустым успешным ответом без объяснения. Отличайте неизвестный объект, неверный вход, отсутствие готового результата и сбой зависимости. Для своей системы выберите согласованные статусы и полезные сообщения для клиента.

Если с внешними системами у вас взаимодействие через gRPC или XML, то можете описать только внутренние сервисы, которые взаимодействуют по стандартному REST API, а на контракт внешнего сервиса дать ссылку, если этот сервис реальный и существует.

## 3. Сохраните особенности кейса

**Антифрод.** Покройте приём запроса проверки транзакции и возврат решения 1/0 согласно условию ДЗ 1. Опишите, что входит в исходный цикл с ограничением 100 мс, какие данные готовятся заранее и что получает клиент при невозможности вынести решение. Не переносите сюда схему чтения недельного прогноза из банковского примера.

**СПАРК.** Покройте получение актуальных сведений по ИНН, состава группы компаний и результата скоринга. Различайте актуальный срез и историческое хранение SCD2, срок жизни кэша и время ответа. Сохраните ограничения исходника: загрузка одного клиента — 10 с, ответ — 1 с. Не выдавайте собственные учебные пути за реальные API СПАРК.

**Прогноз серверных ресурсов.** Покройте доступ к текущим показателям, истории и прогнозам выбранной ИС. Сохраните сбор каждую минуту, горизонты день, месяц, шесть месяцев и год, требование NRT для суточного прогноза и ответы за 1 с. Объясните свежесть и поведение при отсутствии готового результата.

Объясните связь операций со своей C4. Изменения архитектуры относительно ДЗ 1 допустимы при явном обосновании. Проектное ограничение времени ответа не считается доказанным без реализации и измерений.

## 4. Оформите результат

В репозитории команды разместите:

1. `api-design.md`: команда, назначенный кейс, ссылка на архитектуру ДЗ 1, потребители, граница, ресурсы, покрытие сценариев, обоснования методов, обработки ошибок и принятых допущений.
2. `openapi.yaml`: OpenAPI **3.2.1**, все проектируемые операции, параметры, схемы, ограничения, статусы и синтетические примеры. Описания операций можно хранить здесь, без повторения в отдельной таблице.

Используйте только вымышленные сведения. Не включайте пароли, токены, персональные данные или реальные адреса банковских систем. В описании проверки укажите использованный инструмент и версию, команду или действия и фактический результат.

## 5. Проверьте контракт

Откройте контракт в совместимом с OpenAPI 3.2.1 средстве просмотра и убедитесь, что все операции и схемы отображаются. Проверьте структуру спецификации и разрешимость ссылок валидатором OpenAPI 3.2.1. Отдельно проверьте примеры против схем: отсутствие структурных ошибок спецификации само по себе не доказывает корректность каждого примера.

Пройдите по каждой операции: можно ли составить запрос без догадок о типах и обязательных полях; согласованы ли пример и схема; получает ли клиент понятный результат ошибки? Не требуйте сетевого выполнения запросов к ещё не реализованному серверу. Используйте [каркас OpenAPI](../attachments/seminar-002/openapi-template.yaml) и [инструкцию проверки](../attachments/seminar-002/README.md). В этом учебном формате контракт — один файл с локальными ссылками `#/...` и встроенными примерами. Из каталога комплекта, с Python 3.12.14:

```sh
python3.12 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python validate_contract.py /путь/к/openapi.yaml
```

В README есть альтернативная проверка через Docker без запуска сервера. Проверяются OpenAPI 3.2.1, ссылки и соответствие примеров схемам. Запишите команду и её вывод. Пустой каркас тоже может пройти проверку формата; полноту проектирования проверьте по требованиям кейса.

## Критерии приёмки

- Покрыты основные сценарии выбранного кейса, а границы и фоновые действия объяснены.
- Ресурсы и операции понятны потребителям; HTTP-семантика согласована.
- Входные и выходные данные описаны однозначно, ошибки полезны клиенту.
- Все проектируемые операции присутствуют в OpenAPI 3.2.1; ссылки и примеры проверены.
- Сохранены существенные ограничения ДЗ 1; допущения не выданы за измеренные свойства.
- Результат можно прочитать и проверить по переданному GitHub commit.

Таблица интерфейсов, серверный код, Docker и обученная модель не требуются и не влияют на приёмку этого этапа.

## Сдача через GitHub

Сдаётся один результат от команды. Сохраните материалы в GitHub-репозитории команды, предоставьте преподавателю доступ и откройте pull request с изменениями этого этапа. В описании укажите команду, кейс, пути `api-design.md` и `openapi.yaml`, связь с ДЗ 1 и результаты проверки. Передайте ссылку на pull request и точный итоговый commit SHA. Изменение файлов после сдачи создаёт новую версию — сообщите её SHA отдельно.

ДЗ 2 и все последующие ДЗ курса сдаются через GitHub. Закрытое условие задания в репозиторий решения копировать не нужно. Для просмотра преподавателем не требуется делать репозиторий публичным.

Перед сдачей убедитесь, что преподаватель открывает PR, оба файла доступны в указанном commit, ссылки на архитектуру работают, нет реальных данных и результаты проверки записаны.

Полное совпадение всех операций нормативного примера не предполагается. Справочник формата: [OpenAPI 3.2.1](https://spec.openapis.org/oas/v3.2.1).
